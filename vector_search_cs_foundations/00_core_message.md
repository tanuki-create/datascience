# 00. ポストの核心

## 一言でいうと

このポストの核心は、**「FAISSで総当たり検索できる」ことと「本番の検索システムとして成立する」ことは別物**だ、という点です。

小規模実験では、数万から数十万件のベクトルをメモリに載せ、クエリごとに全ベクトルとの cosine / inner product / L2 を計算しても成立します。これは実装が単純で、正解も exact なので、モデル比較や検索品質の基準線を作るには非常に有用です。

しかし本番では、件数、次元数、更新頻度、フィルタ、権限、p95 / p99 レイテンシ、再構築、障害復旧、クラウドコストが効いてきます。総当たり検索のままでは、検索1回あたりの計算量だけでなく、メモリ帯域、I/O、同時実行、再インデックス、運用手順が破綻します。

## FAISS総当たり検索で見えないもの

FAISS の Flat index で全件比較する構成は、次の意味でよい出発点です。

- exact search なので recall の基準線になる
- 実装が単純で、インデックスパラメータによる品質劣化がない
- 小規模データでは十分速い
- embedding model、chunking、distance metric の検証に集中できる

一方で、本番で必要な次の要素はほとんど解決しません。

- 権限付き検索
- tenant_id や category によるフィルタ
- 更新、削除、差し替え
- インデックス再構築
- レプリケーション
- シャーディング
- 監査ログ
- バックアップ、リストア
- p99 レイテンシ
- コスト見積もり
- 検索品質の継続評価

つまり、Flat検索は「検索アルゴリズムの実験」としてはよいが、「検索システムの設計」としては足りません。

## IVF / PQ / HNSW は何の問題を解いているのか

IVF / PQ / HNSW は、単なるライブラリのオプションではありません。それぞれ、下位レイヤーの制約に対する設計です。

- IVF は、全件を見ずに「近そうなクラスタだけを見る」ことで探索範囲を減らす。
- PQ は、float ベクトルを短いコードに圧縮し、メモリ帯域と距離計算コストを減らす。
- HNSW は、近傍グラフをたどって有望な候補へ移動し、全点比較を避ける。

これらは速くなる代わりに、真の最近傍を取り逃がす可能性、量子化誤差、メモリ増加、構築時間、更新困難性を引き受けます。

## 本番システムとして成立する条件

本番システムでは、検索が速いだけでは足りません。少なくとも次を満たす必要があります。

- 必要な文書が検索結果に入る
- 権限のない文書が絶対に出ない
- 更新や削除が期待した時間内に反映される
- p95 / p99 レイテンシがSLO内に収まる
- インデックスを無停止で再構築できる
- 障害時に復旧できる
- コストが事業上許容できる
- 検索品質の劣化を検知できる

このため、DB選定や技術選定には、アルゴリズムだけでなく、DB、OS、CPU、ネットワーク、分散システム、セキュリティ、MLOps / LLMOps / RAGOps の知識が効きます。
