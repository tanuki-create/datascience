# 07. 専門用語注釈

この章は、各章で出てくる専門用語を引くための注釈集です。厳密な教科書的定義よりも、検索・RAG・DB選定の文脈で何を意味するかを優先しています。

## ベクトル検索・RAGの基本用語

### ベクトル

数値を並べた配列です。検索システムでは、文章、画像、商品、ユーザーなどを数百から数千次元の数値表現に変換したものを指します。

### embedding

文章や画像などを、意味や特徴が近いものほど近い位置に来るようなベクトルへ変換した表現です。RAGでは文書チャンクとクエリの両方をembeddingにして検索します。

### 次元数

ベクトルが持つ数値の個数です。1536次元なら、1つのベクトルに1536個の数値があります。次元数が増えると表現力が増える可能性がありますが、メモリ、CPU、I/Oコストも増えます。

### chunk

検索しやすいように文書を分割した単位です。RAGでは、文書全体ではなくchunk単位でembeddingを作り、検索結果としてLLMに渡すことが多いです。

### token

LLMやembedding modelが処理するテキストの単位です。単語そのものとは限らず、単語の一部や記号が1 tokenになることもあります。

### semantic search

単語の一致ではなく、意味の近さで検索する方式です。embeddingとベクトル検索を使うことが多いです。

### lexical search

単語や文字列の一致を重視する検索です。BM25や転置インデックスを使う検索エンジンが代表です。

### BM25

全文検索で広く使われるランキング手法です。クエリ語が文書にどれだけよく出るか、文書が長すぎないか、語がどれだけ珍しいかを使ってスコアを計算します。

### hybrid search

キーワード検索とベクトル検索を組み合わせる検索です。固有名詞や型番はキーワード検索、意味的な近さはベクトル検索が得意なので、RAGでは有効なことが多いです。

### reranking

最初の検索で広めに候補を取り、その候補を別のモデルや高精度な計算で並べ直すことです。RAGでは検索精度を上げるためによく使われます。

### grounding

LLMの回答を、検索で得た根拠文書に基づかせることです。RAGでは、回答が根拠に支えられているかが重要です。

### hallucination

LLMが根拠のない内容をもっともらしく生成することです。検索で正しい文脈を渡せない場合にも起きやすくなります。

### citation

回答の根拠となった文書、URL、chunk、ページ番号などを示すことです。業務RAGでは、回答本文と同じくらい重要です。

## 距離・類似度・線形代数

### cosine similarity

2つのベクトルの向きがどれだけ近いかを表す類似度です。文書検索ではよく使われます。ベクトルの長さではなく向きに注目します。

### cosine distance

cosine similarityを距離として扱うために変換した値です。多くの場合、`1 - cosine similarity` のように、小さいほど近い値として扱います。

### inner product

2つのベクトルの対応する要素を掛けて足し合わせた値です。dot productとも呼ばれます。ベクトルの向きだけでなく長さもランキングに影響します。

### dot product

inner productと同じ意味で使われることが多い用語です。推薦システムや最大内積検索でよく出てきます。

### L2 distance

ユークリッド距離です。2つの点の直線距離に相当します。実装上は平方根を取らず、二乗距離のまま比較することもあります。

### metric

距離の性質を満たす関数です。非負性、同一性、対称性、三角不等式などを満たすものを指します。cosine distanceやinner productは、常に厳密なmetricとして扱えるとは限りません。

### normalization

ベクトルの長さを1にそろえる処理です。cosine similarityをinner productで扱うときによく使います。登録時と検索時で方針を統一しないと検索品質が崩れます。

### vector norm

ベクトルの長さです。inner product検索では、ベクトルのnormがランキングに影響することがあります。

### curse of dimensionality

高次元空間では、距離の差が直感と合わなくなったり、探索が難しくなったりする問題です。高次元ベクトル検索でANNが重要になる理由の一つです。

## ANN・インデックス・評価指標

### exact search

真の最近傍を正確に求める検索です。総当たり検索やFlat indexが代表です。ANNの品質評価では基準線になります。

### brute-force search

全データと比較する総当たり検索です。小規模では単純で強いですが、大規模では計算量とメモリ帯域が問題になります。

### Flat index

圧縮や近似をせず、ベクトルをそのまま持つインデックスです。検索時は全件または対象集合を比較するため、正確ですが大規模では重くなります。

### kNN

`k-nearest neighbors` の略です。クエリに最も近いk件を返す検索を意味します。

### ANN

`Approximate Nearest Neighbor` の略です。真の最近傍を必ず返すのではなく、十分近い候補を高速に返す近似検索です。

### top-k

検索結果の上位k件です。RAGではtop-5やtop-10などで候補chunkを取り、必要に応じてrerankingします。

### candidate set

最終結果を決める前に集める候補集合です。ANNではcandidate setを広げるほどrecallは上がりやすく、レイテンシも増えます。

### recall@k

真の上位k件のうち、検索結果にどれだけ含まれているかを見る指標です。ANNの近似でどれだけ取り逃しているかを測るのに使います。

### precision@k

上位k件のうち、正解や有用な結果がどれだけ含まれているかを見る指標です。ユーザーに見せる検索結果の品質を評価するのに使います。

### MRR

`Mean Reciprocal Rank` の略です。最初の正解が何位に出たかを評価する指標です。正解が上位に出るほど高い値になります。

### nDCG

`normalized Discounted Cumulative Gain` の略です。関連度の高い結果が上位に出ているかを見るランキング評価指標です。検索結果の順位品質を見るのに使います。

### hit rate

検索結果の中に少なくとも1つ正解が含まれる割合です。RAGでは「必要な根拠がtop-kに入ったか」を見る簡易指標として使えます。

### ground truth

評価の基準となる正解データです。ANNではFlat検索の結果をground truthにすることがあります。RAGでは人手で正解文書をラベル付けすることもあります。

### HNSW

`Hierarchical Navigable Small World` の略です。近いベクトル同士をつないだ階層グラフを作り、そのグラフをたどって近傍を探します。高recall・低レイテンシを狙いやすい一方、メモリを多く使います。

### graph index

データ点をノード、近傍関係をエッジとして表すインデックスです。HNSWのように、グラフをたどることで全件比較を避けます。

### adjacency list

各ノードがどのノードとつながっているかを保持するリストです。HNSWではこのリストがメモリ使用量に効きます。

### layer

HNSWの階層です。上位層は少数ノードで大きく移動し、下位層は密なグラフで細かく探索します。

### M

HNSWで各ノードが持つ接続数の目安です。大きくするとrecallは上がりやすいですが、メモリと構築時間が増えます。

### efConstruction

HNSW構築時にどれだけ広く候補を探索するかを表すパラメータです。大きくすると良いグラフになりやすいですが、構築が遅くなります。

### efSearch

HNSW検索時に保持する候補数の目安です。大きくするとrecallは上がりやすいですが、検索レイテンシも増えます。

### IVF

`Inverted File` の略です。ベクトル空間をクラスタに分け、検索時に近いクラスタだけを見ることで探索範囲を減らします。

### centroid

クラスタの代表点です。IVFではクエリに近いcentroidを探し、そのクラスタ内を詳しく探索します。

### k-means

データをk個のクラスタに分ける代表的なクラスタリング手法です。IVFのcentroid作成に使われることがあります。

### inverted list

IVFで、あるcentroidに割り当てられたベクトルのリストです。検索時はクエリに近いinverted listだけを調べます。

### nlist

IVFのクラスタ数です。小さすぎると絞り込みが弱く、大きすぎると学習や管理が難しくなります。

### nprobe

IVF検索時に見るクラスタ数です。大きくするとrecallは上がりますが、検索は遅くなります。

### PQ

`Product Quantization` の略です。高次元ベクトルを複数の部分ベクトルに分け、それぞれを短いコードで近似表現します。メモリ削減に強い一方、距離に誤差が入ります。

### quantization

連続値や高精度な数値を、より少ないビット数や代表値で近似することです。メモリとI/Oを削減できますが、精度が落ちる可能性があります。

### codebook

PQなどで使う代表ベクトルの集合です。各部分ベクトルをcodebook内の代表値IDに置き換えます。

### SQ

`Scalar Quantization` の略です。各次元のfloat値を、8bitや16bitなど低精度の値に変換する圧縮方式です。

### binary quantization

ベクトルを二値や少ないビット数で表す極端な量子化です。メモリは大幅に減りますが、精度低下に注意が必要です。

### DiskANN

巨大なベクトルインデックスをディスク上で扱うことを意識したANN系の設計です。メモリに乗らない規模で、I/Oを抑えながら検索するための考え方として出てきます。

### payload index

ベクトルに付随するメタデータを高速に絞り込むためのインデックスです。tenant_id、category、created_atなどでフィルタするRAGでは重要です。

## DB・ストレージ・検索エンジン

### RDB

`Relational Database` の略です。表、行、列、SQL、トランザクションを中心にしたDBです。PostgreSQLやMySQLが代表です。

### PostgreSQL

代表的なオープンソースRDBです。pgvectorを使うと、PostgreSQL内でベクトル保存と類似検索ができます。

### pgvector

PostgreSQLでベクトル型と類似検索を使えるようにする拡張です。既存の業務データ、権限、JOIN、トランザクションと近い場所でRAGを始めやすいのが強みです。

### FAISS

Metaが公開しているベクトル類似検索ライブラリです。高速で多様なindexを持ちますが、DBではないため、永続化、権限、監査、分散運用は別途設計が必要です。

### vector database

ベクトル検索を主目的にしたDBです。ベクトル、メタデータ、ANN index、検索API、分散運用機能などを提供します。

### Milvus

大規模ベクトル検索向けのオープンソースベクトルDBです。大量データや分散構成を見据える場合に候補になります。

### Qdrant

Rust製のベクトル検索エンジンです。payload filterやHNSWを使ったRAG向け検索で候補になります。

### Weaviate

スキーマ、ベクトル検索、ハイブリッド検索、RAG連携を意識したベクトルDBです。抽象度が高く、アプリケーション開発寄りに使いやすい面があります。

### Elasticsearch

Luceneを基盤とする検索エンジンです。全文検索、フィルタ、集計、ログ検索に強く、近年はベクトル検索も統合されています。

### OpenSearch

Elasticsearchから派生したオープンソース検索エンジンです。全文検索、ログ分析、ベクトル検索、ハイブリッド検索で使われます。

### Redis Vector Search

Redisでベクトル検索を扱う機能です。低レイテンシやキャッシュ用途に向きますが、巨大で恒久的なナレッジベース本体として使う場合はメモリコストに注意します。

### ACID

トランザクションの性質を表す言葉です。Atomicity、Consistency、Isolation、Durabilityの頭文字です。業務データの更新を安全に扱うために重要です。

### transaction

複数のDB操作をひとまとまりとして扱う仕組みです。途中で失敗したら巻き戻すことで、不整合を防ぎます。

### consistency

データの整合性です。検索基盤では、原本データ、チャンク、embedding、インデックスの状態がどの程度そろっているかが問題になります。

### eventual consistency

すぐには全ノードで一致しないが、時間が経てば整合するという考え方です。検索インデックスや分散DBでよく出てきます。

### read-after-write

書き込んだ直後に、その書き込みを読める性質です。RAGでは文書更新後すぐ検索に反映されるかという要件に関係します。

### WAL

`Write-Ahead Log` の略です。DBがデータを書き換える前にログへ記録する仕組みです。クラッシュ復旧やレプリケーションに使われます。

### PITR

`Point-in-Time Recovery` の略です。DBを特定時点の状態に復元する機能です。本番DBのバックアップ戦略で重要です。

### query planner

DBがSQLをどう実行するかを決める仕組みです。index scanにするか、sequential scanにするかなどを選びます。

### index scan

DBがインデックスを使って必要な行を探す実行方法です。条件に合う行が少ない場合に有効です。

### sequential scan

テーブル全体を順番に読む実行方法です。対象行が多い場合やインデックスが効かない場合に選ばれます。

### B-tree

RDBでよく使われるインデックス構造です。範囲検索や等価検索に強く、PostgreSQLの通常インデックスでも多用されます。

### LSM-tree

書き込みを高速化し、後でまとめて整理するストレージ構造です。書き込みが多いDBやログ構造ストレージで出てきます。

### inverted index

単語から、その単語を含む文書一覧へ引けるインデックスです。全文検索エンジンの基本構造です。

### posting list

転置インデックスで、ある単語に対応する文書IDのリストです。検索エンジンはposting listを組み合わせて検索します。

### segment

検索エンジンやベクトルDBで、データやインデックスを分割して保持する単位です。更新、削除、merge、compactionの単位になることがあります。

### compaction

複数のファイルやsegmentを整理し、削除済みデータや重複を減らす処理です。性能維持に重要ですが、実行中はI/O負荷が増えます。

### VACUUM

PostgreSQLで、更新や削除で不要になった行領域を整理する処理です。pgvectorのHNSW indexでも、削除や更新が多い場合に運用上意識します。

### mmap

ファイルをメモリ空間にマップして扱う仕組みです。大きなインデックスをOSのページキャッシュと組み合わせて扱うときに出てきます。

### page cache

OSがディスク上のデータをメモリにキャッシュする仕組みです。DBや検索エンジンの性能に大きく影響します。

### IOPS

1秒あたりのI/O操作数です。SSDやクラウドストレージの性能を見る指標です。ベクトル検索でディスクアクセスが混ざる場合に重要になります。

## 分散システム・性能・運用

### shard

データを分割した単位です。大規模検索では、データを複数shardに分けて複数ノードで処理します。

### replica

同じデータのコピーです。可用性を上げたり、読み取り負荷を分散したりするために使います。

### coordinator

分散検索で、複数shardへ問い合わせ、結果を集約する役割のノードや処理です。

### scatter-gather

1つの検索リクエストを複数ノードに散らし、結果を集めてマージする方式です。分散検索では一般的ですが、最も遅いshardが全体の応答時間に効きます。

### consensus

分散システムで複数ノードが同じ決定に合意する仕組みです。クラスタ構成やメタデータ更新の一貫性に使われます。

### Raft

代表的なconsensusアルゴリズムです。分散システムでリーダー選出やログ複製に使われます。

### quorum

合意や書き込み成功に必要な過半数などの条件です。可用性と整合性のトレードオフに関係します。

### partial failure

システム全体ではなく、一部ノードや一部ネットワークだけが失敗する状態です。分散システムでは通常ケースとして設計します。

### p50

50パーセンタイルのレイテンシです。リクエストの半分がこの時間以内に終わることを意味します。中央値に近い指標です。

### p95

95パーセンタイルのレイテンシです。リクエストの95%がこの時間以内に終わることを意味します。本番のユーザー体験を見る上で平均より重要です。

### p99

99パーセンタイルのレイテンシです。遅い1%のリクエストを含めたtail latencyを見る指標です。RAGではLLM呼び出しと合算されるため重要です。

### tail latency

分布の末尾にある遅いリクエストのレイテンシです。分散検索では、複数shardの最遅応答がtail latencyを悪化させます。

### QPS

`Queries Per Second` の略です。1秒あたりに処理する検索リクエスト数です。

### throughput

単位時間あたりに処理できる仕事量です。検索ではQPS、indexingでは投入件数/秒などで表します。

### latency

1リクエストが完了するまでの時間です。検索ではp50、p95、p99を分けて見る必要があります。

### SLO

`Service Level Objective` の略です。サービスが満たすべき目標値です。例として「検索p95を200ms以内にする」などがあります。

### SLA

`Service Level Agreement` の略です。顧客や利用者との契約上のサービス品質です。SLOより外向きで、違反時の責任が明確なことが多いです。

### indexing lag

原本データの更新から、検索インデックスに反映されるまでの遅れです。RAGでは文書更新や削除の反映時間として重要です。

### blue-green index

新旧2つのインデックスを並行して持ち、検証後に切り替える運用方式です。無停止reindexやrollbackに使います。

### reindex

データからインデックスを作り直すことです。embedding model変更、距離関数変更、量子化設定変更、削除データ整理などで必要になります。

### backpressure

下流処理が追いつかないとき、上流の投入量を抑える仕組みです。indexingやembedding生成のバーストから検索APIを守るために使います。

### rate limit

一定時間あたりのリクエスト数を制限する仕組みです。テナントごとの公平性や過負荷防止に使います。

### load shedding

過負荷時に一部リクエストを意図的に落とす設計です。全体障害を避けるために使います。

### capacity planning

将来のデータ量、QPS、メモリ、CPU、ストレージ、コストを見積もることです。検索基盤では次元数とレプリカ数が大きく効きます。

### graceful degradation

障害時に完全停止するのではなく、機能を落としてでもサービスを継続する設計です。RAGではrerankerを止める、古いインデックスにfallbackするなどが例です。

### observability

システム内部の状態をログ、メトリクス、トレースから理解できる性質です。RAGではインフラだけでなく検索品質も観測対象です。

### OpenTelemetry

ログ、メトリクス、トレースを標準的に収集するための仕組みです。分散システムの原因調査に役立ちます。

## セキュリティ・ガバナンス

### ACL

`Access Control List` の略です。どのユーザーやグループがどの文書へアクセスできるかを表します。RAGでは検索時に必ず適用する必要があります。

### tenant

SaaSなどで、顧客や組織ごとに分かれた利用単位です。検索基盤ではテナントごとのデータ分離、負荷分離、権限分離が重要です。

### tenant isolation

テナント間でデータや負荷が混ざらないように分離することです。共有インデックスでtenant_idフィルタを強制する方式と、テナント別インデックスにする方式があります。

### document-level ACL

文書単位のアクセス制御です。RAGではchunk単位で検索しても、元文書の権限を必ず守る必要があります。

### PII

`Personally Identifiable Information` の略です。個人を特定できる情報です。原文だけでなく、ログ、検索結果、embeddingも取り扱いに注意します。

### audit log

誰がいつ何を検索・閲覧・変更したかを記録するログです。業務RAGやエンタープライズ検索では重要です。

### encryption

暗号化です。保存時暗号化、通信時暗号化、バックアップ暗号化などがあります。

### right to be forgotten

削除要求に応じて個人データを消す権利です。検索インデックス、バックアップ、キャッシュ、embeddingにも削除反映が必要になる場合があります。

## MLOps / LLMOps / RAGOps

### MLOps

機械学習モデルを本番運用するための実践です。モデル管理、評価、デプロイ、監視、再学習を含みます。

### LLMOps

LLMアプリケーションを本番運用するための実践です。prompt、model、tool、評価、コスト、ガードレールなどを管理します。

### RAGOps

RAGシステムを運用するための実践です。データ取り込み、chunking、embedding、index version、検索品質、回答品質、引用、権限を継続的に管理します。

### model registry

モデルのバージョン、メタデータ、評価結果、デプロイ状態を管理する仕組みです。embedding modelの変更管理にも使います。

### dataset versioning

データセットの版を管理することです。検索評価や再現性のために、どの文書集合で評価したかを記録します。

### index versioning

検索インデックスの版を管理することです。embedding model、距離関数、正規化方針、chunking、index parameterと紐付けます。

### online evaluation

本番トラフィックやユーザー行動を使って評価することです。クリック、フィードバック、A/Bテストなどが含まれます。

### offline evaluation

事前に作った評価データセットで評価することです。recall@k、MRR、nDCGなどを使い、リリース前の回帰テストに使います。

### A/B test

2つ以上の方式を実ユーザーに分けて提供し、品質や行動指標を比較する実験です。検索ランキングやRAG回答改善の評価に使います。
