# 10. 設計レビュー用チェックシート

この章は、RAG・ベクトル検索基盤の設計レビューでそのまま使うためのチェックシートです。目的は技術選定の正解を一発で決めることではなく、未確定の前提、測定していない性能、運用で事故になりやすい論点を明らかにすることです。

未記入が多い場合は、DB製品比較より先に要件整理を行います。

## 1. DB選定

| 確認項目 | OK条件 | レビューで見るリスク |
|---|---|---|
| 正本DBと検索インデックスの責務が分かれているか | 原本、chunk、embedding、metadata、権限の置き場所が説明できる | ベクトルDBを正本扱いして復旧・監査・削除で詰まる |
| 既存DBとの関係を説明できるか | PostgreSQL中心、検索エンジン中心、専用ベクトルDB分離などの理由が明確 | 流行しているDBを理由なく追加する |
| 全文検索の必要性を評価したか | 固有名詞、型番、エラーコード、日付、完全一致の要否を確認済み | ベクトル検索だけで検索品質を満たせない |
| JOINや業務トランザクションが必要か | 必要な場合はRDB側に寄せる設計になっている | 検索DB側で業務整合性を無理に再実装する |
| 運用チームの能力に合っているか | バックアップ、監視、再構築、障害対応を担当できる | 小さなチームに重い分散DBを載せる |
| 移行余地があるか | 検索API、評価データ、index versionがDB実装と密結合していない | PoCの実装が本番制約を固定する |

判断の目安です。

- 既存PostgreSQL中心、小中規模、権限や業務データがRDBにあるなら、PostgreSQL + pgvectorを第一候補にします。
- 全文検索、フィルタ、集計、検索ランキングが重要なら、Elasticsearch / OpenSearchを検討します。
- 検索負荷を独立スケールさせたい、フィルタ付きANNが重要なら、Qdrant、Weaviate、Milvusなどの専用ベクトルDBを検討します。
- FAISS単体は、評価、PoC、静的コーパス、オフライン検索には強いですが、DBではないため本番周辺機能を別途設計します。

## 2. ANN・インデックス

| 確認項目 | OK条件 | レビューで見るリスク |
|---|---|---|
| exact baselineを持っているか | Flat検索や小規模全探索で基準結果を作っている | ANNの近似誤差を測れない |
| recallとレイテンシを同時に見たか | recall@k、nDCG、p95 / p99を同じ条件で測定 | 速いが根拠文書を落とす |
| top-kとcandidate sizeを分けているか | ANN候補数、rerank候補数、最終context数が別に設計されている | top-kを増やすだけでLLM入力とコストが膨らむ |
| 距離関数と正規化が一貫しているか | embedding model、DB、評価コードで一致 | cosine想定なのに未正規化inner productで品質劣化 |
| インデックスパラメータを記録しているか | HNSWのM/efConstruction/efSearch、IVFのnlist/nprobeなどを版管理 | 再現不能な性能差が出る |
| フィルタありの性能を測ったか | tenant_id、ACL、document_type、期間など実条件で測定 | フィルタなしベンチだけ速い |
| 再構築時間を測ったか | build時間、切替手順、rollbackがある | モデル更新や障害復旧で長時間停止する |

## 3. フィルタ・権限

| 確認項目 | OK条件 | レビューで見るリスク |
|---|---|---|
| tenant_idを検索条件に強制しているか | アプリ層任せではなく検索クエリに入る | テナント境界を越えた検索結果が返る |
| document-level ACLを扱えるか | chunk検索でも元文書の権限を守る | chunk単位で権限が欠落する |
| 検索後フィルタだけに依存していないか | フィルタ前、フィルタ中、候補拡張の方針がある | top-k不足、または危険なfallback |
| 権限変更の反映SLOがあるか | 変更後何秒・何分で検索結果から消えるか定義 | 退職者・異動者が古い権限で検索できる |
| キャッシュキーに権限が含まれるか | tenant、user、group、ACL version、index versionを考慮 | 他ユーザーの検索結果を再利用する |
| 監査ログを取るか | 誰が、いつ、何を検索し、どの文書を参照したか記録 | 情報漏洩時に追跡できない |

権限は回答生成前に守る必要があります。LLMに渡したcontextは、画面に表示しなくても漏洩経路になります。

## 4. 更新・削除

| 確認項目 | OK条件 | レビューで見るリスク |
|---|---|---|
| 更新処理が冪等か | 同じdocument_id/versionを再投入しても重複しない | リトライで古いchunkと新しいchunkが混在する |
| delete + insertの単位が明確か | document、chunk、embedding、metadataを一貫して更新 | 古いチャンクだけ残る |
| 削除反映を検索で確認しているか | API成功だけでなく検索結果から消えたことを検証 | 削除済み文書がRAG回答に使われる |
| 論理削除と物理削除の方針があるか | tombstone、compaction、reindexの運用がある | 論理削除が溜まり検索効率が落ちる |
| embedding model変更時の移行手順があるか | 新旧indexの並行構築、評価、切替、rollbackがある | 新旧ベクトル空間が混ざる |
| indexing lagを監視しているか | 原本更新から検索反映までの遅延を測る | 鮮度劣化に気づけない |

削除は検索品質ではなくセキュリティとコンプライアンスの論点です。レビューでは、正常系APIではなく、失敗、リトライ、部分更新、rollbackを確認します。

## 5. RAG品質

| 確認項目 | OK条件 | レビューで見るリスク |
|---|---|---|
| 評価クエリを持っているか | 代表質問、難問、権限境界、更新直後の質問を含む | 雰囲気で品質判断する |
| 正解根拠をラベル付けしているか | answerだけでなく期待source/chunkがある | 回答が合っていても根拠が不明 |
| 検索品質と回答品質を分けて測るか | retrieval metricsとgeneration metricsを別に見る | プロンプト問題と検索問題を混同する |
| hybrid searchを検討したか | BM25、ベクトル、metadata boostの必要性を評価 | 固有名詞や型番に弱い |
| rerankerを使う条件が明確か | 候補数、レイテンシ、コスト、fallbackを設計 | rerankが高価なだけで効いていない |
| 引用を返すか | source_uri、document_id、page、chunk_idを回答に紐付け | 根拠確認できない |
| 回答不能を扱うか | 根拠不足時は「不明」と返す条件がある | LLMが根拠なしで補完する |

## 6. 運用

| 確認項目 | OK条件 | レビューで見るリスク |
|---|---|---|
| SLOが分解されているか | 検索、rerank、LLM生成、全体応答のp95 / p99がある | 全体が遅いとき原因を切り分けられない |
| メトリクスがあるか | latency、QPS、empty result、filter後候補数、indexing lag、error rateを取得 | 品質劣化を検知できない |
| ログがデバッグ可能か | query、filter、top候補、score、index version、model versionを追える | 同じ問い合わせを再現できない |
| blue-green index切替があるか | 新indexを検証後に切替、rollback可能 | 再構築が本番停止イベントになる |
| バックアップ・復旧手順があるか | 正本と派生indexの復旧方針が分かれている | 検索基盤障害から戻せない |
| 縮退運転があるか | reranker停止、低k検索、古いindex fallbackなどの方針 | 依存先1つの障害で全体停止 |
| 負荷分離があるか | ingest、embedding、indexing、searchのリソース干渉を抑える | バッチ投入でオンライン検索が詰まる |

## 7. セキュリティ

| 確認項目 | OK条件 | レビューで見るリスク |
|---|---|---|
| embeddingを派生データとして保護しているか | アクセス制御・暗号化・削除対象に含める | ベクトルだから安全と誤認する |
| query logにPIIが残らないか | マスキング、保持期間、アクセス制限がある | 検索ログから機微情報が漏れる |
| prompt/contextログの扱いが明確か | 保存可否、暗号化、閲覧権限、保持期間を定義 | LLM入力ログに権限文書が残る |
| 外部LLM利用時のデータ境界が明確か | 送信データ、リージョン、保持設定、契約条件を確認 | 社外送信してはいけない文書を送る |
| prompt injection対策があるか | 文書内命令をユーザー命令と区別し、ツール実行や権限昇格を禁止 | 検索文書が生成方針を乗っ取る |
| 監査・削除要求に対応できるか | 文書、chunk、embedding、cache、log、backupの範囲を定義 | 一部に個人データが残る |

## 8. コスト

| 確認項目 | OK条件 | レビューで見るリスク |
|---|---|---|
| 生ベクトルサイズを概算したか | 件数 x 次元数 x bytesで見積もる | インデックスやレプリカ以前にメモリ不足 |
| インデックス・メタデータ込みで見たか | HNSW graph、payload index、全文index、削除マーカーを含む | 生ベクトルだけで安く見積もる |
| レプリカ数を含めたか | 可用性、読み取り性能、バックアップ分を含む | 本番構成にした瞬間に費用が倍増する |
| embedding生成コストを含めたか | 初回投入、再埋め込み、失敗リトライを含む | モデル更新のたびに予算超過する |
| rerankとLLM生成コストを含めたか | 候補数、context token、回答tokenを見積もる | 検索は安いがRAG全体が高い |
| p99改善の余剰キャパシティを含めたか | 平均負荷ではなくピークと再構築時を含む | 平常時は安いがピークでSLO未達 |
| コスト削減策の品質影響を測ったか | 量子化、次元削減、低k、cacheの品質低下を評価 | 安くした結果、RAGが使えなくなる |

簡易見積もりの出発点です。

```text
生ベクトルサイズ = chunk件数 x 次元数 x 4 bytes
総メモリ目安 = 生ベクトル + ANN index + メタデータindex + page cache + 余裕
総コスト目安 = 検索DB + レプリカ + embedding生成 + rerank + LLM生成 + 監視 + バックアップ + 再構築余力
```

## レビュー判定

| 判定 | 条件 |
|---|---|
| Go | 主要要件、評価、削除・権限、運用、コストが説明でき、未確定リスクに対応計画がある |
| Conditional Go | PoCや限定公開なら進められるが、特定論点の測定や設計修正が必要 |
| Hold | 権限、削除、評価、運用、コストのいずれかに重大な未検証がある |

Holdにすべき典型例です。

- 権限フィルタが検索後だけで、候補不足時のfallbackが未設計
- 削除済み文書が検索結果から消えたことを確認できない
- ANNのrecallを測らず、レイテンシだけでindexを選んでいる
- 評価クエリと正解根拠がなく、RAG品質を主観で判断している
- 再構築、モデル更新、rollbackの手順がない
- コスト見積もりにレプリカ、reindex、rerank、LLM tokenが入っていない
