# 05. 実用的な判断フレームワーク

この章は、設計レビューでそのまま使える判断フレームワークです。

## まず確認する前提

技術名を見る前に、次を確認します。

- 現在の件数、半年後、1年後の件数
- ベクトル次元数
- QPS、ピークQPS
- p95 / p99 レイテンシ目標
- 更新頻度
- 削除と権限変更の反映SLO
- tenant_idやACLなどのフィルタ要件
- 全文検索やBM25の必要性
- 正本DBの場所
- チームの運用能力
- コスト上限

## 条件別の第一候補

データ件数が少なく、プロトタイプなら、FAISS Flatまたはpgvectorから始めます。Flat検索はexact基準を作れるため、ANN導入前の品質評価に必要です。

既存システムがPostgreSQL中心なら、まずPostgreSQL + pgvectorを検討します。データの正本、権限、メタデータ、業務トランザクションがPostgresにある場合、検索DBを増やさない価値が大きいです。

低レイテンシが必要で、データがメモリに乗るなら、HNSW系を検討します。pgvector HNSW、Qdrant、Weaviate、Milvus、Elasticsearch/OpenSearchなどで、実データのrecallとp99を測ります。

更新頻度が高いなら、更新・削除・再構築の運用機能を重視します。FAISS単体で本番化する場合は周辺実装が重くなります。専用DBやPostgres、検索エンジンの運用機能を利用する方が安全です。

メタデータフィルタが重要なら、pgvector + Postgres index、Qdrant payload index、Elasticsearch/OpenSearchのfilter、Weaviateのスキーマ設計を比較します。検索後フィルタだけの構成は危険です。

全文検索が重要なら、Elasticsearch / OpenSearchを強く検討します。RAGでは固有名詞、型番、エラーコード、日付、正確な語句が重要なことが多く、ベクトル検索だけでは品質が安定しません。

画像検索や推薦で数千万から億件を見据えるなら、Milvus、Qdrant、Weaviate、Elasticsearch/OpenSearchの量子化や大規模index、またはFAISSベースの専用構成を検討します。メモリ、I/O、GPU、rerankの設計が必要です。

1人開発や少人数チームなら、運用コンポーネントを増やさないことを重視します。PostgreSQL + pgvector、マネージドDB、または単純なQdrant構成から始めるのが現実的です。

エンタープライズなら、可用性、監査、権限、削除、バックアップ、リージョン、SLA、運用分掌を重視します。検索基盤をアプリDBから分離する判断も現実的になります。

## 選定表

| 条件 | 第一候補 | 理由 |
|---|---|---|
| PoC・小規模実験 | FAISS / pgvector | 単純でexact基準を作れる |
| 既存Postgres中心 | PostgreSQL + pgvector | 正本データ・権限・JOINと近い |
| 全文検索が重要 | Elasticsearch / OpenSearch | BM25、フィルタ、集計、ハイブリッドに強い |
| RAG専用DBを分離 | Qdrant / Weaviate | ベクトル検索とメタデータ検索を扱いやすい |
| 大規模ベクトル検索 | Milvus | 大量データ・分散・多様なindex向き |
| 極低レイテンシ | Redis / FAISS組み込み | ネットワーク・メモリ設計次第で速い |
| 特殊要件・競争優位 | 自作検討 | 専門チームと明確な理由が必要 |

## 典型的な判断

### 最初は pgvector でよいケース

既存Postgresがあり、データ量が小中規模で、RAGがプロダクトの補助機能であり、権限やメタデータがRDBにあるなら、pgvectorで始めるのが妥当です。

この場合、将来の移行に備えて、embedding生成、chunk管理、検索API、評価基盤をDB実装から少し分離しておきます。

### FAISSで十分なケース

静的データ、研究、評価、オフラインバッチ、個人用ローカル検索、デモではFAISSで十分です。Flatでexact基準を作り、必要ならHNSW/IVF/PQを試します。

本番APIにする場合は、永続化、メタデータ、権限、更新、削除、監視をどこで持つかを明確にします。

### 専用ベクトルDBを使うべきケース

検索負荷をアプリDBから分けたい、フィルタ付きANNが重要、ベクトル件数が増えてPostgres運用が重くなった、検索APIを独立サービスとして育てたい場合は、Qdrant、Weaviate、Milvusを検討します。

### Elasticsearch / OpenSearch と組み合わせるべきケース

キーワード検索、BM25、正確な語句、ログ、フィルタ、集計、ランキングが重要なら、検索エンジンを使います。ベクトル検索はその中の一要素です。

### 自作すべきではないケース

一般的なRAG、小中規模検索、社内文書検索、FAQ検索では、自作はほぼ過剰です。既存製品が解いている運用問題を再実装することになります。

### 自作を検討してよいケース

検索そのものが競争優位で、既存製品では満たせない要件があり、専門チームと運用予算がある場合です。その場合でも、まずFAISSや既存エンジンで基準線を作り、自作する範囲を最小化します。

## 設計レビューで聞くべき質問

- exact baselineを測ったか
- recall@kとp99を同時に見たか
- フィルタあり検索を測ったか
- 削除と権限変更がいつ検索に反映されるか
- インデックス再構築中に検索を継続できるか
- embedding model変更時の移行手順はあるか
- 検索結果が悪化したときに検知できるか
- コストは次元数、レプリカ数、再構築を含んでいるか
