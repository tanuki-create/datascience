# 09. ベンチマーク用テンプレート

この章は、RAG、ベクトルDB、検索基盤を比較するときのレビュー素材です。

目的は、速い・賢い・使いやすいという印象論ではなく、同じ条件、同じ評価クエリ、同じ合格基準で比較できる状態を作ることです。

## ベンチマークで決めるべきこと

まず、何を選びたいのかを明確にします。

- RAGの検索品質を改善したいのか
- ベクトルDBや検索エンジンを選定したいのか
- index方式やパラメータを選びたいのか
- chunking、embedding model、rerankerを比較したいのか
- 本番移行前にSLOを満たすか確認したいのか
- コスト上限内で成立する構成を探したいのか

同じ「検索ベンチマーク」でも、目的が違うと測るべき指標は変わります。DB選定の比較で回答品質だけを見るのは不足です。RAG改善の比較でp99だけを見るのも不足です。

## 測るべき指標

### 検索品質

検索品質は、正解文書または正解チャンクが上位に出るかで測ります。

| 指標 | 見ること | 注意点 |
|---|---|---|
| recall@k | 正解がtop-k内に含まれるか | ANN比較ではexact baselineとの差を見る |
| precision@k | top-kのうち有用な結果の割合 | 複数正解があるクエリで有効 |
| MRR | 最初の正解が何位に出るか | FAQや単一正解に向く |
| nDCG@k | 順位と関連度の両方 | 関連度ラベルを複数段階で作れる場合に有効 |
| hit rate | 少なくとも1件有用な結果があるか | 粗いがRAGの初期評価に使いやすい |
| zero-result rate | 有用な候補が出ない割合 | フィルタや権限条件の影響が出やすい |

RAGでは、検索品質と回答品質を分けて測ります。回答が悪い原因が、検索で文脈を取れていないのか、LLMが文脈を使えていないのかを分離するためです。

### 回答品質

RAGシステム全体を見る場合は、検索結果を使った回答も評価します。

| 指標 | 見ること | 注意点 |
|---|---|---|
| groundedness | 回答が検索文脈に基づいているか | 文脈外の推測を検出する |
| answer correctness | 業務上正しい回答か | 人手評価または強い評価基準が必要 |
| citation accuracy | 引用元が回答内容を支えているか | 取得しただけの文書を引用していないか見る |
| refusal accuracy | 答えられない時に拒否できるか | 検索結果が弱い時の挙動を見る |
| context utilization | 取得した文脈を使えているか | rerankerやcontext constructionの比較に有効 |

回答品質はLLM、プロンプト、検索、rerank、context lengthの影響が混ざります。DBやindex方式の比較では、回答生成を固定し、検索部分だけ差し替えます。

### 性能

性能は平均ではなくtail latencyを重視します。

| 指標 | 見ること | 注意点 |
|---|---|---|
| p50 latency | 通常時の体感速度 | 単独では採用判断に使わない |
| p95 latency | 多くのユーザーが見る遅さ | SLO候補として使いやすい |
| p99 latency | 最悪寄りの遅さ | 分散検索、I/O、GC、再構築の影響が出る |
| throughput / QPS | 処理できる検索数 | 同時実行数とセットで見る |
| indexing throughput | 登録・更新速度 | 初期投入と日次更新の両方を見る |
| indexing lag | 更新が検索可能になるまでの遅延 | RAGでは鮮度SLOになる |
| timeout rate | 制限時間内に返せない割合 | p99より実害に近い場合がある |

RAGでは、検索レイテンシ、rerankレイテンシ、LLMレイテンシを分けて記録します。全体時間だけを見ると、検索基盤の改善余地が隠れます。

### 運用性

本番採用の比較では、検索APIの速さだけでは不十分です。

| 指標 | 見ること | 注意点 |
|---|---|---|
| index build time | 初期構築・再構築にかかる時間 | モデル変更時の移行時間に直結する |
| memory usage | ベクトル、index、metadata、cacheの使用量 | 生ベクトルだけで見積もらない |
| storage usage | 永続化データとバックアップ容量 | レプリカとshadow indexも含める |
| delete propagation | 削除が検索結果から消えるまでの時間 | セキュリティ要件では必須 |
| ACL propagation | 権限変更が反映されるまでの時間 | 検索後フィルタでは事故になりやすい |
| reindex impact | 再構築中の検索劣化 | p99とエラー率を見る |
| recovery time | 障害後に復旧する時間 | バックアップ復元も含める |

### コスト

コストは単純な月額ではなく、要件を満たすために必要な構成で比較します。

| 指標 | 見ること | 注意点 |
|---|---|---|
| steady-state cost | 通常運用の月額 | CPU、メモリ、ストレージ、レプリカを含める |
| peak capacity cost | ピークQPSに耐える費用 | 平均負荷だけで見ない |
| rebuild cost | 再構築時の一時費用 | shadow indexや二重書き込みを含める |
| embedding cost | embedding生成・再生成費用 | モデル変更時に大きくなる |
| rerank cost | rerankerの推論費用 | 候補数に比例しやすい |
| ops cost | 運用・監視・障害対応の負荷 | 少人数チームでは重要 |

## 実験条件テンプレート

ベンチマーク結果には、必ず実験条件を添えます。条件が欠けた数値は比較できません。

| 項目 | 記入例 | レビュー観点 |
|---|---|---|
| 目的 | RAG用検索DBの本番候補を比較 | 何を採用判断するのか明確か |
| データ種別 | 社内Markdown、PDF、FAQ、チケット | 実データに近いか |
| 文書数 | 10万文書 | 将来量も別途見る |
| チャンク数 | 120万チャンク | 実際の検索単位で書く |
| ベクトル次元数 | 768 / 1536 / 3072 | メモリと速度に直結する |
| embedding model | model名、version、正規化有無 | 本番と一致しているか |
| 距離関数 | cosine / dot product / L2 | モデルの想定と一致しているか |
| chunking | 800 tokens、overlap 120 | 比較間で固定するか、比較対象にする |
| metadata | tenant_id、ACL、created_at、doc_type | フィルタ条件を再現できているか |
| 検索方式 | BM25、vector、hybrid、rerankあり | どこまでをDB比較に含めるか |
| top-k | 10 / 20 / 50 | RAG投入候補数と一致しているか |
| フィルタ条件 | tenant、ACL、期間、文書種別 | 本番で必須の条件を含むか |
| 評価クエリ数 | 200 queries | クエリ分布が偏っていないか |
| 正解ラベル | 正解chunk、関連度0-3 | 誰がどう作ったか明確か |
| 負荷条件 | 20 / 100 / 500 concurrent users | ピーク想定を含むか |
| 更新条件 | 毎時1万chunk更新、削除あり | 静的データだけで見ていないか |
| ハードウェア | vCPU、RAM、disk、network | 結果の再現に必要 |
| レプリカ・シャード | shard数、replica数 | 可用性要件込みの構成か |
| キャッシュ | 有無、warm/cold | warm cacheだけで判断していないか |
| タイムアウト | 300ms / 1s / 3s | timeout rateを比較できるか |

## クエリセット設計

評価クエリは、成功しやすい質問だけで作ってはいけません。本番で起きる検索の難しさを含めます。

| クエリ種別 | 例 | 見たい失敗 |
|---|---|---|
| 直接一致 | 製品AのSLAは何か | 正解文書が上位に来るか |
| 言い換え | 障害時の復旧目標を知りたい | semantic searchが効くか |
| 固有名詞 | エラーコードE1234の原因 | BM25やhybridが必要か |
| 数値・日付 | 2025年4月以降の料金 | embeddingだけで落ちないか |
| 複数条件 | tenant Aの管理者向け設定 | filterとrankingが両立するか |
| 権限付き | 自分が読める契約だけ | ACL漏れがないか |
| 古い情報 | 廃止済み手順について | freshnessやversion管理が効くか |
| 答えなし | 存在しない仕様を聞く | 不正確な回答をしないか |
| 類似文書多数 | 似たFAQが複数ある | rerankが効くか |
| 長文文脈 | 手順全体を要約したい | chunkingで文脈が切れないか |

最低限、クエリごとに次を持ちます。

| 項目 | 内容 |
|---|---|
| query_id | 評価クエリのID |
| query | ユーザー入力 |
| query_type | 直接一致、言い換え、固有名詞など |
| expected_doc_ids | 正解文書ID |
| expected_chunk_ids | 正解チャンクID |
| relevance_label | 0から3などの関連度 |
| required_filters | tenant、ACL、日付など |
| expected_answer | RAG評価をする場合の期待回答 |
| must_cite | 必須引用元 |
| notes | 判断が難しい点 |

## 落とし穴

### 小さすぎるデータで判断する

1万件で速い構成が、1000万件で速いとは限りません。件数、次元数、metadata量、シャード数が増えると、メモリ、I/O、再構築時間、p99が変わります。

### 正解ラベルが弱い

評価クエリに対して正解文書が1つだけだと、別の有用な文書を誤って不正解にすることがあります。可能なら、正解、部分正解、関連なしの複数段階でラベルを作ります。

### exact baselineがない

ANN index同士だけを比較すると、近似による取りこぼしが見えません。小さめの代表データではFlat検索や全件探索を基準にして、recall低下と速度改善をセットで見ます。

### warm cacheだけで測る

本番では再起動直後、デプロイ直後、シャード移動後、日次バッチ後にcold寄りの挙動が出ます。warmとcoldを分けて測ります。

### フィルタなしで測る

RAG本番ではtenant、ACL、期間、文書種別などのフィルタが入ります。フィルタなしのANN性能は参考値でしかありません。

### 平均レイテンシだけを見る

平均が良くてもp99が悪いと、ユーザー体験やタイムアウト率は悪化します。分散検索では一部シャードの遅延が全体を遅くします。

### 更新・削除を測らない

静的データの検索だけでは、本番運用を評価できません。更新中の検索品質、indexing lag、削除反映、論理削除の蓄積、reindexの影響を測ります。

### 回答品質でDBを評価してしまう

RAG回答はLLM、プロンプト、reranker、context constructionの影響を受けます。DB比較では、検索結果の品質と速度を個別に測り、回答生成は固定します。

### コストを通常時だけで見る

本番ではレプリカ、バックアップ、監視、ピーク余力、shadow index、reindex時の一時容量が必要です。通常時の最小構成だけで採用判断しないようにします。

### 候補ごとにチューニング量が違う

片方だけ丁寧にindexパラメータを調整すると、公平な比較になりません。各候補に同じ時間予算または同じ改善手順を与えます。

## 合格基準の書き方

合格基準は、採用前に数値で書きます。測った後に都合よく変えると、ベンチマークではなく説明資料になります。

### 良い書き方

```text
検索品質:
- 評価クエリ200件で recall@10 >= 0.90
- 重要クエリ50件で recall@10 >= 0.96
- zero-result rate <= 2%

性能:
- top-k=20、ACLフィルタあり、100 concurrent usersで p95 <= 250ms
- 同条件で p99 <= 800ms
- timeout rate <= 0.1%

鮮度・削除:
- 通常更新は5分以内に検索結果へ反映
- 権限変更と削除は60秒以内に検索結果から除外

運用:
- embedding model変更時にshadow indexを構築し、30分以内に切り替え可能
- reindex中も検索APIのp95劣化が2倍以内

コスト:
- 本番想定QPSとレプリカ込みで月額上限内
- reindex時の一時コストが通常月額の1.5倍以内
```

### 悪い書き方

```text
- 速いこと
- 精度が高いこと
- だいたい本番で使えること
- 運用しやすいこと
- コストが安いこと
```

悪い基準は、レビューで判断が割れます。良い基準は、条件、指標、しきい値、例外が明確です。

## レビューで確認する質問

- 何を採用判断するためのベンチマークか
- 本番データに近い文書、chunk、metadata、権限条件を使っているか
- 評価クエリは直接一致、言い換え、固有名詞、答えなし、権限付き検索を含むか
- exact baselineとの差を見たか
- recall、p95、p99、コストを同じ構成で測ったか
- フィルタあり検索とフィルタなし検索を分けたか
- 更新中、削除後、reindex中の挙動を測ったか
- RAG回答品質と検索品質を分離して評価したか
- 候補ごとのチューニング条件は公平か
- 合格基準は測定前に決められているか

## 最小ベンチマーク手順

小さく始める場合でも、次の順序にします。

1. 本番に近い文書とmetadataを用意する
2. chunking、embedding model、距離関数を固定する
3. 評価クエリと正解ラベルを作る
4. Flatまたはexact検索で品質基準を作る
5. 候補DB、index、パラメータを同じ条件で測る
6. recall、p95、p99、timeout、コストを表にする
7. フィルタ、ACL、更新、削除、reindexを追加で測る
8. 合格基準に対して採用、保留、不採用を判断する

最初の比較は完璧でなくてよいですが、測定条件と失敗パターンを残します。後からデータ量、クエリ、候補構成を増やしても、同じ形式で比較できることが重要です。
