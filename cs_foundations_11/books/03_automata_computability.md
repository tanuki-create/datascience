# オートマトン・形式言語・計算可能性

## はじめに

この本の目的は、正規表現やパーサの使い方を増やすことではない。要求を「どの計算モデルなら表現できるか」「そもそも決定できるか」「決定できても資源内に終わるか」に分類する力を得ることである。記号列を \(w\)、空文字を \(\varepsilon\)、文字列集合を言語 \(L\) と書く。実装例は Python 風だが、議論は言語処理系に依存しない。

---

## 第1章　計算とは何か

### この章を学ぶ理由／現場の問題

「入力を読んで出力する」を分解できないと、状態遷移、再試行、プロトコル検証を場当たり的な `if` の集合として実装してしまう。計算は、**状態**と読んだ**記号**に応じて**規則**を適用する過程として捉えられる。

### 中心概念と正式な定義

構成（configuration）を機械の有限な制御状態、未処理入力、必要なら作業記憶の組とする。遷移関係 \(\vdash\) が \(C_i\vdash C_{i+1}\) を定め、初期構成から停止構成までの列が計算である。決定器はすべての入力で停止し yes/no を返し、認識器は非所属入力で停止しないことがある。ここが API の「結果なし」と「処理中」の違いに対応する。

### 直感 → 図解 → 数式 → 例 → 実装

自動販売機なら「投入額」が状態、「硬貨」が記号、「加算」が規則である。

```text
(0円) --100--> (100円) --50--> (150円/販売可能)
```

決定的な一歩を \(\delta:S\times\Sigma\to S\) と書く。入力 `100,50` への拡張遷移は \(\delta^*(0,[100,50])=150\)。

```python
def run(initial, symbols, transition):
    state = initial
    for symbol in symbols:
        state = transition(state, symbol)
    return state
```

このループは有限状態機械にも、状態にスタックやテープを含めた強いモデルにも共通する骨格である。

### よくある誤解／実務接続

- 「計算＝数値演算」ではない。構文解析、型検査、ルーティングも記号変換である。
- 状態を変数として持たないコードにも、PC、呼出しスタック、DB 行として状態は存在する。
- 停止しないことと遅いことは別問題である。
- ワークフロー、通信プロトコル、UI 状態機械は、規則を明示すると到達不能状態を検査できる。

### 要点

1. 計算は構成間の遷移列である。
2. 状態は過去について保持された情報である。
3. 記号は機械が区別する入力単位である。
4. 規則は次構成を定める。
5. 決定器には全入力での停止が必要である。

### 誤解チェック（5問）

1. 出力しない無限ループは計算ではないか。 2. DB は機械状態になり得るか。 3. 同じ状態と記号から複数の次状態があるモデルは無意味か。 4. 認識と決定は同じか。 5. 実行時間が長いことは停止不能の証拠か。

### 基礎問題（5問）

1. ログイン処理の状態・記号・規則を列挙せよ。 2. 信号機を遷移表にせよ。 3. `run` のループ不変条件を書け。 4. 決定器と認識器の例を一つずつ挙げよ。 5. 不正な遷移を含む注文フローを作り修正せよ。

### 応用問題（3問）／設計問題／調査課題

1. 再試行を含むジョブの構成を定義せよ。 2. 非決定的規則を集合値関数で表せ。 3. 「タイムアウト」を停止と同一視できない理由を説明せよ。 **設計:** 決済ワークフローの状態と不変条件を設計せよ。 **調査:** 利用中の一つのプロトコル仕様から状態機械の記述を探せ。

### 知らないとする誤判断／次章への接続

状態を明示せず「例外時だけフラグを足せばよい」と判断し、到達不能・復旧不能状態を増やす。次章では有限個の状態だけを持つ最小モデルを形式化する。

## 第2章　有限状態機械：DFA と NFA

### この章を学ぶ理由／現場の問題

トークナイザ、入力検証、接続ライフサイクルでは、過去すべてでなく有限種類の要約だけが必要である。DFA/NFA はその境界を与える。

### 中心概念と正式な定義

DFA は五つ組 \(M=(Q,\Sigma,\delta,q_0,F)\)。\(Q\) は有限状態集合、\(\Sigma\) は有限アルファベット、\(\delta:Q\times\Sigma\to Q\)、\(q_0\) は初期状態、\(F\subseteq Q\) は受理状態である。\(\delta^*(q,\varepsilon)=q\)、\(\delta^*(q,wa)=\delta(\delta^*(q,w),a)\)、\(L(M)=\{w\mid\delta^*(q_0,w)\in F\}\)。NFA は \(\delta:Q\times(\Sigma\cup\{\varepsilon\})\to\mathcal P(Q)\) で、少なくとも一つの経路が受理すればよい。

### 直感 → 図解 → 数式 → 例 → 実装

偶数個の `1` を含むビット列は、偶奇だけ覚えればよい。

```text
        1          1
   -->[even]* <--------> [odd]
       ^  |0             ^ |0
       +--+               +-+
```

`even` が受理状態。NFA は「候補を同時に追跡する」記法であり、部分集合構成 \(Q_D=\mathcal P(Q_N)\) により DFA に変換できる。

```python
def accepts(bits):
    state = 0
    for b in bits:
        if b == "1": state ^= 1
    return state == 0
```

### よくある誤解／実務接続

- NFA が物理的に未来を予知するわけではない。複数候補を集合として実行できる。
- DFA と NFA の表現能力は同じだが、状態数は指数的に違い得る。
- 有限状態とは入力長が有限という意味ではなく、記憶の種類が有限という意味である。
- TCP、認証、字句解析では、状態遷移表が仕様とテストの共通語になる。

### 要点

1. DFA の次状態は一意。 2. NFA は状態集合へ遷移する。 3. 受理は入力を読み切った後に判定する。 4. DFA/NFA は同じ言語族を認識する。 5. 部分集合構成は NFA の並行候補を一状態に符号化する。

### 誤解チェック（5問）

1. NFA は DFA より多くの言語を認識するか。 2. 受理状態に一度入れば必ず受理か。 3. \(\varepsilon\) 遷移は入力を消費するか。 4. 状態名に意味は必須か。 5. DFA は無限長入力を記憶するか。

### 基礎問題（5問）

1. `01` で終わる DFA を作れ。 2. `a` の個数が 3 の倍数の DFA を作れ。 3. 遷移表から受理列を列挙せよ。 4. 3状態 NFA を部分集合構成せよ。 5. 到達不能状態を除去せよ。

### 応用問題（3問）／設計問題／調査課題

1. 二つの DFA の積で積集合を作れ。 2. DFA の受理状態を反転すると補集合になる条件を述べよ。 3. 最小化前後の同値性をテストせよ。 **設計:** WebSocket 接続ライフサイクルを DFA として設計せよ。 **調査:** Ragel、re2c 等の状態機械生成器の用途を調べよ。

### 知らないとする誤判断／次章への接続

有限の状態で十分な問題に履歴配列や複雑な分岐を導入し、検証可能性を失う。次章では有限オートマトンで認識できる言語を特徴づける。

## 第3章　正規言語

### この章を学ぶ理由／現場の問題

入力検証に「regex が書けるか」ではなく、有限記憶で判定できる構造かを見抜く必要がある。正規言語はストリーミングで一定メモリ判定できる範囲の基礎である。

### 中心概念と正式な定義

言語 \(L\subseteq\Sigma^*\) が正規であるとは、ある DFA が \(L\) を認識すること。同値に NFA または理論的正規表現で記述できる（Kleene の定理）。正規言語は和、積、補、差、連接、Kleene star、逆像などで閉じる。Pumping lemma: 正規な \(L\) には長さ \(p\) があり、\(|w|\ge p\) の各 \(w\in L\) は \(w=xyz\)、\(|xy|\le p, |y|>0\)、すべての \(i\ge0\) で \(xy^iz\in L\) と分解できる。

### 直感 → 図解 → 数式 → 例 → 実装

有限状態は長い接頭辞を有限個の「将来に対して区別できるクラス」へ潰す。

```text
prefixes --future behavior--> finitely many equivalence classes
```

Myhill--Nerode 関係 \(x\equiv_L y\iff\forall z[xz\in L\Leftrightarrow yz\in L]\)。同値類が有限個 iff \(L\) は正規。\(\{a^nb^n\}\) は必要な `a` 個数を無限に区別するため非正規。

```python
def regular_log_level(line):
    # 任意長の行でも現在の字句状態だけを保持
    return dfa_accepts(line)
```

### よくある誤解／実務接続

- Pumping lemma は非正規性の必要条件を使う道具で、正規性の証明にはならない。
- 「有限文字列の集合」は常に正規だが、「各文字列が有限」な無限集合は自動的に正規ではない。
- 正規言語の交差閉包は、独立な入力制約を DFA の積で合成できることを意味する。
- ログフィルタ、字句規則、単純なプロトコル監視は正規モデルと相性がよい。

### 要点

1. 正規性は構文の見た目でなく有限状態で決まる。 2. 閉包性は設計の合成則である。 3. Pumping lemma は反証に使う。 4. Myhill--Nerode は必要な状態の意味を与える。 5. 等数対応は一般に有限状態では保持できない。

### 誤解チェック（5問）

1. 無限言語は非正規か。 2. 有限言語は正規か。 3. 正規言語の交差は正規か。 4. Pumping lemma を満たせば正規か。 5. JSON 全体は正規か。

### 基礎問題（5問）

1. `ab*` の言語を列挙せよ。 2. 偶数長言語の DFA を作れ。 3. 正規言語二つの差を構成せよ。 4. 有限言語が正規と示せ。 5. \(a^nb^n\) を pumping lemma で反証せよ。

### 応用問題（3問）／設計問題／調査課題

1. Myhill--Nerode で最小状態数を下界づけよ。 2. 準同型像の閉包を実装例で説明せよ。 3. ストリーミング検査と正規性の関係を論ぜよ。 **設計:** ログ行フォーマットを正規部分と非正規部分に分割せよ。 **調査:** RE2 が保証する計算量を調べよ。

### 知らないとする誤判断／次章への接続

入れ子や対応数まで正規表現に押し込み、保守不能か最悪時爆発を招く。次章では正規表現の代数と実装 regex の差を明確にする。

## 第4章　正規表現の理論と regex エンジン

### この章を学ぶ理由／現場の問題

同じ「正規表現」という名でも、理論式、バックトラッキング VM、DFA 系エンジンは能力と最悪計算量が異なる。入力境界で ReDoS を避けるには区別が必要である。

### 中心概念と正式な定義

理論的正規表現は \(\emptyset,\varepsilon,a\in\Sigma\) を基底とし、和 \(R|S\)、連接 \(RS\)、反復 \(R^*\) で帰納的に作る。意味は \(L(R|S)=L(R)\cup L(S)\)、\(L(RS)=L(R)L(S)\)、\(L(R^*)=\bigcup_{i\ge0}L(R)^i\)。後方参照 `\1` は同じ部分文字列を要求し、一般には正規言語を越える。lookaround や atomic group はエンジン固有である。

### 直感 → 図解 → 数式 → 例 → 実装

```text
regex syntax --compile--> NFA/DFA  : paths are shared
regex syntax --run VM--> backtrack : alternatives may be revisited
```

`(a|aa)*b` を素朴にバックトラックし `a...a` に適用すると、分割候補が指数的に増え得る。一方 Thompson NFA シミュレーションは各文字で状態集合を更新し、おおむね \(O(|R||w|)\)。

```python
def fullmatch_ascii_id(s):
    return bool(s) and (s[0].isalpha() or s[0] == "_") \
        and all(c.isalnum() or c == "_" for c in s[1:])
```

### よくある誤解／実務接続

- `^`/`$` と full match、Unicode の改行規則を混同しない。
- 「短いパターン」は安全性を意味しない。曖昧な反復が危険である。
- 後方参照を含む regex を DFA として説明してはいけない。
- 信頼できない長文には線形時間保証のエンジン、長さ制限、タイムアウトを境界防御として選ぶ。

### 要点

1. 理論正規表現は三演算で定義できる。 2. Kleene の定理で有限オートマトンと同値。 3. 実装 regex は拡張により非正規になり得る。 4. バックトラッキングは最悪指数時間になり得る。 5. エンジン選択はセキュリティ判断である。

### 誤解チェック（5問）

1. すべての regex 機能は正規か。 2. DFA 系は後方参照を自然に扱えるか。 3. `.*` は常に危険か。 4. match と search は同じか。 5. タイムアウトだけで根本的 ReDoS は解決するか。

### 基礎問題（5問）

1. `(ab|c)*` の NFA を描け。 2. `a+` を基本演算へ展開せよ。 3. アンカーなし検索の意味を説明せよ。 4. 曖昧な反復を一つ修正せよ。 5. 後方参照が比較する情報を述べよ。

### 応用問題（3問）／設計問題／調査課題

1. Thompson 構成を疑似コード化せよ。 2. 悪意ある入力で二種類のエンジンを比較せよ。 3. Unicode 正規化と regex の責務を分けよ。 **設計:** 公開 API の入力検証方針を作れ。 **調査:** 利用言語のエンジンがバックトラッキング型か確認せよ。

### 知らないとする誤判断／次章への接続

「regex で書けたから正規、したがって線形」と誤認する。次章では入れ子を有限に表現する文脈自由文法へ進む。

## 第5章　文脈自由文法

### この章を学ぶ理由／現場の問題

括弧、式、ブロックなど再帰的入れ子を、手続きの分岐でなく宣言的な生成規則として扱う。文法が曖昧なら、同じ入力が異なる AST を持ち障害になる。

### 中心概念と正式な定義

CFG は \(G=(V,\Sigma,R,S)\)。非終端記号 \(V\)、終端記号 \(\Sigma\)、生成規則 \(R\subseteq V\times(V\cup\Sigma)^*\)、開始記号 \(S\)。\(S\Rightarrow^*w\) なら \(w\in L(G)\)。同じ文字列に異なる構文木が二つあれば文法は曖昧。曖昧性は言語でなく文法の性質だが、本質的曖昧な CFL もある。

### 直感 → 図解 → 数式 → 例 → 実装

式文法 `E → E + T | T`, `T → T * F | F`, `F → n | (E)` は優先順位を木構造にする。

```text
      E
    / | \
   E  +  T
   n    /|\
       T * F
       n   n
```

```python
def parse_factor(tokens):
    if peek() == "n": return Number(take())
    expect("("); node = parse_expr(tokens); expect(")"); return node
```

左再帰は素朴な再帰下降で無限再帰するため、`E → T E'`, `E' → + T E' | ε` のように変形する。

### よくある誤解／実務接続

- CFG は任意の意味制約（宣言済み変数、型整合）までは扱わない。
- 構文木と AST は同じではない。AST は句読記号等を落とす。
- 文法の曖昧性とパーサ実装の不具合を分ける。
- 設定言語、SQL、テンプレート、プロトコルの構文仕様に接続する。

### 要点

1. CFG は再帰的構造を生成する。 2. 生成と認識は同じ言語の二つの見方。 3. 構文木は導出の階層を表す。 4. 曖昧性は複数解釈を生む。 5. 優先順位・結合性は文法へ明示する。

### 誤解チェック（5問）

1. CFG は正規言語を表せるか。 2. CFG なら意味検査も完了するか。 3. 左端導出と右端導出が違えば必ず曖昧か。 4. 左再帰は CFG 自体を無効にするか。 5. AST は全トークンを保存すべきか。

### 基礎問題（5問）

1. balanced parentheses の CFG を書け。 2. `n+n*n` の構文木を描け。 3. 曖昧な式文法を示せ。 4. 左再帰を除去せよ。 5. nullable 非終端を求めよ。

### 応用問題（3問）／設計問題／調査課題

1. dangling else を説明せよ。 2. FIRST/FOLLOW 集合を計算せよ。 3. 文法と意味制約を分離せよ。 **設計:** 小さなフィルタ DSL の CFG と AST を設計せよ。 **調査:** 使用中の言語の公式文法表記を確認せよ。

### 知らないとする誤判断／次章への接続

入れ子構造を文字列置換で処理し、例外ケースを無限に追加する。次章では CFG を認識するために必要なスタック機械を見る。

## 第6章　プッシュダウン・オートマトン

### この章を学ぶ理由／現場の問題

括弧対応には「深さ」を保持する未上限の記憶が必要で、有限状態だけでは足りない。PDA は有限制御に LIFO スタックを一つ加えたモデルである。

### 中心概念と正式な定義

PDA は \((Q,\Sigma,\Gamma,\delta,q_0,Z_0,F)\)。\(\Gamma\) はスタックアルファベット、\(Z_0\) は底記号、\(\delta:Q\times(\Sigma\cup\{\varepsilon\})\times\Gamma\to\mathcal P(Q\times\Gamma^*)\)。非決定性 PDA が認識する言語族は CFL と一致する。決定性 PDA は真部分集合のみを認識する。

### 直感 → 図解 → 数式 → 例 → 実装

`(` で push、`)` で pop、末尾で底だけなら受理する。

```text
input: (()())    stack: Z -> (Z -> ((Z -> ... -> Z
```

```python
def balanced(s):
    depth = 0
    for c in s:
        depth += 1 if c == "(" else -1
        if depth < 0: return False
    return depth == 0
```

一種類の括弧なら整数で圧縮できるが、複数種類ではスタック頂上の種別が必要である。

### よくある誤解／実務接続

- 「スタックがあるプログラム」は自動的に PDA ではない。任意アクセスのヒープ等はより強い。
- 一つのスタックで二つの独立カウンタを一般に比較できない。
- 再帰下降パーサの呼出しスタックは PDA 的記憶である。
- 深さ上限は実装安全性のための資源制約で、形式言語上の定義とは別。

### 要点

1. PDA は有限制御＋LIFO 記憶。 2. NPDA と CFL は等価。 3. DPDA は NPDA より弱い。 4. push/pop が入れ子を表現する。 5. 実装では深さ制限も必要。

### 誤解チェック（5問）

1. DFA に十分多い有限状態を与えれば任意深さを扱えるか。 2. DPDA=NPDA か。 3. 空スタック受理と終状態受理は能力が違うか。 4. 二スタック PDA は一スタックと同じか。 5. 再帰は必ず終了するか。

### 基礎問題（5問）

1. `a^n b^n` の PDA を記述せよ。 2. 括弧列の構成列を追え。 3. 複数括弧の検査器を書け。 4. 不正接頭辞を早期拒否せよ。 5. CFG から PDA への対応を説明せよ。

### 応用問題（3問）／設計問題／調査課題

1. `a^n b^n c^n` が一スタックで難しい理由を示せ。 2. 深さ制限が言語をどう変えるか述べよ。 3. スタックオーバーフローを形式モデルと実装境界に分けよ。 **設計:** ストリーミング XML 部分検証器を設計せよ。 **調査:** 実運用パーサのネスト上限を調べよ。

## 第7章　コンパイラとの接続：lexer・parser・AST

### この章を学ぶ理由／現場の問題

言語処理を一つの巨大 regex や文字列置換にすると、字句・構文・意味の責務が混ざる。段階ごとの契約を理解すれば DSL や設定検査も堅牢になる。

### 中心概念と正式な定義

lexer は文字列 \(\Sigma^*\) をトークン列へ写す。parser はトークン列が CFG に属するか判定し構文木を作る。AST は意味に必要な構造へ射影する。意味解析は名前解決、型、スコープ等の文脈依存条件を検査する。LL(1) は左から読み左端導出を一トークン先読みで選び、LR は右端導出の逆をボトムアップで構成する。

### 直感 → 図解 → 数式 → 例 → 実装

```text
source -> [lexer/DFA] -> tokens -> [parser/PDA] -> CST -> AST
       -> [name/type checks] -> IR -> optimize -> target
```

```python
def compile_expr(source):
    tokens = lex(source)
    ast = parse(tokens)
    typed = check(ast, env={})
    return lower(typed)
```

各段の出力型を別にし、エラー位置を source span として保つと診断可能性が上がる。

### よくある誤解／実務接続

- lexer と parser の境界は絶対ではないが、責務分離は有用。
- パース成功は安全な実行を意味しない。意味検査と権限制御が残る。
- AST の最適化は入力文字列への置換ではなく意味保存変換である。
- SQL、GraphQL、ルールエンジン、IaC も同じパイプラインで捉えられる。

### 要点

1. lexer は正規構造を扱う。 2. parser は再帰構造を扱う。 3. AST は意味上の構造。 4. 意味解析は文脈条件を扱う。 5. 段階間契約が診断とテストを改善する。

### 誤解チェック（5問）

1. lexer は必須か。 2. AST=CST か。 3. CFG だけで型検査できるか。 4. パース成功は注入攻撃耐性を保証するか。 5. IR は機械語だけか。

### 基礎問題（5問）

1. `x+12` を token 化せよ。 2. CST から AST を描け。 3. 字句エラーと構文エラーを区別せよ。 4. source span のデータ型を設計せよ。 5. 左再帰が再帰下降へ与える影響を述べよ。

### 応用問題（3問）／設計問題／調査課題

1. エラー回復同期点を提案せよ。 2. 意味保存最適化を一つ証明せよ。 3. parser combinator と生成器を比較せよ。 **設計:** 設定 DSL の全段階と中間型を設計せよ。 **調査:** 一つのコンパイラで lexer/parser 技術を確認せよ。

### 知らないとする誤判断／次章への接続

## 第8章　Chomsky 階層

### この章を学ぶ理由／現場の問題

仕様の制約を正規表現、CFG、汎用コードのどこへ置くべきか判断するには、生成規則と機械能力の階層が地図になる。

### 中心概念と正式な定義

Type 3 正規文法 ↔ 有限オートマトン、Type 2 文脈自由文法 ↔ PDA、Type 1 文脈依存文法 ↔ 線形拘束オートマトン、Type 0 句構造文法 ↔ Turing 機械。概ね \(REG\subsetneq CFL\subsetneq CSL\subsetneq RE\)。CSL の規則は原則として長さ非減少、Type 0 は \(\alpha\to\beta\)（\(\alpha\) は非終端を含む）を許す。

### 直感 → 図解 → 数式 → 例 → 実装

```text
REG [finite memory]
  ⊊ CFL [one stack]
      ⊊ CSL [linear tape]
          ⊊ RE [unbounded tape]
```

`a^n b^n` は CFL、`a^n b^n c^n` は CFL でないが CSL。実装では強いモデルを常に使えるが、弱いモデルで表せるほど解析・性能保証が容易になる。

```python
validators = [lexical_dfa, syntax_parser, semantic_checker]
```

### よくある誤解／実務接続

- 階層が上ほど実務上優秀という意味ではない。
- 自然言語や実在 PL が一つの階層だけで完全に説明されるとは限らない。
- 実装言語が Turing 完全でも各検査器を弱いモデルに限定できる。
- 入力層の責務分割、静的解析ルール、DSL 能力制限に接続する。

### 要点

1. 文法制約と認識機械が対応する。 2. 包含は真。 3. 記憶能力が表現力を増す。 4. 表現力と解析容易性には緊張がある。 5. 最弱で十分なモデルを選ぶ。

### 誤解チェック（5問）

1. CFL は正規言語を含むか。 2. Type 0 は常に停止するか。 3. Turing 完全な検証器なら安全か。 4. 正規文法は左線形と右線形を無条件に混ぜてよいか。 5. 高い型番号ほど強いか。

### 応用問題（3問）／設計問題／調査課題

### 知らないとする誤判断／次章への接続

## 第9章　Turing 機械

### この章を学ぶ理由／現場の問題

実機の細部を捨てて「アルゴリズムで計算できる」の境界を議論する共通モデルが必要である。Turing 機械は性能モデルではなく計算可能性モデルである。

### 中心概念と正式な定義

一テープ決定性 TM を \(M=(Q,\Sigma,\Gamma,\delta,q_0,q_{acc},q_{rej})\) とする。空白 \(\sqcup\in\Gamma\)、\(\Sigma\subseteq\Gamma\setminus\{\sqcup\}\)、\(\delta:(Q\setminus\{q_{acc},q_{rej}\})\times\Gamma\to Q\times\Gamma\times\{L,R\}\)。テープ内容、ヘッド位置、状態が構成。受理言語は受理状態へ到達する入力集合である。

### 直感 → 図解 → 数式 → 例 → 実装

```text
... □ 1 0 1 □ ...
        ^ head, state=q
read 0 -> write 1, move R, state=q'
```

複数テープ、非決定性、stay move は計算可能な言語族を変えない。万能 TM は機械記述 \(\langle M,w\rangle\) を読み M を模倣する。

```python
while state not in {ACCEPT, REJECT}:
    state, tape[head], move = delta[state, tape[head]]
    head += -1 if move == "L" else 1
```

### よくある誤解／実務接続

- 無限テープは事前に無限セルへ書く装置ではなく必要分だけ使える抽象。
- TM は現代 CPU の速度予測には粗すぎる。
- 万能性は自分の停止性を万能に判定できることを意味しない。
- インタプリタ、VM、コンテナ化されたコード実行は「プログラムをデータとして扱う」万能機械の実務像。

### 要点

1. TM は有限制御と非有界テープを持つ。 2. 構成が一計算時点を表す。 3. 多様な TM 変種は計算可能性で同等。 4. 万能 TM は符号化された機械を模倣する。 5. 受理と決定を区別する。

### 誤解チェック（5問）

1. TM は実在ハードウェアか。 2. 非決定性 TM は計算可能性を増やすか。 3. 受理器は必ず停止するか。 4. 多テープで新しい関数が計算可能になるか。 5. 有限入力なら計算も有限か。

### 基礎問題（5問）

1. ビット反転 TM を記述せよ。 2. 構成を3手追跡せよ。 3. 停止状態からの遷移が不要な理由を述べよ。 4. 二テープを一テープへ符号化せよ。 5. 決定器の条件を再述せよ。

### 応用問題（3問）／設計問題／調査課題

1. 万能機械の入力符号化を設計せよ。 2. インタプリタとの類似と相違を論ぜよ。 3. 時間計算量のモデル依存性を述べよ。 **設計:** 安全なコード実行サービスで形式モデル外の資源制限を設計せよ。 **調査:** register machine と TM の等価性を調べよ。

### 知らないとする誤判断／次章への接続

「実機が高速化すれば原理的不能も解ける」と判断する。次章で「実効的手続き」の同定を扱う。

## 第10章　Church--Turing thesis

### この章を学ぶ理由／現場の問題

計算モデルを変えれば不能問題を回避できるのかを考える基準が必要である。これは証明済み定理ではなく、計算という非形式概念と形式モデルを結ぶテーゼである。

### 中心概念と正式な定義

Church--Turing thesis は「実効的に計算可能な関数は Turing 計算可能である」と主張する。ラムダ計算、一般再帰関数、Turing 機械など独立な形式化が同じクラスになったことが強い根拠。Extended/Strong Church--Turing thesis（現実的計算を確率 TM が多項式オーバーヘッドで模倣できる等）は計算量の主張で、量子計算との関係も含め別物である。

### 直感 → 図解 → 数式 → 例 → 実装

```text
effective procedure ──thesis──> TM-computable
lambda calculus == recursive functions == TM  (theorems)
```

Python、CPU、セルオートマトンが汎用計算を表現できても、停止問題は回避しない。

```python
def interpreter(program, input_):
    # 万能性は、別の計算モデルを符号化・模倣できること
    return execute(decode(program), input_)
```

### よくある誤解／実務接続

- テーゼは数学定理ではないため「証明」できない。
- 量子計算は既知の意味で計算可能性境界を越えるのではなく複雑性を変え得る。
- AI がコードを推測できることと決定手続きが存在することは別。
- 新しい言語や計算基盤の「万能」を評価する際、表現力と効率を分離する。

### 要点

1. 実効的計算可能性と TM を同定するテーゼ。 2. 複数形式の収束が根拠。 3. 定理ではない。 4. 計算可能性と効率は別。 5. 強い版と通常版を混同しない。

### 誤解チェック（5問）

1. テーゼは証明されたか。 2. Turing 完全なら高速か。 3. 量子計算は停止問題を決定するか。 4. Excel は計算モデルになり得るか。 5. 有限メモリの実機と抽象 TM は完全に同じか。

### 基礎問題（5問）

1. thesis と theorem を区別せよ。 2. 同等な三モデルを挙げよ。 3. 万能性を説明せよ。 4. 強い版を通常版から分けよ。 5. 実効的手続きの特徴を書け。

### 応用問題（3問）／設計問題／調査課題

1. オラクルが仮定をどう変えるか論ぜよ。 2. AI コード生成をテーゼの反例と呼べない理由を述べよ。 3. 量子計算との関係を整理せよ。 **設計:** 新 DSL を意図的に非 Turing 完全にする利点を記せ。 **調査:** ラムダ計算と TM の等価性の証明概略を調べよ。

### 知らないとする誤判断／次章への接続

## 第11章　決定可能性

### この章を学ぶ理由／現場の問題

検査器や静的解析に「必ず終了し、常に正しい答え」を要求できるかを先に判定しないと、実装努力や仕様が破綻する。

### 中心概念と正式な定義

言語 \(L\) が decidable（recursive）とは、全入力で停止して \(w\in L\) を判定する TM が存在すること。recognizable（recursively enumerable）とは、所属入力を受理する TM が存在すること。\(L\) と補集合 \(\overline L\) がともに recognizable iff \(L\) は decidable。代表例：DFA の受理問題 \(A_{DFA}=\{\langle B,w\rangle\mid B\text{ accepts }w\}\) は決定可能。

### 直感 → 図解 → 数式 → 例 → 実装

```text
decider:      yes -> halt, no -> halt
recognizer:   yes -> halt, no -> reject OR run forever
```

CFG の空性は到達可能・生成可能な非終端を有限回マークして決定できる。一方「任意プログラムがある性質を持つか」は一般に不能になる。

```python
def dfa_acceptance(dfa, word):
    q = dfa.start
    for a in word: q = dfa.delta[q, a]
    return q in dfa.accepting
```

### よくある誤解／実務接続

- ある実装が見つからないことは undecidable の証明ではない。
- semi-decision は timeout 付き decision ではない。
- 有限ドメインへ制限すれば、本来の一般問題が決定可能になることがある。
- model checking、型検査、lint は対象言語・状態を制限して決定可能性を得る。

### 要点

1. 決定器は全入力で停止。 2. 認識器は yes 側だけ保証。 3. 補言語との対称性が決定可能性を特徴づける。 4. 対象制限は重要な設計手段。 5. 不能の主張には証明が要る。

### 誤解チェック（5問）

1. timeout で no を返せば決定器か。 2. 有限言語は決定可能か。 3. recognizable の補集合は必ず recognizable か。 4. undecidable は結果が一つも分からない意味か。 5. 全テスト通過は決定可能性の証明か。

### 基礎問題（5問）

1. 三つの DFA 問題を決定せよ。 2. 有限言語の決定器を作れ。 3. 認識器と列挙器の関係を説明せよ。 4. 補集合定理を概説せよ。 5. timeout 実装の偽陰性を示せ。

### 応用問題（3問）／設計問題／調査課題

1. dovetailing を説明せよ。 2. 有界プログラム検査が決定可能な理由を述べよ。 3. Rice の定理を先取りして性質を分類せよ。 **設計:** 静的解析器の保証範囲と unknown を設計せよ。 **調査:** SMT solver の `unknown` が生じる条件を調べよ。

### 知らないとする誤判断／次章への接続

timeout を「不成立の証明」として扱い、正しい入力を拒絶する。次章では停止問題を用いて一般的不能を証明する。

## 第12章　停止問題

### この章を学ぶ理由／現場の問題

任意コードが終わるかを常に正しく判断する万能ツールは作れない。この限界を知らないと、静的解析やジョブ管理へ矛盾した保証を要求する。

### 中心概念と正式な定義

\(HALT_{TM}=\{\langle M,w\rangle\mid M\text{ halts on }w\}\) は決定不能。仮に決定器 \(H(M,w)\) があるとし、\(D(x)\) を「\(H(x,x)\) が halt なら無限ループ、そうでなければ停止」と作る。\(D(D)\) は停止すると仮定しても非停止と仮定しても矛盾する。

### 直感 → 図解 → 数式 → 例 → 実装

```text
H(D,D)=halts     => D(D) loops
H(D,D)=not halt  => D(D) halts
```

```python
def diagonal(program):
    if hypothetical_halts(program, program):
        while True: pass
    return
```

これは実行資源不足ではなく、自己参照と万能判定仮定の論理矛盾である。個別プログラムや制限言語では停止を証明できる。

### よくある誤解／実務接続

- 「停止を一切解析できない」のではない。万能で完全な判定器がない。
- timeout、監視、fuel は運用上必要だが数学的判定器ではない。
- 人間が証明できる事例があることは反例でない。
- sandbox では CPU、メモリ、syscall を制限し、不能な事前判定を実行時隔離へ置き換える。

### 要点

1. 停止問題は決定不能。 2. 対角化が証明の核。 3. 一般不能と個別証明可能を区別。 4. timeout は unknown の運用処理。 5. 制限言語なら終了性を保証できる。

### 誤解チェック（5問）

1. 静的解析器が停止警告を出せることは矛盾か。 2. 全有限状態機械の停止は判定可能か。 3. 長時間実行は非停止か。 4. AI が予測すれば決定したことになるか。 5. 停止問題はハードウェア改善で解けるか。

### 基礎問題（5問）

1. 対角化証明を自分の言葉で書け。 2. 有界ループ言語の停止性を示せ。 3. timeout の三値結果を設計せよ。 4. 明らかに停止する再帰関数を証明せよ。 5. 明らかな無限ループを検出する規則を書け。

### 応用問題（3問）／設計問題／調査課題

1. total language の利点と制約を論ぜよ。 2. size-change termination の発想を説明せよ。 3. 自己参照を使う証明を一般化せよ。 **設計:** ユーザーコード実行基盤の隔離・fuel・結果状態を設計せよ。 **調査:** proof assistant が終了性を要求する方法を調べよ。

### 知らないとする誤判断／次章への接続

## 第13章　還元

### この章を学ぶ理由／現場の問題

新しい問題の難しさをゼロから論じず、既知問題との変換で分類できる。還元方向を誤ると難しさについて正反対の結論になる。

### 中心概念と正式な定義

写像還元 \(A\le_m B\) とは、全計算可能関数 \(f\) が存在し \(x\in A\iff f(x)\in B\) となること。B の決定器があれば `decide_A(x)=decide_B(f(x))`。よって A が決定不能で \(A\le_m B\) なら B も決定不能。計算量では多項式時間還元 \(\le_p\) を使う。

### 直感 → 図解 → 数式 → 例 → 実装

```text
A instance x --f--> B instance f(x) --solver_B--> answer for A
```

\(A_{TM}\) から停止に還元するなら、M が w を受理した時だけ停止する機械を構成する。

```python
def solve_A(x):
    return solve_B(transform(x))
```

transform が答えを保存し、対象資源内で計算できることを別々に示す。

### よくある誤解／実務接続

- B を A に還元しても「B が難しいから A も難しい」とは限らない。
- 例を数個変換しただけでは全入力の証明にならない。
- undecidability 還元と NP-hardness 還元は資源条件が違う。
- API 互換層、問題の canonicalization、solver 選択に「変換＋既存解法」の実務像がある。

### 要点

1. 還元は解答保存変換。 2. A≤B は B が少なくとも A ほど難しい向き。 3. 変換の計算可能性が必要。 4. 計算量還元では変換コストも制限。 5. 不能性を問題間で移せる。

### 誤解チェック（5問）

1. A≤B なら A が B より難しいか。 2. B が決定可能なら A も決定可能か。 3. A が容易なら B も容易か。 4. 多項式還元で指数変換を使えるか。 5. 一方向の含意だけでよいか。

### 基礎問題（5問）

1. 還元図を描け。 2. 方向を言葉で確認せよ。 3. 恒等還元を説明せよ。 4. 変換の正当性を二方向で示せ。 5. 決定不能性の背理法を書け。

### 応用問題（3問）／設計問題／調査課題

1. HALT から別のプログラム性質へ還元せよ。 2. many-one と Turing reduction を比較せよ。 3. 入力サイズ増大を分析せよ。 **設計:** 複数 solver への共通 IR を設計せよ。 **調査:** SAT への実用還元例を一つ調べよ。

### 知らないとする誤判断／次章への接続

還元方向を逆にして「簡単な問題へ変換できるから難しい」と誤証明する。次章では計算可能な問題の中の資源差へ進む。

## 第14章　計算量理論への入口

### この章を学ぶ理由／現場の問題

決定可能でも入力増加に対して現実的時間・空間で解けない問題がある。「動く」と「スケールする」を分類する語彙が必要である。

### 中心概念と正式な定義

入力長 \(n=|x|\) に対し時間 \(T(n)\)、空間 \(S(n)\) を測る。\(P=\bigcup_k TIME(n^k)\)。NP は yes 証明書を多項式時間で検証できる決定問題（同値に非決定性 TM の多項式時間）。問題 B が NP-hard とは全 \(A\in NP\) について \(A\le_p B\)、さらに \(B\in NP\) なら NP-complete。P対NPは未解決である。

### 直感 → 図解 → 数式 → 例 → 実装

```text
undecidable | decidable but costly | polynomially bounded
                       NP: yes witness checked quickly
```

SAT の割当て `w` は \(V(\varphi,w)\in O(|\varphi|)\) で検証できるが、既知の一般解法は最悪指数的。

```python
def verify_sat(formula, assignment):
    return all(any(eval_lit(x, assignment) for x in clause)
               for clause in formula)
```

### よくある誤解／実務接続

- NP は「非多項式」でも「非常に難しい」の略でもない。
- NP-hard 問題が決定問題とは限らず、NP に入るとも限らない。
- 最悪計算量と典型入力性能、固定パラメータ、近似可能性を分ける。
- 配置、スケジューリング、依存解決、テスト生成は solver と制約設計に接続する。

### 要点

1. 計算量は入力長の関数。 2. P は決定性多項式時間。 3. NP は証明書を速く検証可能。 4. NP-complete は NP 内の最難群。 5. P=NP は未解決。

### 誤解チェック（5問）

1. NP=not polynomial か。 2. NP-hard はすべて NP-complete か。 3. 指数時間は小入力でも必ず遅いか。 4. SAT の候補検証も指数時間か。 5. P≠NP は証明済みか。

### 基礎問題（5問）

1. 入力長を定義せよ。 2. 証明書と検証器を例示せよ。 3. P⊆NP を説明せよ。 4. NP-hard と complete を区別せよ。 5. 2^n の増加を計算せよ。

### 応用問題（3問）／設計問題／調査課題

1. 最適化問題を決定問題へ変換せよ。 2. pseudo-polynomial を説明せよ。 3. パラメータ化計算量の利点を述べよ。 **設計:** シフト割当てで厳密解・近似・時間上限を選べ。 **調査:** 利用中 solver の終了条件を調べよ。

### 知らないとする誤判断／次章への接続

NP-hard と分かった時点で「実務では解けない」と捨て、構造・近似・小パラメータを見ない。次章で理論を実務の道具へ配置する。

## 第15章　実務との接続：parser・protocol・static analysis・verification・DSL

### この章を学ぶ理由／現場の問題

形式理論は実装から遠いのではなく、保証範囲を小さく正確に言うための設計道具である。強すぎる DSL と完全すぎる解析要求が保守性を壊す。

### 中心概念と正式な定義

protocol state machine は許容 trace の言語を定義する。abstract interpretation は具体状態集合を抽象領域へ写し、健全な過近似で性質を解析する。model checking は遷移系 \(K\) が時相論理式 \(\varphi\) を満たす \(K\models\varphi\) か調べる。DSL は対象領域の構文・意味・能力を意図的に制約した言語である。

### 直感 → 図解 → 数式 → 例 → 実装

```text
events -> monitor DFA -> allowed/rejected trace
program -> abstract states -> warning / proved-safe / unknown
DSL source -> parser -> typed AST -> bounded evaluator
```

```python
def protocol_step(state, event):
    try: return TRANSITIONS[state, event]
    except KeyError: raise ProtocolViolation(state, event)
```

完全性を捨て偽陽性を許す、あるいは健全性を捨て bug finder と明記するなど、契約を選ぶ。

### よくある誤解／実務接続

- 静的解析は yes/no の万能神託ではない。
- DSL を Turing 完全にすることは機能追加でなく解析契約の変更。
- protocol の happy path だけでは再接続・重複・順序逆転を表せない。
- verification はテストの代替一語ではなく、モデルと仮定の下での証明。

### 要点

1. trace を言語として扱える。 2. 抽象解釈は健全な近似を設計する。 3. model checking は有限化・状態爆発との戦い。 4. DSL 制限は価値。 5. 保証には仮定と対象範囲が必要。

### 誤解チェック（5問）

1. 警告なしは常に安全証明か。 2. 偽陽性ゼロと偽陰性ゼロを常に両立できるか。 3. DSL は汎用言語より弱いと失敗か。 4. モデル検査は現実そのものを検査するか。 5. trace 検査は過去の状態を要約できるか。

### 基礎問題（5問）

1. protocol trace を DFA にせよ。 2. unknown を含む結果型を書け。 3. DSL の能力を列挙せよ。 4. 健全性と完全性を説明せよ。 5. model と実装の対応仮定を書け。

### 応用問題（3問）／設計問題／調査課題

1. 状態爆発への抽象化を提案せよ。 2. typestate API を設計せよ。 3. bug finder と verifier の UI を比較せよ。 **設計:** 課金ルール DSL を終了保証付きで設計せよ。 **調査:** TLA+、Alloy、SPIN の一つを一次資料で調べよ。

### 知らないとする誤判断／次章への接続

「解析器が通したので本番障害はあり得ない」と、モデル外の I/O・障害・仮定を無視する。次章では問題分類の実践手順を作る。

## 第16章　「解けない問題」を認識する

### この章を学ぶ理由／現場の問題

不能性を言い訳にせず、要求を分類し直して有用な保証へ変換する能力が必要である。曖昧な「自動で全部検査」を、判定対象・量化・停止要求へ分解する。

### 中心概念と正式な定義

分類手順は (1) 入力と yes/no 性質を言語化、(2) 状態・記憶の上限、(3) 全入力で停止する必要、(4) 既知問題への/からの還元、(5) 計算量、(6) 制約・近似・半決定・運用隔離の選択。Rice の定理：認識言語に関する任意の非自明な意味的性質は TM 記述について決定不能。構文的性質や有限制限には直接適用しない。

### 直感 → 図解 → 数式 → 例 → 実装

```text
requirement -> formal language/property
  -> REG/CFL? -> decidable? -> feasible?
  -> exact / approximate / bounded / unknown / runtime isolation
```

「任意 plugin が秘密を送らない」を一般コードの意味的性質として完全判定するのは不能。対策は capability 制限、通信遮断、監査、既知危険パターン検出に分解する。

```python
class Result(Enum): PROVED = 1; REFUTED = 2; UNKNOWN = 3
```

### よくある誤解／実務接続

- undecidable は対策不能ではない。仕様制限と実行時制御が主要な対策。
- heuristic の成功を完全判定と広告しない。
- Rice の定理を文字数や AST 形状の構文検査へ誤適用しない。
- `unknown` は欠陥ではなく、保証を誠実に表す場合がある。

### 要点

1. まず問題を言語として定式化。 2. 表現能力・決定可能性・複雑性を順に分ける。 3. Rice は非自明な意味的性質を対象。 4. 制限は保証を可能にする。 5. 三値・近似・隔離を設計選択にする。

### 誤解チェック（5問）

1. undecidable なら一例も答えられないか。 2. heuristic は決定器か。 3. Rice は構文的 lint に適用されるか。 4. 有限状態へ制限すれば変わるか。 5. `unknown` を false と同一視してよいか。

### 基礎問題（5問）

1. 要求を yes/no 問題にせよ。 2. 三つの問題を階層分類せよ。 3. 意味的/構文的性質を分けよ。 4. 制限で決定可能にせよ。 5. 結果型を設計せよ。

### 応用問題（3問）／設計問題／調査課題

1. 任意 migration の無損失性要求を分解せよ。 2. マルウェア完全検出要求を再設計せよ。 3. solver timeout の契約を書け。 **設計:** plugin 審査を静的解析・sandbox・監視へ分割せよ。 **調査:** Rice の定理の正確な仮定と証明を調べよ。

### 知らないとする誤判断／次章への接続

解けない一般問題を、無期限の実装努力か偽の保証で覆う。次の最終章で典型的な誤判断を横断的に点検する。

## 第17章　この分野を知らないエンジニアが陥りやすい誤判断

### この章を学ぶ理由／現場の問題

形式理論を個別用語として覚えても、要求の表現能力、停止保証、資源量を混同すれば設計判断には使えない。実務で頻出する誤りを原因仮説から診断し、保証可能な問題へ作り替える。

### 中心概念と正式な定義

問題 \(L\subseteq\Sigma^*\) について、(1)必要記憶から REG/CFL/より強い言語族を分類し、(2)全入力で停止するdeciderの存在、(3)入力長nに対する時間・空間、(4)実装上の有限資源と失敗契約を順に問う。これら四層のどこを議論しているかを明示することが誤判断対策の中心である。

### 直感 → 図解 → 数式 → 例 → 実装

```text
requirement -> language/model -> decidable? -> feasible? -> bounded implementation
              REG/CFL/TM        yes/no        T(n),S(n)    timeout/unknown/isolation
```

```python
class AnalysisResult(Enum):
    PROVED = 1
    REFUTED = 2
    UNKNOWN = 3
```

「任意pluginは安全か」を完全なyes/no検査へ潰さず、構文規則、制限DSL、soundな部分証明、heuristic警告、sandboxへ責務分解するのが具体例である。

### Countermeasures：誤判断22例

以下は優先度の高い仮説から並べた。形式は「**対策: 作業（想定原因）**」である。

1. **対策: 入力制約を有限状態・スタック・意味検査へ分解する（想定原因: regex を万能な構文解析器だと考える）。** 入れ子は parser、名前や型は意味解析へ移す。
2. **対策: 信頼不能入力には線形時間保証の regex エンジンと長さ上限を選ぶ（想定原因: パターンが短ければ高速だと思う）。** 曖昧な反復のバックトラックを負荷試験する。
3. **対策: ワークフローを状態と許容遷移の表で定義する（想定原因: 状態は分岐から自然に読み取れると思う）。** 不変条件と禁止遷移も同じ仕様に置く。
4. **対策: 「受理」「拒否」「不明/継続中」を別の結果にする（想定原因: 認識可能性と決定可能性を混同する）。** timeout を false に変換しない。
5. **対策: ユーザーコードを資源制限・権限制限・隔離下で実行する（想定原因: 停止性を事前に完全判定できると思う）。** 監視と強制終了を通常経路にする。
6. **対策: DSL の必要能力を先に定義し意図的に Turing 非完全に保つ（想定原因: 表現力が高いほど良いと思う）。** 有界反復や総関数で解析可能性を得る。
7. **対策: 構文、意味、実行時環境の保証を分離する（想定原因: parse 成功を安全性保証と考える）。** 型、権限、I/O 失敗は別境界で扱う。
8. **対策: 還元図を「A の solver を B で作る」と読み上げる（想定原因: 還元方向を暗記する）。** 難しさを移す向きをレビューで検算する。
9. **対策: 一般不能と制限領域での判定可能を同時に文書化する（想定原因: undecidable を何も解析できない意味に取る）。** bounded model checking 等の適用範囲を書く。
10. **対策: 最悪計算量、典型性能、入力分布、パラメータを別に測る（想定原因: NP-hard なら実務で常に解けないと思う）。** 時間上限と incumbent 解を返す。
11. **対策: lexer、parser、AST、意味解析に異なる型を使う（想定原因: すべてを文字列変換として実装する）。** source span を全段で保持する。
12. **対策: 文法に優先順位と結合性を明示する（想定原因: parser が常識的に解釈すると思う）。** 曖昧な入力を golden test に入れる。
13. **対策: 再帰入力に深さ・サイズ予算を置く（想定原因: 文脈自由構造なら実装資源も無限に使えると思う）。** stack exhaustion と巨大 AST を防ぐ。
14. **対策: 正規性の主張を DFA 構成または閉包性で証明する（想定原因: pumping lemma を正規性の証明に使う）。** lemma は主に非正規性反証へ使う。
15. **対策: NFA の候補集合と DFA 状態数を見積もる（想定原因: NFA が魔法の並列性で高速だと思う）。** 部分集合爆発を設計コストに入れる。
16. **対策: 静的解析の健全性・完全性・対象言語・仮定を書く（想定原因: 警告ゼロをバグゼロと読む）。** `unknown` と対象外を可視化する。
17. **対策: モデルと実装の対応を検証するテストを作る（想定原因: 形式モデルを証明すれば実装も自動的に正しいと思う）。** parser、整数範囲、I/O の refinement gap を確認する。
18. **対策: 新計算基盤の主張を計算可能性と効率へ分ける（想定原因: 量子・AI が原理的不能をすべて解くと思う）。** 停止問題と速度向上を混ぜない。
19. **対策: protocol trace の重複・再順序化・再接続を状態機械へ入れる（想定原因: happy path の系列だけが仕様だと思う）。** 障害注入で禁止遷移を試す。
20. **対策: heuristic を成功率・偽陽性・偽陰性付きで提供する（想定原因: 多くの場合当たることを決定手続きと呼ぶ）。** 完全保証の表現を避ける。
21. **対策: 証明書検証の容易さと探索の容易さを分ける（想定原因: 答えを速く確認できるなら速く見つかると思う）。** NP の定義を verifier から確認する。
22. **対策: 実験でなく反例構成または還元で不能性を論じる（想定原因: 多数のテスト不成功を不可能性の証明とする）。** 経験的限界と数学的限界を区別する。

### よくある誤解／実務接続

- 「理論上不能」は対策不能を意味しない。入力制限、近似、三値結果、実行時隔離へ設計を変える。
- Turing完全性は製品価値や性能の尺度ではない。設定・policy言語では弱さが保証になる。
- formal proofの保証はmodel、仮定、実装対応の範囲内である。
- parser、protocol、static analysis、verification、solver、plugin実行のreviewに四層分類を組み込む。

### 要点

1. 表現能力、決定可能性、計算量、実装資源を分ける。 2. 最弱で十分な計算modelを選ぶ。 3. timeoutをfalseに変換しない。 4. heuristicの誤り率と保証範囲を示す。 5. 不能問題は制約と隔離で有用な問題へ変える。

### 誤解チェック（5問）

1. undecidableなら個別入力にも答えられないか。 2. Turing完全なら高速か。 3. parser成功は意味的安全を保証するか。 4. timeoutは非停止証明か。 5. NFAはDFAより多くの言語を認識するか。

### 基礎問題（5問）

1. 入力検証を正規・文脈自由・意味制約へ分けよ。 2. 三値解析結果をAPI型にせよ。 3. 還元方向を図で確認せよ。 4. 一つのDSLを非Turing完全に制限せよ。 5. regexの最悪実行方式を調べる手順を書け。

### 応用問題（3問）／設計問題／調査課題

1. 任意programの秘密送信検出要求を再設計せよ。 2. NP-hard schedulingを時間上限・近似・証明書付きで設計せよ。 3. model checkerのstate explosionを抽象化で緩和せよ。 **設計:** plugin platformをDSL、static check、capability、sandbox、monitoringへ分割せよ。 **調査:** 組織の一つの「安全保証」がsound/complete/heuristicのどれか監査せよ。

### 知らないとする誤判断／次章への接続

万能検査器を約束するか、不能性を理由に何も検査しないかの二択に陥る。本書の次は実案件を四層へ分類し、形式仕様とproperty test、runtime controlを同じ保証caseに結びつける。

## 付録　専門家の思考を測る

### 専門家が共有する5つの中核的メンタルモデル

1. **言語は文字列の集合であり、記法や機械はその集合を扱う別々の表現である。** 直感的には、正規表現、DFA、NFA は同じ境界線を異なる道具で描き得る。正式には、二つの表現が受理する言語の等価性と、表現変換の正しさ・サイズ増大を分けて考える。実務では、要件を先に言語として定めてから、検証、生成、説明可能性に合う表現を選ぶ。
2. **表現能力・決定可能性・計算量・有限資源は別の層である。** 「書ける」「必ず答えられる」「現実的な時間で答えられる」「この本番環境で安全に動く」は同じ問いではない。正式には言語族、decider の存在、時間・空間計算量、実装上限を順に区別する。設計レビューでは、timeout や近似がどの層への対策かを明記し、原理的不可能性と性能不足を混同しない。
3. **閉包性と還元は、未知の問題を既知の問題へ運ぶ変換装置である。** 直感的には、問題の外見ではなく「既知の境界を壊さず写せるか」を見る。正式には変換が yes/no を保存すること、計算可能または所要計算量内であること、還元方向が正しいことを証明する。実務では、新しい検査器をゼロから信じず、既知の parser、solver、検証可能な証明書へ落とせるかを判断する。
4. **機械の記述もデータになり、自己参照が万能解析の限界を生む。** プログラムを入力として別のプログラムへ渡せると、対角化や停止問題の構図が現れる。正式には符号化、universal machine、自己適用を通じて「全入力に対して正しく停止する解析器」という仮定を反転する。実務では、万能な静的判定を約束せず、対象言語の制限、sound な部分解析、三値結果、sandbox を組み合わせる。
5. **十分な最弱モデルを選ぶことが保証を買う。** 表現力は一方向の品質尺度ではなく、不要な能力を捨てると停止性、解析可能性、説明可能性が得られる。正式には有限状態、有界メモリ、総関数、構造的再帰などの制約が許す性質を示す。設定言語、policy、workflow では、必要要件から能力を逆算し、Turing 完全性を安易に持ち込まない。

### 専門家の意見が根本的に分かれる3つの論点

1. **汎用言語には最大限の表現力を与えるべきか、意図的に総関数的・制限的にすべきか。** **立場A（表現力重視）の steelman:** 現実の要件は事前に閉じず、一般再帰や効果を禁止すると利用者は言語外の逃げ道を作り、統合全体はかえって複雑で検証不能になる。**立場B（制約重視）の steelman:** policy、build、設定のように保証が価値となる領域では、全停止や決定可能な解析を構文で保証する方が、任意コードを後から監視するより強く単純である。拡張性、信頼境界、失敗時の被害、要求できる保証の強さによって判断が変わる。
2. **古典的な最悪時漸近解析を中心に据えるか、分布・パラメータ・実測を中心に据えるか。** **立場A（最悪時重視）の steelman:** 入力分布は変化し攻撃者にも選べるため、機械非依存の上界こそ長期に残る安全な契約であり、平均値は破局的 tail を隠す。**立場B（構造と実測重視）の steelman:** NP-hard という粗い分類だけでは、固定パラメータ、近似、実入力の構造、hardware 特性によって十分解ける案件の判断を誤る。敵対入力の有無、SLO、入力分布の安定性、近似許容度、定数項とデータ規模によって重み付けが変わる。
3. **高保証を証明中心で構築するか、試験・監視・隔離を含む運用的 assurance case として構築するか。** **立場A（証明中心）の steelman:** safety-critical な不変条件は有限個の test では覆えず、仕様から実装への refinement を証明して初めて全状態への主張ができる。**立場B（運用的保証重視）の steelman:** model、compiler、hardware、operator を含む現実の system は証明対象の外にも失敗点を持ち、fault injection と観測・回復能力を欠いた証明済み component は system-level reliability を保証しない。被害の重大性、状態空間、仕様の安定性、証明と実装の対応、運用環境の変化率で投資配分が変わる。

### 深い理解と暗記を見分ける10の質問

1. 入れ子を含む設定構文と、変数の宣言前参照を禁止する規則がある。どこまでを正規言語、文脈自由言語、意味解析で扱うか、境界をずらした場合の反例と実装コストを説明せよ。
2. ある malware detector が全ての program を必ず `safe` / `unsafe` に分類すると主張している。その主張を停止問題へ結び付ける還元の方向を示し、実用的に成立するよう要求をどう弱めるか述べよ。
3. NFA から DFA への変換で指数個の状態が生じ得るのに、両者を同じ表現能力だと言えるのはなぜか。表現能力と記述量を混同するとどんな設計判断を誤るか。
4. 100万件の実入力ですぐ停止した program について、「停止する」とどの範囲まで主張できるか。追加の仮定ごとに、主張を強める証拠と反例を挙げよ。
5. NP-hard な scheduling が本番で毎日解けている。この事実は理論分類と矛盾するか。入力構造、parameter、近似、最悪例を用いて説明せよ。
6. regex engine を置き換えずに入力長上限だけを加えたとき、ReDoS の risk はどこまで変わるか。時間計算量、定数、同時実行数、攻撃者の選択能力から評価せよ。
7. 静的解析器が「警告なし」を返した。この結果から安全を結論するために必要な soundness、対象言語、環境仮定を列挙し、一つが崩れる反例を作れ。
8. Turing 完全な既存 DSL を総停止する言語へ再設計する。失われる正当な利用例と、代わりに得られる保証を比較し、移行境界をどう決めるか。
9. ある性質について model checker が `unknown`、runtime monitor が違反なしを返した。これらを `true` に統合してはいけない理由と、利用者へ返す結果型を設計せよ。
10. 新しい計算模型が従来より大幅に高速だという仮定の下でも、停止不能性が通常は消えない理由を説明せよ。どの仮定が変われば結論を再検討すべきかも示せ。
