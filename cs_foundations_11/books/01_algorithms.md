# アルゴリズムと計算量――規模と制約から設計を判断する

対象は、コードは書けるが計算機科学を体系的に学んでいない実務者である。本書でいう入力サイズ `n` は、件数とは限らず、頂点数、文字数、ビット長、制約の個数など「仕事量を支配する量」である。Python は観察装置として使い、言語機能とアルゴリズムを混同しない。式は、前提を明記したモデルであり、実測を不要にするものではない。

**関連巻:** 証明・集合・グラフの記法は [離散数学](02_discrete_math.md)、memory/I/Oの実費用は [オペレーティングシステム](05_operating_systems.md)、indexとquery planは [データベース理論](07_database.md)、乱択・測定の不確実性は [確率・統計](08_probability_statistics.md) を参照する。

## 第1章 アルゴリズムとは何か

### この章を学ぶ理由
同じ仕様を満たすプログラムでも、入力全域で終了して正しい答えを返す手続きと、たまたまテストを通る実装は違う。変更前に「正しさ」と「費用」を別々に論証する語彙を得る。

### 現場の問題
100件のサンプルでは速い重複検査が、本番の1,000万件で停止する。ベンチマーク値だけでは、入力分布、計算機、負荷が変わった後を説明できない。

### 中心概念と正式定義
アルゴリズムは、許される入力集合から出力へ至る有限で曖昧でない手続きである。仕様を前提条件 `P` と事後条件 `Q` で表す。部分正当性は「`P` で開始し終了すれば `Q`」、全正当性はそれに停止性を加える。プログラムは特定言語・実行環境での表現である。費用関数 `T(x)` と入力サイズ `|x|=n` を区別し、最悪値 `T_w(n)=max_{|x|=n}T(x)`、最良値は `min`、平均値は明示した分布 `D_n` に対する `E[T(X)]` とする。

### 直感→図解→数式→例→実装または疑似コード
料理手順がアルゴリズム、厨房と器具を含む実施がプログラムに相当する。`入力 → [前提条件] → 手続き → [事後条件] → 出力`。最大値探索なら不変条件は「走査済み範囲の最大値が `best`」。比較回数は常に `n-1` である。

```python
def maximum(xs):
    assert xs
    best = xs[0]
    for x in xs[1:]:
        if x > best:
            best = x
    return best
```

### よくある誤解
「結果が合った」は証明ではない。平均ケースは都合のよい入力の平均でもない。CPU時間、I/O、メモリ、通信量は異なる費用尺度である。

### 実務接続
SLA設計では p99 実測と、件数増加に対する費用モデルの両方を使う。API仕様の前提条件、DB制約、ループ不変条件は同じ正しさの鎖に属する。

### 要点
- アルゴリズムは言語から独立した手続きである。
- 正しさは仕様に相対的である。
- 全正当性には停止性が必要である。
- 入力サイズは支配変数として選ぶ。
- 平均計算量には確率分布が要る。
- 実測と漸近解析は補完関係にある。

### 誤解チェック
1. 同じアルゴリズムなら全言語で実測時間も同じか。2. テスト網羅率100%なら正しさは証明済みか。3. 最悪ケースは現実に起きない入力か。4. `n` は必ずレコード件数か。5. 部分正当性は停止を保証するか。

### 基礎問題
1. ログ検索の入力サイズを三通り定義せよ。2. 最大値探索の不変条件を書け。3. 最良・最悪が異なる処理を挙げよ。4. 停止しない正しい途中計算の反例を作れ。5. CPU以外の費用尺度を三つ挙げよ。

### 応用問題
1. タイムアウトを含むAPIの正しさを定義せよ。2. キャッシュ有無で平均費用を表せ。3. 外部ソートの費用尺度を設計せよ。

### 設計問題
請求バッチについて、前提・事後条件、失敗時の意味、入力サイズ、時間・空間・I/O費用を含むレビュー票を作れ。

### 調査課題
Python の `sorted` の仕様と実装を調べ、保証された性質と実装依存の性質を分けよ。

### 知らないとする誤判断
小さな正常データでの速さを、規模変更後の安全性だと判断する。

### 次章接続
費用関数の増え方を比較するため、第2章で漸近記法を導入する。

## 第2章 計算量

### この章を学ぶ理由
ハードウェア世代を越えて、入力規模に対する増加率を比較できるようにする。

### 現場の問題
「O記法では定数を無視するから実務に無意味」「`O(n²)` でも速いCPUなら平気」というレビューを正す必要がある。

### 中心概念と正式定義
`f∈O(g)` は、ある `c>0,n0` が存在して `n≥n0` で `0≤f(n)≤cg(n)`。`f∈Ω(g)` は逆向きの下界、`Θ(g)=O(g)∩Ω(g)`。これは集合であり等号ではない。`log_b n=ln n/ln b` なので底の差は定数倍。代表的増加順は `1 < log n < n < n log n < n² < 2^n < n!`。

### 直感→図解→数式→例→実装または疑似コード
入力を倍にしたときの倍率を見る。`log n:+1`、`n:×2`、`n log n:約×2`、`n²:×4`、`2^n:二乗`。`n=50` では `n²=2,500` だが `2^n≈1.13×10^15`。二重ループでも内側が等比縮小なら線形になり得る。

```text
for i = 1..n:
  j = n
  while j > 0: j = floor(j/2)   # Θ(n log n)
```

### よくある誤解
`O(n)` は常に `O(n²)` より実測が速い、`O(1)` は一命令、最悪 `O(n)` なら平均も `Θ(n)`、という推論はいずれも誤りである。

### 実務接続
DBのクエリ計画、JSON応答サイズ、リトライ増幅、メモリ上限を同じ増加率の言葉で比較する。定数・局所性・並列性は漸近クラスを選んだ後に実測する。

### 要点
- Oは上界、Ωは下界、Θは同じ次数である。
- 閾値以後の増加率を扱う。
- 定数を捨てるのは機種非依存の構造を見るためである。
- 対数の底は漸近クラスを変えない。
- 指数時間は入力増加に極端に弱い。
- 時間と空間の計算量を分ける。

### 誤解チェック
1. `3n+4=O(n²)` は偽か。2. `O(1)` は時間一定か。3. `log₂n` と `log₁₀n` は同じΘか。4. `n=10` で速ければ次数は不要か。5. 上界だけで厳密な増加率が分かるか。

### 基礎問題
1. `7n²+2n+9` をΘで表せ。2. `n` を倍にした倍率を各クラスで求めよ。3. 三重ループの回数を数えよ。4. `1+2+…+n` を導出せよ。5. 再帰深さ `log₂n` の例を示せ。

### 応用問題
1. 1秒に10⁸操作として各クラスの実行可能規模を比較せよ。2. 償却 `O(1)` と最悪 `O(n)` の違いを説明せよ。3. ネットワーク往復を含む費用モデルを作れ。

### 設計問題
日次件数が毎年10倍になる処理について、5年後までの計算・保存・通信予算を見積もれ。

### 調査課題
任意の標準ライブラリ操作の計算量保証を一次文書と実装コードで照合せよ。

### 知らないとする誤判断
係数だけの高速化で、悪い増加率を恒久的に解決したと思う。

### 次章接続
増加率は操作の選び方で決まる。第3章ではデータ配置と操作コストを結ぶ。

## 第3章 配列・リスト・スタック・キュー

### この章を学ぶ理由
抽象データ型とメモリ上の表現を分け、操作集合に合う構造を選ぶ。

### 現場の問題
先頭挿入の多いワークロードに配列を使う、ランダムアクセスに連結リストを使う、無制限キューで障害を遅延させる、といった設計不整合が起きる。

### 中心概念と正式定義
配列は連続領域に同型要素を置き、添字アクセス `Θ(1)`、途中挿入・削除 `Θ(n)`。連結リストはノードと参照で表し、位置既知の挿入 `Θ(1)`、k番目探索 `Θ(k)`。スタックはLIFO、キューはFIFOという抽象データ型である。動的配列は容量を幾何級数的に拡張する。総コピー回数 `1+2+4+…<2n` より append は償却 `Θ(1)`。

### 直感→図解→数式→例→実装または疑似コード
配列 `[a][b][c][ ][ ]` は近接性が高い。リスト `[a|•]→[b|•]→[c|null]` は位置を辿る。容量を2倍にする `push` は時々 `Θ(n)` だが `m` 回の総費用は `Θ(m)`。

```python
class Stack:
    def __init__(self): self._a = []
    def push(self, x): self._a.append(x)
    def pop(self): return self._a.pop()
```

### よくある誤解
連結リストの挿入が常に速いわけではなく、挿入位置の探索を含めれば線形である。償却計算量は確率的平均ではない。

### 実務接続
CPUキャッシュにより連続配列は漸近次数が同じでも速いことが多い。バックプレッシャ付き境界キューはメモリを有限にし、過負荷を観測可能にする。

### 要点
- ADTは許される操作、構造は表現である。
- 配列はランダムアクセスと局所性に強い。
- リストは参照既知の局所更新に強い。
- スタックはLIFO、キューはFIFOである。
- 動的配列のappendは償却定数時間である。
- 無境界キューは容量計画を隠す。

### 誤解チェック
1. リストのk番目アクセスはO(1)か。2. 配列の末尾追加は毎回O(1)か。3. 償却平均には入力分布が必要か。4. FIFOは再帰呼出しに適するか。5. 同じΘならキャッシュ差は無視できるか。

### 基礎問題
1. 操作表を作れ。2. 2倍拡張のコピー総数を求めよ。3. 括弧検査にスタックを使え。4. BFS用キューの不変条件を書け。5. 循環バッファの添字式を書け。

### 応用問題
1. 拡張率1.5と2を比較せよ。2. dequeの用途を分析せよ。3. キュー飽和時の方針を比較せよ。

### 設計問題
毎秒10万イベント、許容遅延2秒の処理器について、構造、容量、溢れ方を設計せよ。

### 調査課題
CPython `list` と `collections.deque` の実装・複雑度を調べよ。

### 知らないとする誤判断
抽象操作名だけを見て、配置・探索費用・容量上限を無視する。

### 次章接続
データ配置が分かれば、探索の正しさを不変条件で説明できる。

## 第4章 探索

### この章を学ぶ理由
探索を「APIを呼ぶこと」でなく、探索空間を正しく縮小する過程として理解する。

### 現場の問題
境界の一件を取りこぼす二分探索、未整列データへの適用、DBで索引を使えない述語が本番障害になる。

### 中心概念と正式定義
線形探索は各候補を検査し最悪 `Θ(n)`。二分探索は全順序で整列された列に対し、候補区間を毎回半減して `Θ(log n)`。lower bound は「`a[i]≥x` となる最小i」。半開区間 `[lo,hi)` と不変条件「答えは区間内」を維持する。反復回数 `k` は `n/2^k≤1` より `k≥log₂n`。

### 直感→図解→数式→例→実装または疑似コード
`[小さい | 未確定 | 大きい]` の未確定区間を半分にする。重複があると「どれか」と「最初」の仕様は異なる。

```python
def lower_bound(a, x):
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] < x: lo = mid + 1
        else: hi = mid
    return lo
```

### よくある誤解
二分探索は値が数値なら使えるのではなく、判定が境界を境に単調である必要がある。「中央を調べる」だけでは不十分で、不変条件と終了測度が要る。

### 実務接続
時刻ログの範囲検索、B-tree索引、設定値に対する最小可行容量の探索は単調述語上の二分探索で統一できる。

### 要点
- 線形探索は前提が少ない。
- 二分探索には順序または単調述語が必要である。
- 半開区間は境界を統一する。
- 不変条件が正しさを支える。
- lower/upper bound は重複の仕様を明示する。
- 探索前のソート費用も数える。

### 誤解チェック
1. 未整列配列に二分探索できるか。2. 一回だけなら先にソートすべきか。3. `lo<hi` の終了性を説明できるか。4. 重複時の返値は自明か。5. 文字列にも全順序があれば使えるか。

### 基礎問題
1. 7要素で反復を追跡せよ。2. upper boundを書け。3. 空配列を検証せよ。4. 線形探索の最良・最悪を求めよ。5. 不変条件を帰納的に示せ。

### 応用問題
1. 答え上の二分探索を例示せよ。2. 浮動小数点探索の停止条件を設計せよ。3. リモートAPI探索の費用を分析せよ。

### 設計問題
10億件の時系列ログに対する点・範囲・最新検索を、更新頻度も含め設計せよ。

### 調査課題
Python `bisect` の重複・key・スレッド安全性の契約を調べよ。

### 知らないとする誤判断
比較回数だけを減らし、整列維持やランダムI/Oの費用を見落とす。

### 次章接続
探索を速くする整列を、正しさ・安定性・下界から比較する。

## 第5章 ソート

### この章を学ぶ理由
ソートを速度順位ではなく、入力特性、メモリ、安定性、最悪保証で選ぶ。

### 現場の問題
同値キーの順序が壊れてページング結果が揺れる、再帰quicksortが敵対入力で停止する、全データをメモリへ載せてOOMになる。

### 中心概念と正式定義
選択ソートは最小を選び `Θ(n²)`・通常不安定。挿入ソートは既整列接頭辞へ挿入し最悪 `Θ(n²)`、ほぼ整列なら速い。merge sort は分割・線形併合で `Θ(n log n)`、追加 `Θ(n)`、安定化可能。quicksort はpartitionし平均 `Θ(n log n)`、最悪 `Θ(n²)`。heap sort は `Θ(n log n)`・in-place・不安定。安定とは等値要素の相対順を保存すること。比較ソート決定木は `n!` 葉を持ち高さ `≥log₂(n!)=Ω(n log n)`。

### 直感→図解→数式→例→実装または疑似コード
mergeは `[1,4,7]+[2,3,8]→[1,2,3,4,7,8]`。漸化式 `T(n)=2T(n/2)+Θ(n)=Θ(n log n)`。

```text
merge_sort(A):
  if |A|≤1 return A
  L,R = split(A)
  return merge(merge_sort(L), merge_sort(R))
```

### よくある誤解
`quicksort` は常に最速ではない。比較下界は整数のcounting sort等に適用されない。安定性は「壊れにくい」の意味ではない。

### 実務接続
複合キーでは後段の安定ソートが前段順序を保存する。外部merge sortは連続I/Oを利用し、DB `ORDER BY` のspill設計へつながる。

### 要点
- 適応性、安定性、空間、最悪保証を比較する。
- 挿入ソートは小規模・ほぼ整列に強い。
- merge sortは安定な最悪Θ(n log n)を得やすい。
- quicksortのpivotは最悪ケースを左右する。
- heap sortは追加空間を抑える。
- 比較モデルにはΩ(n log n)下界がある。

### 誤解チェック
1. 安定ソートは障害耐性が高いか。2. quicksortは最悪もn log nか。3. 比較下界は全ソートに適用されるか。4. merge sortはin-placeか。5. 既整列入力で挿入ソートは二乗か。

### 基礎問題
1. 各方式を5要素で追跡せよ。2. 安定性の反例を作れ。3. 比較回数を数えよ。4. mergeの不変条件を書け。5. heap sortの空間を説明せよ。

### 応用問題
1. 三方向partitionを設計せよ。2. introsortの動機を説明せよ。3. 100GBを1GBメモリで整列せよ。

### 設計問題
多言語氏名・更新時刻・IDによる再現可能な一覧順序を定義し、照合順序まで決めよ。

### 調査課題
Timsortのrun検出と最悪計算量を一次資料または実装で調べよ。

### 知らないとする誤判断
平均ベンチマークだけで選び、敵対入力・安定性・spillを無視する。

### 次章接続
順序ではなくキーから直接位置を得るハッシュを扱う。

## 第6章 ハッシュ

### この章を学ぶ理由
期待定数時間という言葉の前提と、衝突・容量・敵対性を設計できるようにする。

### 現場の問題
負荷率上昇でレイテンシが跳ねる、利用者キーで衝突攻撃を受ける、反復順へ誤って依存する。

### 中心概念と正式定義
ハッシュ関数 `h:U→{0,…,m-1}` は広いキー空間を表サイズへ写す。鳩の巣原理により `|U|>m` なら衝突は不可避。chainingはbucketに集合を持ち、単純一様仮定で成功探索期待 `Θ(1+α)`、`α=n/m`。open addressingは表内をprobeし `α<1` が必要で、削除にはtombstone等が要る。暗号学的ハッシュと表用ハッシュの目的は違う。

### 直感→図解→数式→例→実装または疑似コード
`key → h → bucket → 衝突解決`。負荷率が閾値を越えたら新表へrehashする総費用は動的配列同様に償却できる。

```text
get(k):
  for (key,value) in table[h(k)]:
    if key == k: return value
  return NOT_FOUND
```

### よくある誤解
衝突ゼロが良い関数の定義ではない。平均O(1)は無条件の最悪保証でなく、順序範囲検索もできない。hash値が同じでもキー同値とは限らない。

### 実務接続
言語runtimeのmap、DB hash join、分散partitionに現れる。公開入力ではseeded hash、容量制御、最悪時のtree化などを検討する。

### 要点
- 衝突は原理的に避けられない。
- 衝突解決方式が正しさを担う。
- 負荷率は性能の状態変数である。
- 期待O(1)には分布仮定がある。
- hash/equality契約を守る。
- 敵対入力を境界で考える。

### 誤解チェック
1. 完全ハッシュは万能か。2. `h(a)=h(b)` ならa=bか。3. open addressingでα>1は可能か。4. 順序検索に適するか。5. 暗号hashなら表でも必ず高速か。

### 基礎問題
1. αを計算せよ。2. chaining挿入を追跡せよ。3. linear probingを追跡せよ。4. 削除で空に戻す誤りを示せ。5. equality契約を書け。

### 応用問題

## 第7章 木

### この章を学ぶ理由
階層、優先度、索引を同じ木の不変条件から理解し、メモリとストレージで表現を変える。

### 現場の問題
偏ったBSTが線形化する、heapを全順序だと思う、DB索引で列順とfan-outを無視する。

### 中心概念と正式定義
木は連結かつ閉路のないグラフ。根付き木では各非根頂点に親が一つ。BSTは左部分木キー `<` ノード `<` 右部分木という不変条件を持ち、高さ `h` の操作は `Θ(h)`。平衡木は `h=Θ(log n)` を保つ。binary heapは親子間の半順序を配列で表しmin抽出 `Θ(log n)`、最小参照 `Θ(1)`。B-treeは高fan-outの多分木でノードをページに合わせ、I/O高さ `Θ(log_B n)` を抑える。

### 直感→図解→数式→例→実装または疑似コード
`root(8) → left(3), right(10)`。完全二分木の高さは `⌊log₂n⌋`。B-treeでfan-out 200、3段なら概算 `200³=800万` の分岐を数回のページI/Oで辿れる。

```text
bst_search(node,k):
  while node != null and node.key != k:
    node = node.left if k < node.key else node.right
  return node
```

### よくある誤解
二分木はBSTとは限らず、BSTは自動で平衡しない。heapの配列は整列済みではない。B-treeとbinary treeのBは同じ意味ではない。

### 実務接続
DOM、AST、scheduler heap、DB B+tree索引に現れる。B+treeは値を葉へ集め葉を連結し範囲走査に向く。

### 要点
- 木は閉路のない連結構造である。
- BST操作は高さに依存する。
- 平衡化は対数高さを維持する。
- heapは最小/最大選択に特化する。
- B-treeはページI/Oを減らす。
- 不変条件を壊さない更新が中心である。

### 誤解チェック
1. BSTは必ずlog nか。2. heapで中央値をO(1)取得できるか。3. inorderはBSTを整列順にするか。4. B+tree葉は範囲走査に向くか。5. fan-outは高さに影響するか。

### 基礎問題
1. 挿入で偏りを示せ。2. inorderを書け。3. heapifyを追跡せよ。4. nから高さを求めよ。5. BST削除三場合を説明せよ。

### 応用問題
1. AVLとred-blackの方針を比較せよ。2. heap構築がΘ(n)である理由を示せ。3. ページサイズからfan-outを見積もれ。

### 設計問題
更新多・範囲検索多の表に対し、複合B+tree索引とページ費用を設計せよ。

### 調査課題
PostgreSQL等のB-tree索引の順序、NULL、並行更新仕様を一次文書で調べよ。

### 知らないとする誤判断

## 第8章 グラフ

### この章を学ぶ理由
依存、接続、経路という異なる現場問題を頂点と辺へ落とし、適切な探索を選ぶ。

### 現場の問題
循環依存でdeployが止まる、重み付き経路にBFSを使う、巨大疎グラフを隣接行列で持つ。

### 中心概念と正式定義
グラフ `G=(V,E)` は頂点集合と辺集合。有向/無向、重み付き/なしを区別する。隣接リスト空間は `Θ(|V|+|E|)`、行列は `Θ(|V|²)`。BFSは非重み付き最短辺数を層ごとに `Θ(V+E)`、DFSは到達・閉路・終了時刻を同じ次数で求める。Dijkstraは非負重みで、priority queue利用時概ね `O((V+E)log V)`。DAGのtopological orderは全辺 `u→v` でuが先の線形順序。

### 直感→図解→数式→例→実装または疑似コード
`A→B→D, A→C→D`。BFS frontierを距離0,1,2と広げる。負辺があると確定済み距離が後から短くなりDijkstra不変条件が壊れる。

```python
from collections import deque
def bfs(g, s):
    dist, q = {s: 0}, deque([s])
    while q:
        u = q.popleft()
        for v in g[u]:
            if v not in dist: dist[v] = dist[u] + 1; q.append(v)
    return dist
```

### よくある誤解
頂点名が階層的でも木とは限らない。DFSは重みなし最短路を保証しない。topological sortの結果は一意とは限らず、閉路があれば存在しない。

### 実務接続
package dependency、workflow、ネットワークrouting、権限継承、障害伝播をモデル化する。モデルの辺の意味と向きがアルゴリズムより先である。

### 要点
- グラフ化では頂点・辺・方向・重みを定義する。
- 疎グラフは隣接リストが自然である。
- BFSは非重み付き最短路を得る。
- DFSは構造探索と閉路検出に向く。
- Dijkstraは負辺を許さない。
- DAGだけがtopological orderを持つ。

### 誤解チェック
1. BFSは全重み付き最短路か。2. DFS木は元グラフと同じか。3. DAGに順序は一つか。4. 行列空間は辺数に比例するか。5. Dijkstraは負閉路だけ避ければよいか。

### 基礎問題
1. API依存をグラフ化せよ。2. BFSを追跡せよ。3. DFSで閉路を検出せよ。4. topological orderを二つ示せ。5. 表現の空間を計算せよ。

### 応用問題
1. 0-1 BFSを説明せよ。2. strongly connected componentsの用途を示せ。3. A*のheuristic条件を調べよ。

### 設計問題
monorepoの増分buildについて、変更影響、循環検出、並列実行順を設計せよ。

### 調査課題
実際のrouting protocol一つが使う最短路モデルと障害収束を調べよ。

### 知らないとする誤判断
アルゴリズムを選んでから、現実を都合のよい辺へ押し込む。

### 次章接続
探索空間が大きいとき、局所選択と部分問題再利用で構造を利用する。

## 第9章 貪欲法と動的計画法

### この章を学ぶ理由
指数的な組合せ探索を、局所選択の安全性または部分問題の再利用によって縮める。

### 現場の問題
最安の選択を繰り返して全体最適だと思う、再帰をmemo化しただけで状態爆発を解決したと思う、状態定義に将来必要な情報が欠ける。

### 中心概念と正式定義
貪欲法は各段階で局所最適な選択を確定し、交換論法やmatroid等により大域最適性を示す。optimal substructureは最適解が部分問題の最適解から構成できる性質。overlapping subproblemsは同じ部分問題が再出現する性質。DPは状態 `s` の値 `F(s)` を漸化式で定義し、memoizationは必要状態をtop-downで、tabulationは依存順にbottom-upで計算する。状態数×遷移数が時間の基本見積りである。

### 直感→図解→数式→例→実装または疑似コード
区間scheduleは終了が最早の仕事を選ぶと交換論法で安全。0/1 knapsackは価値密度greedyが失敗するが、`DP[i,w]=max(DP[i-1,w], DP[i-1,w-w_i]+v_i)` で解ける。

```python
def coin_change(coins, amount):
    dp = [0] + [float("inf")] * amount
    for x in range(1, amount + 1):
        dp[x] = min((dp[x-c] + 1 for c in coins if c <= x), default=float("inf"))
    return dp[amount]
```

### よくある誤解
局所最適は一般に大域最適でない。DPは再帰の別名ではなく、状態と依存DAGの評価である。memoizationでも到達状態数が指数なら指数時間である。

### 実務接続
interval scheduling、差分計算、rate plan、resource allocation、compiler最適化に現れる。厳密最適が必要かも仕様で確認する。

### 要点
- greedyには選択の安全性の証明が要る。
- DPにはoptimal substructureと重複がある。
- 状態は将来を決める十分な情報を持つ。
- 漸化式、初期値、計算順を分ける。
- 時間は状態数×遷移数で見積もる。
- 解復元には選択を記録する。

### 誤解チェック
1. 最小を選び続ければ最小になるか。2. memo化は常に多項式時間か。3. 状態を減らせば正しさは自動か。4. tabulationに依存順は必要か。5. optimal substructureだけでDPに向くか。

### 基礎問題
1. Fibonacciを両方式で書け。2. coin例でgreedy反例を作れ。3. interval greedyを追跡せよ。4. knapsack表を埋めよ。5. 状態数を数えよ。

### 応用問題
1. 編集距離を定式化せよ。2. rolling arrayで空間を削減せよ。3. greedy交換論法を書け。

### 設計問題
クラウドjobを期限・価値・容量制約下で配置する。厳密解/近似/online方針を分けよ。

### 調査課題
実用solverまたは標準ライブラリで、DP・greedyが使われる箇所をコードから確認せよ。

### 知らないとする誤判断
局所的に最も安い選択を「直感的に最適」と承認する。

## 第10章 分割統治

### この章を学ぶ理由
分割、再帰解決、統合という設計を、再帰木と漸化式から費用予測する。

### 現場の問題
再帰だから速いと思う、分割が偏り最悪化する、細かく分け過ぎて呼出し・通信費が支配する。

### 中心概念と正式定義
divide and conquerはサイズnの問題をa個のサイズ約`n/b`へ分け、各々を解き、`f(n)`で統合する。漸化式 `T(n)=aT(n/b)+f(n)`。Master theoremの核は、葉総仕事 `n^{log_b a}` と各層の統合仕事を比較すること。`f` が小さければ葉支配、同程度なら層数`log n`が掛かり、大きければ根側支配（正則条件等の前提あり）。

### 直感→図解→数式→例→実装または疑似コード
再帰木は `n → a個のn/b → … → 1`、深さ `log_b n`。merge sortは各層Θ(n)がlog n層でΘ(n log n)。binary searchは `T(n)=T(n/2)+Θ(1)=Θ(log n)`。

```text
solve(x):
  if small(x): return direct(x)
  parts = divide(x)
  return combine(map(solve, parts))
```

### よくある誤解
Master theoremはすべての漸化式に使えない。部分問題が重複するならDPが適する場合がある。並列化可能性と高速化は、統合・帯域・粒度に制約される。

### 実務接続
parallel reduction、map-reduce、画像処理、空間索引に現れる。閾値以下を反復実装に替えるのは、モデルの定数項を改善する設計である。

### 要点
- 分割・解決・統合を別責務にする。
- 漸化式は費用の構造を表す。
- 再帰木で層ごとの仕事を見る。
- 葉仕事と統合仕事を比較する。
- 偏った分割は深さを増やす。
- 並列化にはcritical pathがある。

### 誤解チェック
1. 再帰なら分割統治か。2. `T(n)=2T(n/2)+n` は線形か。3. Master theoremは不均等分割へそのまま使えるか。4. 部分問題重複は望ましいか。5. 無限に細分化すれば並列高速化するか。

### 基礎問題
1. 三つの漸化式を再帰木で解け。2. merge sortを追跡せよ。3. base case欠落を分析せよ。4. quicksortの偏りを描け。5. 空間深さを求めよ。

### 応用問題
1. Karatsubaの次数を求めよ。2. 最大部分配列を設計せよ。3. work/spanを計算せよ。

### 設計問題
1TBログ集約を単一機・並列機・分散機で分割し、統合、skew、障害を比較せよ。

### 調査課題
実用並列frameworkの分割粒度とwork stealingを一次文書で調べよ。

### 知らないとする誤判断
タスク数を増やせば比例して速くなると考え、critical pathと統合費を無視する。

### 次章接続

## 第11章 NPと計算困難性

### この章を学ぶ理由
解法が見つからない状況を能力不足と即断せず、問題の分類、入力規模、必要保証から戦略を選ぶ。

### 現場の問題
厳密な最適scheduleを一般入力で即時要求する、NPを「非多項式」と読む、検証しやすさと探索しやすさを混同する。

### 中心概念と正式定義
決定問題についてPは決定性計算モデルで多項式時間に解ける言語、NPはyes証明書を多項式時間で検証できる言語（同値に非決定性多項式時間）。多項式時間many-one reduction `A≤pB` は、`x∈A ⇔ f(x)∈B` となる多項式時間関数f。BがNP内で、全NP問題がBへ還元できればNP-complete。NP-hardはNP内を要求しない。`P⊆NP` だが `P=NP` は未解決である。

### 直感→図解→数式→例→実装または疑似コード
`既知困難A → 変換f → 候補B`。Bを速く解ければAも速く解けるので、A≤pBはBが少なくともA程度に難しい。SATの割当は代入すれば速く検証できる。

```text
verify_clique(G, vertices, k):
  check |vertices|=k and every pair has an edge  # polynomial verification
```

### よくある誤解
NPは「解けない」「指数時間と証明済み」ではない。実数最適化や停止問題を雑にNP-hardと呼ばない。小規模・特殊構造なら厳密解は実用的である。

### 実務接続
配送、割当、配置、SAT/SMT、テスト組合せで、入力のパラメータ、制約構造、近似許容度を明示する理由になる。

### 要点
- P/NPは決定問題の計算量クラスである。
- NPは証明書を速く検証できる。
- 還元の向きが困難性を伝える。
- NP-completeはNPかつNP-hardである。
- P対NPは未解決である。
- 特殊ケースと実用規模は別に評価する。

### 誤解チェック
1. NPはnon-polynomialの略か。2. P問題はNPにも入るか。3. A≤pBならAがBより難しいか。4. NP-hardは決定問題だけか。5. NP-completeなら近似も不可能か。

### 基礎問題
1. 探索問題を決定版へ直せ。2. 証明書を定義せよ。3. 還元の向きを説明せよ。4. P,NPの包含を描け。5. 小規模総当たり回数を計算せよ。

### 応用問題
1. vertex coverとindependent setの関係を示せ。2. parameterized complexityを調べよ。3. pseudo-polynomialの意味を説明せよ。

### 設計問題
シフト割当について、厳密最適、時間制限付きsolver、近似、人手介入の契約を設計せよ。

### 調査課題
SAT/SMTまたはMIP solverの停止条件、最適性gap、証明出力を一次資料で調べよ。

### 知らないとする誤判断
一般問題の厳密最適解をSLA内で必須にし、保証の緩和を設計しない。

### 次章接続
困難な問題に対し、近似保証・経験則・乱択を使い分ける。

## 第12章 近似・ヒューリスティクス

### この章を学ぶ理由
厳密解が高価なとき、品質・時間・再現性の契約を明示して有用な解を返す。

### 現場の問題
heuristicの成功例だけを示す、乱数seedを記録しない、近似比と経験的品質を混同する。

### 中心概念と正式定義
最小化問題のρ-approximationは全入力で `ALG(I)≤ρ·OPT(I)`（ρ≥1）を保証する。最大化では `ALG(I)≥OPT(I)/ρ`、同値に `OPT(I)/ALG(I)≤ρ` と定める（目的値が非負など問題固有の前提を明記する）。heuristicは通常そのような全入力保証を持たない経験則。randomized algorithmは乱数を計算過程に使い、Las Vegas型は常に正しいが時間が確率的、Monte Carlo型は時間を抑え誤り確率を許す。期待値だけでなくtailも契約する。

### 直感→図解→数式→例→実装または疑似コード
最適値100に対し2-近似の最小化解は最大200を保証する。randomized quicksortはpivotを乱択し固定入力に対する期待 `Θ(n log n)` を得る。

```text
randomized_select(A,k):
  pivot = uniform_choice(A)
  partition; recurse only into part containing k
```

### よくある誤解
近似は雑、heuristicはAI、乱択は非決定的でテスト不能、ではない。保証対象、確率空間、seed、予算を明示すれば工学的契約になる。

### 実務接続
検索ranking、cache eviction、query optimizer、経路計画で使う。品質metricが利用目的とずれると高速でも失敗する。

### 要点
- 近似には解品質の数学的保証がある。
- heuristicは経験的評価を要する。
- 乱択の期待は乱数に関する期待である。
- seedと入力を記録し再現可能にする。
- time budgetとbest-so-farを設計する。
- 品質・時間・失敗確率を同時に測る。

### 誤解チェック
1. 2-近似は最適値との差が2か。2. heuristicに保証は不要か。3. Monte Carloは必ず正しいか。4. seed固定だけで分布試験になるか。5. 期待時間はp99を保証するか。

### 基礎問題
1. 近似比を計算せよ。2. 二方式を分類せよ。3. seed再現を実装せよ。4. confidence intervalを設計せよ。5. budget超過時を定義せよ。

### 応用問題
1. set cover greedyの比を調べよ。2. reservoir samplingを証明せよ。3. simulated annealing評価を設計せよ。

### 設計問題
推薦候補生成について品質metric、時間予算、fallback、乱数、online検証を設計せよ。

### 調査課題
実用DB query optimizerの探索空間制限とcost modelを一次資料で調べよ。

### 知らないとする誤判断
「だいたい良い」を測定可能な品質契約へ翻訳せず本番化する。

### 次章接続
複数資源と階層を持つ現実のシステムへ計算量を接続する。

## 第13章 現実のシステムと計算量

### この章を学ぶ理由
RAMモデルだけで終えず、I/O、cache、通信、serialization、fan-outを含む階層的費用モデルを作る。

### 現場の問題
O(log n)のDB検索が遅い、N+1 APIが小規模テストを通る、cache導入でtail latencyが悪化する。

### 中心概念と正式定義
外部記憶モデルではblock size B、memory Mを使いI/O回数を数える。ネットワークでは仕事 `W`、critical path `S`、通信量、round tripを分ける。Amdahl則は直列割合s、並列度pでspeedup `≤1/(s+(1-s)/p)`。cache期待時間は単純化すれば `E[T]=hT_hit+(1-h)T_miss` だが、相関・stampede・tailを別に扱う。分散fan-out kで各下流が99%成功でも独立仮定なら全成功は `.99^k`。

### 直感→図解→数式→例→実装または疑似コード
`API → k services → DB index → pages` と層別に費用を足す。N件で個別queryなら往復 `N·L`、batchなら `L+transfer(N)`。

```text
cost = cpu_ops*c_cpu + page_reads*c_io + round_trips*latency + bytes/bandwidth
```

### よくある誤解
漸近次数が同じなら実装差は小さい、cache hit率だけ高ければよい、水平分割で計算量が消える、はいずれも誤りである。

### 実務接続
DB索引、search engine倒立索引、filesystem page cache、CDN、map-reduce、pagination契約を一つの費用表でレビューする。

### 要点
- 費用尺度を層ごとに定義する。
- I/Oはblock単位で数える。
- RTTは小操作を支配し得る。
- Amdahl則が直列部分の上限を示す。
- cacheはmissとtailも測る。
- fan-outは費用と失敗を増幅する。

### 誤解チェック
1. O(log n)ならネットワーク越しでも速いか。2. hit率99%ならp99はhitか。3. shard数倍で無限に速くなるか。4. batchは常にメモリ安全か。5. 全下流成功率は各成功率と同じか。

### 基礎問題
1. N+1のRTTを計算せよ。2. cache期待時間を求めよ。3. Amdahl速度向上を求めよ。4. B-tree I/O高さを概算せよ。5. fan-out成功率を求めよ。

### 応用問題
1. tail-at-scaleをモデル化せよ。2. skewしたshardを分析せよ。3. bloom filterのI/O削減を評価せよ。

### 設計問題
検索APIに対しCPU/I/O/通信/メモリ予算、劣化時の返却契約、観測指標を設計せよ。

### 調査課題
一つのDBの`EXPLAIN` cost modelと実測値の関係を一次文書・実験で調べよ。

### 知らないとする誤判断
単一のBig-Oラベルで、階層的なボトルネックをすべて説明したと思う。

### 次章接続
費用モデルを使い、成長で破綻したシステムを因果的に分析する。

## 総合演習B（第9〜13章）

配送計画APIが厳密solver、DB、32 shard、cacheから成る。件数増加後にタイムアウトと解品質低下が同時発生した。NP困難性、近似保証、DP状態数、分割のskew、cache miss、fan-out成功率を仮説の優先順に並べる。各反証metric、入力縮約、品質SLO、time budget、fallbackを含む実験計画を作れ。

## 第14章 ケーススタディ――重複排除サービスの破綻

### この章を学ぶ理由
「最初は動いた」を、入力・不変条件・費用・資源の変化に分解して再発防止へ結ぶ。

### 現場の問題
初期実装は受信済みIDをPython listに保存し、各イベントを線形検索した。件数が10万倍になりCPU飽和、再起動時に全再読込、無制限保持でOOM、timeout retryで流量が増幅した。

### 中心概念と正式定義
1件当たり探索Θ(n)、n件処理の総費用 `Σ_{i=0}^{n-1}Θ(i)=Θ(n²)`。hash setなら期待総費用Θ(n)だが、永続性、TTL、負荷率、敵対キーの契約が必要。近似重複判定としてBloom filterはm bit、k hash、n要素で偽陽性率およそ `(1-e^{-kn/m})^k`、偽陰性なし（通常の追加のみモデル）。

### 直感→図解→数式→例→実装または疑似コード
`受信→dedup→処理→commit→ack` の順序を描くと、データ構造だけでなくcrash windowが見える。CPU改善後も無期限集合は空間Θ(n)で破綻する。

```text
on_event(e):
  atomically:
    if durable_keys.contains(e.id): return DUPLICATE
    apply_business_effect(e)
    durable_keys.put(e.id, expires_at)
```

### よくある誤解
listをsetへ変えるだけでは、期限、durability、原子性、false positiveの仕様は直らない。retry停止は原因ではなく可用性を落とすだけの症状対策である。

### 実務接続
idempotency key、message consumer、決済webhook、ETL checkpointに現れる。algorithm、DB transaction、distributed delivery semanticsを横断する。

### 要点
- 総費用は一件費用の累積で見る。
- 時間改善後の空間増加も評価する。
- dedupの期間は業務仕様である。
- crash pointごとの不変条件を定義する。
- retryは負荷を増幅し得る。
- 近似構造は誤りの方向を契約する。

### 誤解チェック
1. set化だけでexactly-onceになるか。2. TTLは純粋な性能値か。3. Bloom filterに偽陰性があるか。4. ack順序は正しさに無関係か。5. CPUが下がれば容量問題は完了か。

### 基礎問題
1. 二乗総費用を導出せよ。2. 空間を見積もれ。3. crash点を列挙せよ。4. retry増幅を計算せよ。5. TTL境界を定義せよ。

### 応用問題
1. Bloom filterのパラメータを求めよ。2. hash adversaryを検討せよ。3. LSM/B-treeを比較せよ。

### 設計問題
決済webhookの重複排除を、保持期間、障害、監査、容量、再処理まで設計せよ。

### 調査課題
実在message systemの再配信・offset commit契約を一次文書で調べ、本ケースへ適用せよ。

### 知らないとする誤判断
profileで最も熱い行だけ直し、破綻を生む不変条件と成長モデルを放置する。

### 次章接続
本書全体を使う設計レビュー演習へ進む。

## 第15章 総合演習――設計レビュー

### この章を学ぶ理由
問題名が与えられない現実で、モデル選択、正しさ、費用、検証を一つの判断へ統合する。

### 現場の問題
レビューが「好みの構造」「過去の成功例」「単一ベンチマーク」の応酬になり、反証可能な仮説がない。

### 中心概念と正式定義
レビュー対象を `(仕様, 入力分布, 不変条件, アルゴリズム, 資源モデル, 失敗モデル, 観測)` の七つ組として表す。可行設計は全正当性と資源上限を満たし、最適設計は明示した目的関数と制約に相対的である。

### 直感→図解→数式→例→実装または疑似コード
`要求→モデル→候補→証明/反例→費用上界→実測→決定`。レビューではまず入力軸n,m,kと上限を表にし、候補ごとに時間・空間・I/O・品質を埋める。

```text
review(design):
  assert specification and invariants
  enumerate growth axes and adversarial inputs
  derive costs; test crossover points
  record decision and invalidation signals
```

### よくある誤解
正解のアルゴリズムが一つある、Big-Oが小さい候補を自動選択できる、benchmarkが証明を置換する、ではない。

### 実務接続
ADR、capacity planning、load test、incident reviewへ直結する。撤回条件を記録すると、データ分布が変わったとき再判断できる。

### 要点
- 仕様を費用より先に固定する。
- 入力軸と分布を明示する。
- 不変条件で正しさを検討する。
- 多資源費用を比較する。
- 敵対入力とcrossoverを試験する。
- 決定の撤回条件を残す。

### 誤解チェック
1. Θが小さい候補が常に最適か。2. 平均には分布が必要か。3. load testだけで上界が分かるか。4. 近似品質は性能と別契約か。5. 撤回条件は設計の一部か。

### 基礎問題
1. 七つ組を一例で埋めよ。2. 入力軸を三つ挙げよ。3. 不変条件を書け。4. 費用表を作れ。5. 反例を一つ作れ。

### 応用問題
1. crawler frontierを設計レビューせよ。2. top-k集約を単一/分散で比較せよ。3. rate limiterを解析せよ。

### 設計問題
次の三件をレビューせよ。(a) 10億URLのcrawl、(b) 期限付きjob scheduler、(c) 複合条件検索。各々で代替案三つ、正しさ、計算量、容量、障害、検証を示せ。

### 調査課題
実在OSSの性能ADRまたはissueを一件選び、暗黙の入力モデルと撤回条件を復元せよ。

### 知らないとする誤判断
技術名の比較でレビューを終え、問題構造と制約の比較をしない。

### 次章接続
最後に、知識が欠けたとき生じる誤判断を優先度順に再点検する。

## 第16章 この分野を知らないエンジニアが陥りやすい誤判断

### この章を学ぶ理由
頻出する誤判断を症状でなく背後の仮説と結び、設計レビューの早期警戒表にする。

### 現場の問題
性能障害は複数要因が連鎖するため、簡単な修正順でなく、確率と影響の高い原因仮説から反証する必要がある。

### 中心概念と正式定義
誤判断とは、前提・モデル・保証範囲のどれかを暗黙にした推論である。以下は優先度順の「Countermeasure: 作業（assumed cause）」であり、自分の状況に合う原因かを先に検証する。

### 直感→図解→数式→例→実装または疑似コード
`観測→原因仮説→反証metric→構造的対策→回帰境界`。単なる高速化ではなく、費用 `C(n)`、容量上限、正しさ不変条件を同じレビュー票へ置く。

1. Countermeasure: 入力サイズごとの増加曲線を測る（assumed cause: 小規模実測を将来性能へ外挿している）。
2. Countermeasure: 総費用を導出し二重走査を索引化する（assumed cause: 一件O(n)をn件実行している）。
3. Countermeasure: 前提・事後条件と不変条件を書く（assumed cause: テスト例を正しさの定義にしている）。
4. Countermeasure: 時間・空間・I/O・通信を別計上する（assumed cause: CPU計算量だけを費用としている）。
5. Countermeasure: 平均の入力分布を記録する（assumed cause: 「平均O(1)」を無条件保証と読んでいる）。
6. Countermeasure: 最悪入力と敵対入力を試す（assumed cause: 利用者が入力を制御できる境界を無視している）。
7. Countermeasure: 構築・更新費を含める（assumed cause: 検索の速さだけで索引を選んでいる）。
8. Countermeasure: bounded queueと過負荷契約を設ける（assumed cause: 無制限bufferを可用性と誤認している）。
9. Countermeasure: hash負荷率・resize・衝突を観測する（assumed cause: dictionaryを最悪O(1)と見なしている）。
10. Countermeasure: 木の高さを保つ方式を選ぶ（assumed cause: treeという名称だけでO(log n)と判断している）。
11. Countermeasure: 二分探索の単調述語と境界を証明する（assumed cause: 中央比較だけで成立すると考えている）。
12. Countermeasure: sortの安定性とtie-breakerを仕様化する（assumed cause: 同値要素の順序を未定義にしている）。
13. Countermeasure: 外部記憶アルゴリズムを選ぶ（assumed cause: 全入力がRAMに入ると仮定している）。
14. Countermeasure: greedyの交換論法か反例を示す（assumed cause: 局所最適を全体最適だと推測している）。
15. Countermeasure: DPの状態数×遷移数を数える（assumed cause: memo化すれば常に速いと思っている）。
16. Countermeasure: NP困難性と特殊構造を分類する（assumed cause: 一般厳密最適を短いSLAで要求している）。
17. Countermeasure: 近似比または品質metricを契約する（assumed cause: heuristicの「良さ」を逸話で評価している）。
18. Countermeasure: work/spanと直列部分を測る（assumed cause: core数に比例して高速化すると考えている）。
19. Countermeasure: RTTとbatch sizeをモデル化する（assumed cause: remote callを関数呼出しと同じ費用で数えている）。
20. Countermeasure: fan-outのtailと全成功率を計算する（assumed cause: 各下流の平均だけを見ている）。
21. Countermeasure: cache miss時とstampedeを負荷試験する（assumed cause: hit率だけでcacheを評価している）。
22. Countermeasure: データskewを再現する（assumed cause: 一様分布でshard負荷を見積もっている）。
23. Countermeasure: randomized処理のseedと分布試験を保存する（assumed cause: 一回の成功を確率保証と混同している）。
24. Countermeasure: n以外のm,k,bit長も入力軸にする（assumed cause: 件数だけが規模だと考えている）。
25. Countermeasure: 最適化の撤回条件をADRへ残す（assumed cause: 現在の分布が恒久的だと考えている）。
26. Countermeasure: 数値表現とoverflow境界を検証する（assumed cause: 数学上の整数と機械整数を同一視している）。
27. Countermeasure: 反復順依存を削除する（assumed cause: hash containerの偶然の順序を契約だと思っている）。
28. Countermeasure: 再帰深さと明示stackを比較する（assumed cause: 漸近時間が同じなら実行可能だと考えている）。
29. Countermeasure: amortized worst spikeをSLOへ照合する（assumed cause: 償却O(1)なら各操作もO(1)と思っている）。
30. **rare** Countermeasure: 計算モデル自体を見直す（assumed cause: 巨大定数、非一様hardware、量子/特殊acceleratorでRAMモデルが判断を逆転させる）。

### よくある誤解
この一覧を機械的checklistにするのも誤りである。まず観測から高確率仮説を選び、反証可能にする。

### 実務接続
設計レビュー、capacity planning、障害対応、ADRに各項目を「仮説・証拠・対策・撤回条件」として埋める。

### 要点
- 増加率と定数を順に評価する。
- 正しさと性能を分けて証明する。
- 前提を明示して保証を読む。
- 複数資源とtailを扱う。
- 高確率原因から反証する。
- 対策は構造と回帰境界へ落とす。

### 誤解チェック
1. 一覧上位が常に自分の原因か。2. O記法だけで容量を決められるか。3. worstだけ測れば分布は不要か。4. metricなしのheuristicを比較できるか。5. 対策後の撤回条件は不要か。

### 基礎問題
1. 自案件の誤判断を三つ選べ。2. 各原因の反証metricを書け。3. 費用関数を一つ導出せよ。4. 敵対入力を作れ。5. ADR撤回条件を書け。

### 応用問題
1. 性能事故をこの分類で再分析せよ。2. 二つの原因が連鎖する因果図を作れ。3. rare仮説を上げる証拠を定義せよ。

### 設計問題
新規APIについて30項目から関連する上位5仮説を選び、設計・試験・観測へ落とせ。

### 調査課題
公開障害報告を一件読み、報告されたcountermeasureが根本原因と一致するか検証せよ。

### 知らないとする誤判断
誤判断一覧を暗記し、問題ごとのモデル化を省略する。

離散数学、OS、DB、並行分散へ進み、本書の費用モデルをそれぞれの不変条件と結び付ける。

## 付録　専門家の思考を測る

### 専門家が共有する5つの中核的メンタルモデル

1. **不変条件と状態遷移** 直感的には、アルゴリズムとは「各手順の後にも壊れてはいけない約束」を保ちながら、入力を目的の状態へ動かす過程である。正式には、事前条件から初期不変条件を示し、各遷移がそれを保存することと、停止時に不変条件から事後条件が導けることを証明する。実務では、実装より先に不変条件を書き、境界値テスト、並列化の可否、障害後の再開地点を判断する。
2. **入力族に対する資源増加率** 直感的には、一回の計測値でなく「入力が10倍になったとき、何が何倍になるか」を見る。正式には、入力サイズを一変数 `n` に潰さず、頂点数と辺数、件数とキー長、RAMとI/O回数などを分け、最悪・平均・償却のどの量を評価しているか明記する。実務では、SLO、容量上限、データ分布、ネットワーク往復を同じ費用モデルへ置き、最適化の対象と撤回条件を決める。
3. **問題構造から状態空間を選ぶ** 直感的には、解法名を思い出す前に「何を区別して覚えれば、残りの判断に十分か」を問う。正式には、最適部分構造、単調性、交換可能性、グラフ構造などを見つけ、状態・遷移・目的関数として表現するか、既知問題へ帰着する。実務では、DPの状態爆発、greedyの誤適用、不要に一般的な解法を避け、制約に合う最小の表現を選ぶ。
4. **反例・敵対者・下界** 直感的には、うまくいく例を増やすより、主張を壊す最小入力と、アルゴリズムにとって最も不利な情報の与え方を探す。正式には、比較回数や必要情報量の下界、敵対入力、帰着による困難性を用いて「改善できない理由」と保証範囲を区別する。実務では、性能目標が実現可能かを早期に判定し、攻撃入力、偏り、最悪遅延に対する試験と防御を設計する。
5. **保証と不確実性の交換** 直感的には、常に厳密最適を求めるのでなく、時間・空間・解品質・失敗確率のどれをどこまで交換できるかを決める。正式には、近似比、期待計算量、高確率保証、償却計算量など、単発の結果ではなく入力族や試行に対する契約として表す。実務では、締切のある最適化、stream処理、cacheやrandomized data structureで、品質metricと悪化時のfallbackを明文化する。

### 専門家の意見が根本的に分かれる3つの論点

1. **保証中心の設計か、分布中心の適応か**
   - **立場A――最悪時保証を設計の中心に置く。** 最も強い主張は、入力分布は変化し、利用者や攻撃者が入力を選べるため、過去の平均値だけではSLOや安全性を契約できないというものだ。証明可能な上界は、未知の将来にも持ち越せる数少ない根拠になる。
   - **立場B――実分布に適応した期待性能を中心に置く。** 最も強い主張は、極端に稀な入力のために通常ケースへ恒常的な費用を課すと、有限資源のシステム全体ではかえって利用者価値を下げるというものだ。分布を継続観測し、適応・randomization・fallbackを組み合わせれば、保証一辺倒より高い実効性能を得られる。
   - 判断は、入力を誰が制御するか、tail SLO、誤差や停止の損失、分布変化を検知する速さ、fallbackの有無で変わる。
2. **汎用的な抽象アルゴリズムか、計算機階層に特化した実装か**
   - **立場A――抽象的な計算量と再利用可能性を優先する。** 最も強い主張は、機種依存の最適化より正しさを監査しやすく、入力規模や実行環境が変わっても性能の劣化理由を説明でき、保守期間全体の費用を抑えられるというものだ。
   - **立場B――cache、SIMD、分岐予測、I/O単位まで含むhardware-aware設計を優先する。** 最も強い主張は、現実の律速資源はRAMモデルの一命令ではなくデータ移動であり、漸近的に優れた解法が対象規模では一貫して遅いこともあるというものだ。レイアウトやbatch化は単なる定数倍でなく、実行可能性を左右する。
   - 判断は、対象規模、platformの固定期間、portable性、性能余裕、測定可能性、実装を維持できる組織能力で変わる。
3. **厳密最適解を求めるか、近似・heuristicを製品上の答えとするか**
   - **立場A――解の最適性または明示的な近似保証を要求する。** 最も強い主張は、評価関数が同じなら、無保証heuristicの成功例は未知入力での品質を何も約束せず、重要な配分や検証可能性を任せられないというものだ。
   - **立場B――制限時間内の実用解と反復改善を優先する。** 最も強い主張は、現実の目的関数自体が不完全かつ変動し、NP困難な一般問題で厳密解を待つことは「解なし」と同じであるため、測定可能なheuristicと人間のfeedbackの方が総効用を高めるというものだ。
   - 判断は、最適性の価値、誤差の非対称性、計算期限、instanceの特殊構造、品質をonline評価できるか、再計算や人手修正が可能かで変わる。

### 深い理解と暗記を見分ける10の質問

1. 平均では高速な検索方式が本番の一部tenantだけで遅くなった。入力分布と敵対性についてどの仮定が壊れた可能性があるかを列挙し、競合仮説を識別する観測を設計せよ。
2. 「このloopは `O(n)`」という主張に対し、要素比較の費用、I/O、出力サイズが入力とともに変わる反例を作り、より適切な多変数の費用関数を書け。
3. あるgreedy解法が多数のテストを通った。交換論法を組み立てるか最小反例を系統的に探すには、問題のどの構造を調べるべきか説明せよ。
4. 同じ漸近計算量の二実装で性能が逆転した。cache locality、allocation、branch、parallelismを原因候補として、測定順と採用判断の撤回条件を示せ。
5. 償却 `O(1)` の操作をp99 5msのAPIで使ってよいか。単発のspikeを隠さず、償却保証から運用上の判断を導くために追加で必要な情報を述べよ。
6. 厳密解が期限に間に合わない配車問題について、近似比を持つ方法と経験的heuristicをどう比較するか。目的関数の欠陥も含め、品質契約とfailure時の扱いを設計せよ。
7. randomized algorithmを一度の固定seedで検証することが不十分な理由を説明し、再現性と確率的保証を同時に検査する試験を提案せよ。
8. memoryを増やせば速くなるDPが、ある規模からシステム全体を遅くする事例を構成せよ。状態表、working set、page fault、代替表現の関係を説明せよ。
9. 既知の問題へ帰着できることを示しただけでは、実用的な解法が得られない場合がある。帰着の向き、instanceサイズの増加、定数を使って反例を示せ。
10. 新しい高速アルゴリズムの採用ADRを書くなら、正しさ、性能、入力仮定、障害時のfallback、観測metric、撤回条件をどう結び付けるか。互いに矛盾する条件を一つ含む事例で説明せよ。
