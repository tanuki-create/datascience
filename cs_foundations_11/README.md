# CS基礎11分野――実務エンジニアのための体系的教科書

情報学部・情報工学科で体系的に学ぶ機会がなかった実務エンジニアのための、11冊の教科書セットである。目的は固有製品の操作を覚えることではない。未知の技術や障害に出会ったときに、問題の種類、参照すべき学問領域、検証すべき仮説を判断できるようになることである。

## 学び方

完全な直列学習にはしない。各冊を4〜6章進めた時点で、次の横断経路を往復する。

```text
離散数学 ──証明/関係──> アルゴリズム ──探索/index──> DB
   │                         │                        │
   └─論理/型──> 言語論 ──実行資源──> OS ──永続化──┘
                   │             │                    │
                   └─文法──> オートマトン       並行・分散
                                                │      │
確率・統計 <──障害率/推定──────────────────────┘      │
     │                                                 │
    HCI <──human error/trust──> Security <──変更管理──> Software Engineering
```

おすすめの一週間の単位は「本文1章→章末の誤解チェック→基礎2問→応用1問→実務の一事例へ適用」である。全問を一度に解くより、自分のsystemの設計判断へ写像する。

## 全冊共通の章構造

各章は次の学習loopを持つ。

1. 現場で遭遇する問題と、この章を学ぶ理由
2. 素朴な理解では説明できない点
3. 中心概念、正式な定義、図解、数式
4. codeまたは疑似codeと具体例
5. よくある誤解、現実のsystemとの接続、限界
6. 要点、誤解チェック、基礎・応用・設計問題、調査課題
7. 知らない場合の誤判断と次章への接続
8. 巻末付録「専門家の思考を測る」――5つの中核的メンタルモデル、steelmanした3つの論争、暗記では答えられない10の質問

各冊の最終章は「この分野を知らないエンジニアが陥りやすい誤判断」を20例以上扱う。章末問題は暗記ではなく、説明、計算、code読解、bug解析、設計判断、障害分析を混ぜている。

## 横断演習の使い方

「DBが遅い」のような現象を一分野だけで解かない。

| 視点 | 問うこと |
|---|---|
| Algorithms | 入力sizeと演算量はどう増えるか。indexやcacheで構造は変わるか |
| OS | on-CPU、run queue、page fault、block/network I/Oのどこで待つか |
| Database | query plan、lock/MVCC、WAL、buffer、replicationのどこか |
| Concurrency/Distributed | contention、retry、partial failure、consistency要求は何か |
| Probability | 平均か分位点か。sample bias、分散、変化の不確実性は何か |
| HCI/Software Engineering/Security | 運用者の判断、変更経路、権限・攻撃surfaceが増幅していないか |

対策案は、容易さでなく原因仮説の優先順に並べる。記述形式は `Countermeasure: 実施する作業（assumed cause: 想定原因）` とし、観測で反証できるようにする。極端に稀な仮説は `rare` と明示して下位へ置く。

## 成果物の検証

構造検査は次で実行する。

```bash
python3 tools/verify_books.py
```

検査はREADMEから11冊へのlocal link、11ファイルの存在、章番号の連続性、指定章数、最終誤判断章、章末workの必須label、基礎5問・応用3問の各section内での下限、総合演習、巻末付録の5/3/10項目と最終配置を確認する。内容の正確性は構造検査では保証できないため、分野横断レビューと一次資料への調査課題を併用する。

## 2040年代にも残すもの

言語、cloud、framework、製品名は例として使う。残すべきものは、不変条件、状態遷移、計算量、資源待ち、整合性、failure model、統計的推論、human limitation、変更可能性、trust boundaryである。新技術を見たら、機能一覧より先に「どの古い問題へ、どの新しい制約と保証を与えたか」を問う。
