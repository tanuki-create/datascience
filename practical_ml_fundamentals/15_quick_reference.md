# 15. 現場判断の早見表

## 現場の問い

実務では、毎回すべての理論を思い出す時間はありません。異常な数字、壊れた学習、説明できない予測が出たとき、最初にどこを見るかを素早く決める必要があります。

## 直感

ML の問題は、モデルだけで起きるわけではありません。データ、前処理、分割、評価指標、閾値、運用、インフラのどこでも起きます。症状から原因候補を並べ、安い確認から潰すのが現場の基本です。

## 最小限の数式

本番判断では、単一指標ではなく損失を分解します。

```text
total_risk = model_error + data_risk + operation_cost + maintenance_risk
```

数式として厳密に計算するというより、見落としを防ぐチェックリストとして使います。

## 実装で見るべきログ・指標

- 入力件数、欠損率、スキーマ違反、カテゴリ増加。
- train / validation / test / production の分布差。
- 予測スコア分布、閾値別の対象件数。
- セグメント別 precision / recall / error rate。
- モデル、前処理、特徴量、閾値、prompt のバージョン。
- レイテンシ、エラー率、リトライ、コスト。

## よくある失敗

- モデルを疑う前にデータを確認しない。
- 平均指標だけで、重要 slice を見ない。
- notebook の前処理と本番前処理がずれる。
- 閾値や prompt をコード外で変更し、記録しない。
- 失敗例を分類せず、対策が毎回場当たりになる。

## 実務メモ

問題発生時は「最後に変わったもの」を探します。上流データ、ラベル、特徴量、閾値、モデル、ライブラリ、インフラ、業務ルールの変更履歴を追える状態にしておくと、復旧が速くなります。

## 最初に疑う順

| 症状 | 最初に見る場所 |
|---|---|
| 精度が急に落ちた | 入力データ、スキーマ、欠損、期間 |
| validation は良いが本番で悪い | 分割設計、分布差、train/serve skew |
| accuracy は高いが苦情が多い | 指標選定、見逃し/誤検知コスト、重要 slice |
| 学習 loss が下がらない | 前処理、ラベル、learning rate、実装 |
| train だけ良い | 過学習、リーク、正則化不足、データ量 |
| 予測が一部カテゴリで落ちる | rare category、未知値処理、セグメント評価 |
| LLM 回答がもっともらしく間違う | 検索品質、根拠制約、評価セット、拒否設計 |
| 生成画像の品質が安定しない | seed、prompt、sampling、条件付け、評価基準 |

## モデル選定の目安

| 状況 | 最初の候補 |
|---|---|
| 少量の表データ | 線形モデル、決定木、Random Forest |
| 表データで精度重視 | Gradient Boosting 系 |
| 説明責任が強い | 線形モデル、浅い木、ルール併用 |
| 画像 | 事前学習 CNN / Vision Transformer の転移学習 |
| テキスト分類 | TF-IDF + 線形モデル、または小型 Transformer |
| 検索・類似度 | embedding + vector search |
| 文書回答 | RAG + 評価セット + 人手確認 |
| 画像生成 | 条件付き生成 + 安全・権利レビュー |

## やってはいけない近道

- test set を見ながらチューニングする。
- 推論時に取れない特徴量で学習する。
- 平均指標だけでリリース判断する。
- LLM の出力を検証なしに正解データへ戻す。
- prompt、閾値、前処理を版管理しない。
- 失敗例を見ずに精度表だけで報告する。

## 最小チェックリスト

- 問題設定は 1 ページで説明できる。
- ベースラインがある。
- 分割方法が本番利用を模擬している。
- 重要 slice の評価がある。
- 前処理とモデルが一体で保存される。
- 実験 ID、データ版、コード版、seed が残る。
- 誤りパターンに名前が付いている。
- リリース条件と停止条件がある。
- 監視対象がデータ、予測、業務 KPI に分かれている。

## 演習

1. 自分の案件で「精度が急落した」と仮定し、最初の 30 分で確認するログを順番に並べる。
2. 既存の ML 実験メモを 1 つ選び、再現に必要な情報が足りているか確認する。
3. リリース前チェックリストを、データ、モデル、評価、運用、責任分界に分けて作る。
