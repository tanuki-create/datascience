# 00. MLを現場でどう捉えるか

## 現場の問い

機械学習は「すごいモデルを選ぶ仕事」ではありません。現場では、データから意思決定ルールを作り、そのルールが未知のケースでも役に立つかを検証し、運用中に壊れたら原因を切り分ける仕事です。

最初に問うべきことは、次の 4 つです。

- 何を予測・分類・生成したいのか。
- その出力は誰のどの判断を変えるのか。
- 間違えたときの損失は何か。
- データは将来の利用条件を代表しているか。

## 直感

ML は「過去のデータに合う関数」を探します。ただし、現場で必要なのは過去に合う関数ではなく、将来の意思決定を改善する関数です。ここに gap があります。

たとえば問い合わせ優先度を予測するモデルで、過去の対応履歴だけを見ると「ベテラン担当者が対応した案件は解決しやすい」という規則を学ぶかもしれません。しかし本当に知りたいのは案件そのものの難しさです。この違いを見逃すと、モデルは現場の偏りを増幅します。

## 最小限の数式

多くの教師あり学習は、入力 `x` から出力 `y` を予測する関数 `f(x)` を学びます。

```text
予測: y_hat = f(x)
学習: loss(y, y_hat) が小さくなるように f を調整する
目的: 未知データでも loss が小さいこと
```

ここで大事なのは、`loss` が現場の損失を完全には表さないことです。二値分類の log loss が改善しても、見逃しコストが高い業務では recall が悪ければ採用できません。

## 実装で見るべきログ・指標

- データ件数、期間、欠損率、重複率、ラベル比率。
- 学習・検証・テストの分割方法。
- ベースライン指標と改善幅。
- 重要なセグメントごとの性能。
- 失敗例の具体的なサンプル。
- 推論時間、コスト、再学習頻度。

## よくある失敗

- モデル選定から始め、問題設定と評価指標が後付けになる。
- validation の平均値だけを見て、重要顧客・希少ケース・季節変動を見ない。
- データリークに気づかず、高すぎる精度を信じる。
- 推論時に取得できない特徴量を学習に使う。
- PoC の成功条件を決めず、いつまでも実験を続ける。

## 実務メモ

現場での第一成果物はモデルではなく、問題設定メモです。最低限、目的、利用者、意思決定、入力、出力、許容できない失敗、オフライン指標、オンライン確認方法を書きます。

「モデルが当たるか」より先に、「当たったとき現場が動けるか」を確認します。予測値を出しても、運用フロー、担当者、閾値、例外処理がなければ価値には変わりません。

## 演習

1. 自分の業務から ML を使えそうな課題を 1 つ選び、入力、出力、意思決定、失敗コストを書き出す。
2. その課題について、ML を使わないルールベース案を 1 つ作る。
3. ML 案がルールベース案より優れていると判断できる条件を決める。
