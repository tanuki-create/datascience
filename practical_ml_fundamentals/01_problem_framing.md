# 01. 問題設定、目的変数、業務指標

## 現場の問い

ML プロジェクトの失敗は、アルゴリズムより問題設定で起きます。特に危険なのは、「何を当てるか」と「何を改善したいか」がずれている状態です。

## 直感

目的変数は、現場の成功を代替する測定値です。代替なので、必ず歪みます。売上を増やしたいのにクリック率だけを最大化すると、短期的に目立つが購買につながらない候補を押し上げるかもしれません。

良い問題設定は、次を分けて書きます。

| 項目 | 例 |
|---|---|
| 業務目的 | 解約を減らす |
| ML 出力 | 30日以内の解約確率 |
| 行動 | 高リスク顧客にサポート連絡 |
| 成功指標 | 解約率、対応コスト、苦情率 |
| 制約 | 1日1回のバッチ推論、説明可能性が必要 |

## 最小限の数式

モデルの出力は、業務上の行動に変換されて初めて意味を持ちます。

```text
score = model(x)
action = policy(score, constraints)
business_value = outcome(action)
```

モデルだけを最適化しても、`policy` や `constraints` が悪ければ価値は出ません。

## 実装で見るべきログ・指標

- 目的変数の定義日と観測期間。
- 入力特徴量が推論時点で利用可能か。
- ラベルが遅れて到着するか。
- 予測結果を受け取る担当者と処理上限。
- 閾値を変えたときの対象件数とコスト。

## よくある失敗

- 目的変数が「測りやすいもの」になり、業務目的とずれる。
- 未来情報を特徴量に入れてしまう。
- ラベル定義が部署や時期で変わっている。
- 人が介入した履歴を「自然な正解」と誤認する。
- ML を使う前に、ルール・集計・UI 改善で十分かを検討しない。

## 実務メモ

最初の会議で「精度を上げたい」と言われたら、精度の前に意思決定を聞きます。誰が、いつ、どの予測を見て、何を変えるのか。それが答えられない案件は、モデルを作るほど曖昧さが増えます。

また、ML の出力を使う担当者の処理能力も制約です。1日 10,000 件のアラートを出せても、現場が 200 件しか処理できないなら、上位 200 件の precision や期待利益が重要になります。

## 演習

1. 「問い合わせの緊急度判定」について、目的変数を 3 通り考え、それぞれの欠点を書く。
2. 解約予測で、推論時に使ってはいけない特徴量を 5 個挙げる。
3. 閾値を 0.5 固定にしない方がよい理由を説明する。
