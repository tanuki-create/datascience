サービス名の丸暗記で終わらせず、「何を解決する機能か」「誰がどこまで管理するか」「どの制約で選ぶか」をセットで覚えます。

## 3. クラウドの概念（25–30%）

### 3.1 クラウドコンピューティング

クラウドコンピューティングは、インターネット経由で、必要な計算資源・ストレージ・ネットワークなどを利用する考え方です。自社で物理サーバーを購入・設置して固定的に保有する代わりに、必要な量をサービスとして使います。

クラウドの利点は「常に安い」ことではありません。需要変動への対応、初期投資の抑制、管理作業の外部化、世界各地への展開など、要件に合うときに価値が出ます。

### 3.2 クラウドモデル

| モデル | 概要 | 向いている例 |
|---|---|---|
| パブリッククラウド | 事業者の共有基盤上のサービスを、組織ごとに論理分離して利用 | 変動するWebサイト、新規サービス、短期検証 |
| プライベートクラウド | 1組織専用のクラウド環境 | 専用要件、既存設備との密接な統合 |
| ハイブリッドクラウド | オンプレミス/プライベートとパブリックを組み合わせる | 段階移行、データ保持要件、既存システムとの連携 |

「パブリック＝安全でない」「プライベート＝必ず安全」という意味ではありません。セキュリティは構成、設定、運用、責任分界で決まります。

### 3.3 CapExとOpEx

- **CapEx（資本的支出）**：サーバーや設備を先に購入する支出。容量を先に見積もり、余剰や不足のリスクを負います。
- **OpEx（運用支出）**：利用に応じて継続的に支払う支出。クラウドの従量課金はこの考え方と相性がよいです。

試験では、「クラウドにすれば必ず総額が下がる」ではなく、初期投資・利用量・運用負担・契約条件を含めて考えます。

### 3.4 従量課金と価格モデル

従量課金は、利用した量や時間に応じて支払うモデルです。コストは、次のような要因で変わります。

- リソースの種類・サイズ・性能
- 実行時間、保存容量、トランザクション数
- リージョン、通信の送信量
- 冗長性、サービス階層、ライセンス
- 予約、節約プラン、契約条件

試験対策では具体的な価格の暗記より、「価格計算ツールで見積もる」「Cost Managementで実績を分析する」「予算とアラートで監視する」という役割分担を覚えます。

### 3.5 共有責任モデル

クラウドでは、Microsoftと利用者が責任を分担します。クラウドのサービス形態がマネージドになるほど、Microsoftが管理する範囲は広がりますが、利用者の責任がなくなるわけではありません。

| 対象 | オンプレミス | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| 物理設備 | 利用者 | Microsoft | Microsoft | Microsoft |
| ホスト/基盤 | 利用者 | Microsoft | Microsoft | Microsoft |
| OS | 利用者 | 利用者 | Microsoft | Microsoft |
| ランタイム/ミドルウェア | 利用者 | 利用者 | Microsoft | Microsoft |
| アプリ設定・データ | 利用者 | 利用者 | 利用者 | 利用者 |
| ID・アクセス設定 | 利用者 | 利用者 | 利用者 | 利用者 |

これは一般的な整理です。PaaS/SaaSでも、アプリの設定、利用者、データ、アクセス権、アプリ内のコードやライブラリなどの責任は利用者側に残ります。具体的なサービスの責任分界は各サービスの公式資料で確認します。

### 3.6 IaaS、PaaS、SaaS

| 形態 | 利用者が主に管理するもの | 典型例 | 向いている場面 |
|---|---|---|---|
| IaaS | OS、ミドルウェア、アプリ、データ | Azure Virtual Machines | OSレベルの自由度が必要 |
| PaaS | アプリ、データ、設定 | Azure App Service、Azure SQL Database | 基盤運用を減らして開発に集中 |
| SaaS | データ、利用者、設定、使い方 | Microsoft 365など | 完成したアプリをすぐ使う |

**判断のコツ**：要件に「OSを自由に構成」「既存ミドルウェアを維持」とあればIaaS寄り、「コードをデプロイして基盤管理を減らす」とあればPaaS寄り、「完成した業務アプリを設定して使う」とあればSaaS寄りです。

### 3.7 サーバーレス

サーバーレスは、サーバーが存在しないという意味ではありません。利用者がサーバーのプロビジョニングやOS保守を意識せず、イベントや要求に応じて処理を実行する提供形態です。Azure Functionsが代表例です。

### 3.8 クラウドの主要な利点

- **高可用性**：障害があってもサービスを継続できる構成・能力。
- **スケーラビリティ**：処理能力を増減できる能力。1台を大きくするスケールアップと、台数を増やすスケールアウトがあります。
- **弾力性**：需要に応じて自動的にリソースを増減させ、使い終わったら戻せる性質。
- **信頼性**：設計した条件のもとで、期待どおりに動作し続ける性質。
- **予測可能性**：性能・コスト・動作を測定し、見通しを立てやすい性質。
- **管理容易性**：ポータル、CLI、API、テンプレートなどで、繰り返し管理しやすい性質。
- **ガバナンス**：組織のルールやコンプライアンスを、ポリシーや権限で適用・確認すること。

「可用性」と「スケーラビリティ」は別物です。処理能力が高くても1台が止まれば停止する設計はあり得ます。

### 3.9 SLA

**SLA（サービス レベル アグリーメント）**は、特定のサービスについて、一定の条件下で可用性などの提供水準を事業者が約束するものです。SLAの数値はアプリケーション全体の稼働率を保証するものではなく、設計・冗長化・運用の責任がなくなるわけでもありません。

公式：[AzureのSLAの概念](https://learn.microsoft.com/ja-jp/azure/reliability/concept-service-level-agreements)

## 4. Azureのアーキテクチャとサービス（35–40%）

### 4.1 Azureの物理構造

- **データセンター**：Azureの物理設備が置かれた施設。
- **リージョン**：1つ以上のデータセンターで構成される地理的なAzureの提供地域。
- **リージョンペア**：同じ地理圏内の2リージョンを組み合わせ、災害対策や更新の考慮に使う関係。
- **可用性ゾーン**：リージョン内で物理的に分離された場所。電源・冷却・ネットワークが分離されています。対応サービスを複数ゾーンへ配置することで、単一ゾーン障害への耐性を高めます。
- **ソブリンリージョン**：特定の国・政府・主権要件に対応するため、一般リージョンと分離された環境。

リージョン、リージョンペア、可用性ゾーンは、名前を暗記するだけでなく「どの障害範囲に耐えるための配置か」で覚えます。すべてのサービス・リージョンで同じ機能が使えるとは限りません。

### 4.2 Azureの管理階層

```text
管理グループ
└─ サブスクリプション
   └─ リソースグループ
      └─ リソース
```

- **管理グループ**：複数サブスクリプションをまとめ、ポリシーやアクセスを上位から管理する単位。
- **サブスクリプション**：課金・契約・アクセス管理の境界となる単位。
- **リソースグループ**：関連するリソースをまとめる管理単位。デプロイやライフサイクルをまとめやすい。
- **リソース**：VM、ストレージアカウント、VNetなど、Azure上で作成する個々のサービス実体。

リソースグループは単なるフォルダーではありません。ライフサイクル、アクセス、デプロイ、運用の単位として設計します。各リソースは同時に1つのリソースグループにのみ存在できます。

### 4.3 コンピューティングの比較

| 選択肢 | 管理負担 | 使いどころ |
|---|---|---|
| Virtual Machines | OSやパッチなどの管理が大きい | OSレベルの制御、既存ソフト、特殊構成 |
| VM Scale Sets | VM群の展開・スケールをまとめて管理 | 同じ構成のVMを複数台運用 |
| Availability Sets | 1データセンター内で更新/障害ドメインを分散 | VMの計画保守・局所障害への耐性 |
| App Service | OS・基盤を意識する量が少ない | WebアプリやAPIをコード中心で公開 |
| Azure Functions | イベント駆動、サーバー管理を極小化 | タイマー、HTTP、メッセージなどを契機に処理 |
| Container Instances | VMを管理せずコンテナーを実行 | 単発・小規模なコンテナー処理は代表例 |
| AKS | Kubernetesの運用機能を利用 | 複数コンテナー、オーケストレーション |
| Azure Virtual Desktop | 仮想デスクトップ/アプリを提供 | 利用者へWindowsデスクトップ環境を配布 |

**選び方**：OS管理が要件ならVM、Web/APIを素早く公開するならApp Service、イベント単位の処理ならFunctions、Kubernetesが要件ならAKSです。

#### VMに必要な主なリソース

VMは単体の名前だけで動くのではなく、少なくとも次の構成要素を組み合わせます。

- **VM本体**：CPU、メモリ、OSイメージ、サイズを定義する。
- **ディスク**：OSディスクと、必要に応じたデータディスクを用意する。
- **ネットワークインターフェイス（NIC）**：VMをVNetのサブネットへ接続する。
- **IPアドレス**：公開・内部通信の要件に応じて構成する。
- **ネットワークセキュリティ**：必要な通信だけを許可する。

試験では、VMのサイズだけでなく、OS、ディスク、ネットワーク、アクセス方法まで含めて「VMに必要なリソース」と考えます。

### 4.4 ネットワーク

- **Virtual Network（VNet）**：Azure内の論理的なネットワーク。サブネットに分割してリソースを配置します。
- **サブネット**：VNet内のアドレス範囲。役割やセキュリティ境界を分けます。
- **VNetピアリング**：VNet間をAzureのネットワークで接続する機能。異なるVNetのリソースを低遅延で接続する用途です。
- **VPN Gateway**：暗号化されたVPNトンネルで、インターネット経由の拠点間接続やクライアント接続を構成します。
- **ExpressRoute**：専用接続を使ってオンプレミスとAzureを接続する方式。通常のインターネット経由ではありません。
- **Azure DNS**：Azureでドメイン名の名前解決を提供します。
- **パブリックエンドポイント**：公開ネットワーク経由で公開される入口。実際の到達可否はファイアウォールやアクセス制御などの設定によります。
- **プライベートエンドポイント**：VNet内のプライベートIPを使って、Azureサービスへ私設に接続する入口。

#### VPNとExpressRouteの判断

| 要件 | 候補 |
|---|---|
| 既存インターネットを使い、暗号化トンネルで接続したい | VPN Gateway |
| 専用回線・予測可能な接続・インターネット非経由が必要 | ExpressRoute |
| Azure内のVNet同士を接続したい | VNetピアリング |

### 4.5 ストレージ

| サービス | データの形 | 代表的な用途 |
|---|---|---|
| Blob Storage | オブジェクト/非構造化データ | 画像、動画、バックアップ、ログ |
| Azure Files | マネージドファイル共有 | SMB/NFSの共有フォルダー、既存アプリのファイル共有 |
| Queue Storage | メッセージ | 非同期処理、処理待ちキュー |
| Table Storage | キー・属性型のNoSQL | 単純なキー値データ |

#### ストレージ層

Hotは頻繁にアクセスするデータ、Cool/Coldはアクセス頻度が低いデータ、Archiveは長期保管向けです。低頻度・長期保存ほど保管単価が下がる一方、読み出し遅延やアクセス料金などの条件を確認します。

#### 冗長性

| 方式 | 主な考え方 |
|---|---|
| LRS | 1つの物理的な場所で複数コピーを保持。ゾーン障害やリージョン障害への耐性を目的としない |
| ZRS | 1リージョン内の複数可用性ゾーンへ分散 |
| GRS | 別リージョンへ非同期レプリケーション |
| RA-GRS | GRSに加え、セカンダリへの読み取りを提供 |
| GZRS/RA-GZRS | ゾーン分散とリージョン分散を組み合わせる方式 |

どの方式が最適かは、障害範囲、読み取り要件、RPO/RTO、費用で決まります。略語だけを暗記せず、「どこへコピーするか」を説明してください。

#### データ移行・ファイル移動

- **AzCopy**：コマンドラインでAzure Storageとのデータ転送を行う。
- **Azure Storage Explorer**：GUIでストレージを操作する。
- **Azure File Sync**：オンプレミスのWindows ServerとAzure Filesを同期する。
- **Azure Migrate**：移行対象の検出・評価・移行計画などを支援する。
- **Azure Data Box**：大容量データを物理デバイスで搬送し、ネットワーク転送を減らす。

#### ストレージアカウントの選択軸

ストレージアカウントは、データサービスをまとめて利用するための管理・課金上の単位です。選択時は、ストレージの種類（Blob、Files、Queue、Table）、性能（Standard/Premium）、冗長性、アクセス層、レプリケーション、必要なプロトコルを確認します。製品名や選択肢の細部は更新されるため、受験前に [Azure Storageの公式ドキュメント](https://learn.microsoft.com/ja-jp/azure/storage/common/storage-account-overview) を確認してください。

### 4.6 データベースの基本

AZ-900では、製品の細かな設定よりも、データの性質と管理負担から候補を見分けます。

- **リレーショナルデータベース**：表、スキーマ、リレーション、SQL、トランザクションを中心に扱う。定型的な業務データや整合性を重視する処理に向きます。
- **NoSQLデータベース**：固定スキーマに依存しないモデルや、分散スケールを重視する。大量・多様・低遅延のデータを扱う場面で検討します。
- **Azure SQL Database**：SQL Server互換のリレーショナルデータベースをマネージドサービスとして利用する代表例です。
- **Azure Cosmos DB**：グローバル分散や低遅延を考慮するNoSQLの代表例です。

「SQLだから常に正解」「NoSQLだから常に高速」ではありません。データモデル、整合性、クエリ、スケール、運用責任を要件と照合します。

### 4.7 ID・アクセス・セキュリティ

- **Microsoft Entra ID**：クラウドのIDおよびアクセス管理基盤。旧称Azure Active Directory。
- **Microsoft Entra Domain Services**：ドメイン参加、LDAP、Kerberos/NTLMなど、従来型のドメイン機能をマネージドで提供する。
- **認証（Authentication）**：利用者、デバイス、アプリケーションなどの主体が、主張するIDであることを確認する。
- **認可（Authorization）**：確認済みの主体が何を実行できるかを判定する。
- **SSO**：一度のサインインで複数アプリを利用する。
- **MFA**：複数の要素で本人確認を強化する。
- **パスワードレス**：パスワードを使わず、FIDO2やパスキーなどの認証器を使用する。生体情報やPINは、認証器の解除に使われる場合があります。
- **外部ID**：組織外のユーザーを、必要な範囲でアプリやリソースへ招待・連携する。
- **条件付きアクセス**：ユーザー、場所、端末、アプリ、リスクなどの条件に応じ、許可・MFA要求・ブロックなどを行う。
- **Azure RBAC**：Azureリソースに対して、誰にどの操作を許可するかを、管理グループ、サブスクリプション、リソースグループ、リソースなどのスコープで割り当てる。
- **Zero Trust**：「明示的に検証する」「最小権限を使う」「侵害を前提にする」という考え方。
- **多層防御**：ID、ネットワーク、ホスト、アプリ、データなど複数の層で防御する。
- **Microsoft Defender for Cloud**：クラウド環境のセキュリティ体制を可視化し、推奨事項やワークロード保護を提供する。

**RBACと条件付きアクセスの違い**：条件付きアクセスはサインイン時の条件判断、RBACはAzureリソース操作の権限割り当てです。

## 5. Azureの管理とガバナンス（30–35%）

### 5.1 コスト管理

| 機能 | 役割 |
|---|---|
| Pricing Calculator | 作成前に構成を入力し、概算を見積もる |
| Cost Management/Cost Analysis | 発生したコストを分析し、傾向や内訳を見る |
| Budget | 設定した金額や予測額に対して通知する |
| タグ | 所有者、環境、部門、案件などでリソースを分類し、コスト配賦・検索に使う |
| Advisor | コストや性能などの改善提案を受ける |

予算アラートは通知の仕組みです。しきい値を超えたからといって、リソースが自動停止するとは限りません。Azure公式ドキュメントでは、予算のしきい値を超えてもリソースは影響を受けず、消費は停止されないと説明されています。

### 5.2 ガバナンスとコンプライアンス

- **Azure Policy**：組織のルールに対するリソースの準拠を評価・制御する。効果には監査、拒否、変更などがあり、既存リソースの修正が必要な場合は別途修復操作を行う。例：特定リージョンだけ許可、必須タグを要求、特定SKUを禁止。
- **リソースロック**：誤削除や誤変更を防ぐ。ReadOnlyやCanNotDeleteなどの種類があり、運用・デプロイを妨げることがあるため、適用範囲を確認する。
- **Microsoft Purview**：データ資産の発見・分類・ガバナンスや、コンプライアンス/リスク管理に関する機能を提供する。
- **タグ**：分類・検索・コスト分析のためのメタデータ。タグは権限管理や暗号化の代替ではありません。
- **Azure Key Vault**：シークレット、キー、証明書などを保護して管理するためのサービス。アプリのソースコードや設定ファイルへ秘密情報を直書きしないために使います。

#### Policy、RBAC、ロック

| 目的 | 選ぶ機能 |
|---|---|
| その主体が操作できるかを決める | Azure RBAC |
| そのリソース構成が組織ルールに適合するかを確認・制御する | Azure Policy |
| 誤って削除・変更する事故を防ぐ | リソースロック |

### 5.3 管理・デプロイのツール

- **Azure portal**：ブラウザーのGUI。初学者がリソースを確認・作成・設定する入口。
- **Azure Cloud Shell**：ブラウザーから利用できるシェル環境。BashまたはPowerShellを使える。
- **Azure CLI**：コマンドラインからAzureを管理するツール。
- **Azure PowerShell**：PowerShellのコマンドレットでAzureを管理するツール。
- **Azure Resource Manager（ARM）**：Azureリソースのデプロイ・管理の制御面。RBAC、タグ、Policyなどの管理単位と関係する。
- **ARMテンプレート**：Azureリソースを宣言的に定義するJSONテンプレート。繰り返し可能なデプロイに使う。
- **Infrastructure as Code（IaC）**：インフラ構成をコードで管理し、レビュー・再現・自動化する考え方。
- **Azure Arc**：Azure外のサーバー、KubernetesなどをAzureから管理・統制するための仕組み。

GUIで1回作るだけならポータル、繰り返し・自動化・レビューが必要ならCLI/PowerShell/IaCを検討します。

### 5.4 監視・改善

| 機能 | 問い | 代表的な使い方 |
|---|---|---|
| Azure Advisor | どう改善すべきか | コスト、性能、信頼性、セキュリティの推奨事項を見る |
| Azure Service Health | Azure側で自分に影響する問題はあるか | 障害、計画メンテナンス、正常性アドバイザリを確認 |
| Resource Health | 個別リソースは利用可能な状態か | 特定VMやサービスインスタンスの状態・履歴を確認 |
| Azure Monitor | リソースやアプリはどう動いているか | メトリック、ログ、アラートを集約・分析 |
| Log Analytics | ログを検索・分析したい | KQLでログを調査 |
| Azure Monitor Alerts | 条件を満たしたら通知したい | メトリック/ログのしきい値で通知やアクション |
| Application Insights | アプリの性能・失敗を知りたい | リクエスト、依存関係、例外、可用性を調査 |

**混同防止**：Service HealthはAzureサービス側の障害・計画メンテナンス等、Resource Healthは個別リソースの状態、Monitorは自分のリソースやアプリの観測、Advisorは改善提案です。

## 6. 重要比較カード

### 6.1 IaaS/PaaS/SaaS

> 自由度が高いほど利用者の管理責任が増え、マネージドになるほど基盤管理は減る。

### 6.2 VPN/ExpressRoute/VNetピアリング

> インターネット経由の暗号化ならVPN、専用接続ならExpressRoute、Azure内のVNet間ならピアリング。

### 6.3 認証/認可/RBAC/条件付きアクセス

> 認証は「どの主体か」、認可は「何ができるか」。条件付きアクセスはサインイン条件、RBACはAzureリソース操作の権限。

### 6.4 Policy/ロック/タグ

> Policyはルール適合、ロックは事故防止、タグは分類・コスト分析。

### 6.5 Advisor/Service Health/Resource Health/Monitor

> Advisorは改善提案、Service HealthはAzure側の影響情報、Resource Healthは個別リソースの状態、Monitorはリソース・アプリの観測。

## 7. 低コストのハンズオン

詳細手順は、作成操作を伴う3ラボ（表の実習2〜4）について [AZ-900_hands_on_safe.md](./AZ-900_hands_on_safe.md) を参照してください。実習1・5・6はポータルの閲覧・確認を中心とし、新しい課金リソースを作成しない前提です。

実機操作は理解の補助です。試験準備だけならMicrosoft Learnの演習でも構いません。実機で行う場合は、**ラボごとに専用のリソースグループを作り、終了時にそのリソースグループの中身を確認してから全体を削除**します。Azure無料アカウントや従量課金を使う場合は、アカウント条件・無料枠・対象サービス・リージョンを必ず確認してください。

| 実習 | 操作の目的 | 確認ポイント | 終了処理 |
|---|---|---|---|
| 1. ポータル探索 | 専用RG、サブスクリプション、リージョンを確認 | 管理グループ→サブスクリプション→RG→リソースを説明する | RG内を確認してRGごと削除 |
| 2. ストレージ作成 | Storage Account、Blobコンテナー、テスト用Blobを確認 | Blob、Files、Queue、冗長性の用途を言う | データが不要なことを確認し、RGごと削除 |
| 3. App Serviceの確認 | **Free/F1の提供条件を確認したうえで** Web AppとApp Service Planを確認 | PaaSとVMの管理責任を比較する | Web App、Planを確認し、RGごと削除 |
| 4. VNetとサブネットの設計 | VNetとサブネットだけを作成し論理分割を確認 | VNet、サブネット、エンドポイントを説明する | VNet、サブネットを確認し、RGごと削除 |
| 5. タグとコスト表示 | RGやテストリソースに環境タグを付け、Cost Managementを閲覧 | タグとRBAC/Policyの違いを言う | RGごと削除。予算は不要なら解除 |
| 6. Service Health/Advisorの閲覧 | 新規のログ収集基盤を作らず、既存画面を確認 | 監視・改善・サービス状態を区別する | Alert、Action Group、Workspaceを作った場合はRGごと削除 |

**課金上の注意**：現在の公式案内では、新規ユーザー向けの無料アカウントはUSD 200のクレジットを最大30日間利用できます。30日経過またはクレジット消費後、継続利用を選ぶ場合は従量課金制へ移行します。移行しない場合はアカウントとサービスが無効になるため、「何もしなくても自動的に課金される」という意味ではありません。無料枠・F1・Functions・ログ取り込みの条件は同一ではありません。予算アラートは通知であり、課金やリソースを自動停止する機能ではありません。

課金条件を確認できない場合は、Functions、VM、VPN Gateway、NAT Gateway、Firewall、Bastion、Private Endpoint、Log Analytics/Application Insightsのデータ取り込みを作成しないでください。

公式：[Azureの無料アカウント/購入オプション](https://azure.microsoft.com/ja-jp/pricing/purchase-options/azure-account)、[コストのアラート](https://learn.microsoft.com/ja-jp/azure/cost-management-billing/costs/cost-mgt-alerts-monitor-usage-spending)
