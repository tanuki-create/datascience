# Part 12　有限状態機械とオートマトン

## 学習目標

- 状態、入力、遷移、受理状態を使って有限状態機械を定義できる。
- DFAとNFAの違いを説明できる。
- 正規表現と正規言語の関係を、簡単な例で追跡できる。
- 字句解析、通信プロトコル、UI状態管理を状態機械としてモデル化できる。

## まず直感

自動販売機は、投入金額と選択ボタンに応じて状態を変えます。

「0円」「100円」「200円」「商品購入可能」のような状態を持ち、コインやボタンを入力として遷移します。

状態機械は、履歴をすべて保存する代わりに、将来の動作に必要な情報だけを状態へ要約します。

ログイン画面の「未入力」「入力中」「認証成功」「ロック中」も同じ構造です。

## 正式な定義

**DFA（決定性有限オートマトン）**は、五つ組 `(Q,Σ,δ,q0,F)` です。

- Q：有限個の状態集合。
- Σ：入力アルファベット。
- δ：`Q×Σ→Q` の遷移関数。
- q0：初期状態。
- F：受理状態の集合。

入力文字列を左から一文字ずつ読み、最後の状態がFに属せば受理します。

**NFA（非決定性有限オートマトン）**は、一つの状態と入力から複数の遷移先を持てます。

NFAは、可能な経路の少なくとも一つが受理状態へ到達すれば受理します。

DFAとNFAは表現力の点では同じ正規言語を認識しますが、状態数や実装方法が変わることがあります。

## 最小の具体例

0と1からなる文字列で、「末尾が01」のものを受理するDFAを考えます。

```text
q0 --0--> q1 --1--> q2*
 |         |          |
 1         0          0,1
 |         v          v
 └─────── q0 <────── q2*
```

`q0` は末尾が条件に近づいていない状態、`q1` は直前に0を読んだ状態、`q2`は末尾が01の状態です。

実際にはq2から0を読めばq1、1を読めばq0など、すべての入力に遷移を定義します。

## 手計算

入力 `1101` を読むとします。

```text
開始 q0
1: q0 → q0
1: q0 → q0
0: q0 → q1
1: q1 → q2
```

最後がq2なので受理します。

入力 `1100` なら最後はq1で、受理しません。

## 正規表現と正規言語

DFAやNFAが受理できる文字列の集合を正規言語と呼びます。

正規表現 `0*1` は、「0を0回以上並べた後に1が一つ来る」文字列を表します。

`0001` は一致しますが、`0010` は一致しません。

実際の正規表現エンジンには、バックトラッキングや拡張機能があり、形式言語としての正規表現と完全に同じ挙動とは限りません。

## NFAからDFAへの考え方

NFAが複数の状態にいられると考え、その状態集合全体をDFAの一状態にします。

この方法を部分集合構成と呼びます。

NFAの状態数がnなら、DFAの状態数は最大で `2^n` になる可能性があります。

表現は簡潔になっても、決定化で状態数が増える点が重要です。

## 証明の設計と完全な証明

文字列の先頭から決められた有限個の記号を読むDFAは、入力を読み終えた時点で必ず高々一つの状態にいます。

### 何を示すか

決定性という性質が、遷移関数の定義から出ることを示します。

### 完全な証明

DFAの遷移関数は `δ:Q×Σ→Q` です。

関数は、各入力対 `(q,a)` に対して出力状態を一つだけ割り当てます。

したがって現在状態qと次の入力aが決まれば、次の状態δ(q,a)は一意です。

文字列を一文字ずつ読むたびにこの一意な遷移を適用するため、入力全体を読んだ後の状態も一意です。

## 擬似コードとPython

```text
accepts(machine, word):
    state = machine.start
    for symbol in word:
        state = machine.delta[state][symbol]
    return state in machine.accepting
```

```python
def accepts(delta, start, accepting, word):
    state = start
    for symbol in word:
        state = delta[state][symbol]
    return state in accepting

delta = {
    "q0": {"0": "q1", "1": "q0"},
    "q1": {"0": "q1", "1": "q2"},
    "q2": {"0": "q1", "1": "q0"},
}
assert accepts(delta, "q0", {"q2"}, "1101")
```

入力長をnとすると、DFAのシミュレーションは `O(n)` 時間、状態一つだけを持つため追加空間は `O(1)` です。

## 応用

- 字句解析：識別子、数値、コメントなどのトークンを認識する。
- コンパイラ：文字列をトークン列へ分解する。
- 通信プロトコル：接続前、接続中、認証済み、切断などの手順を制約する。
- UI状態管理：画面の状態とイベントによる遷移を管理する。
- 入力検証：メールアドレスや識別子の形式を限定的に検査する。

## よくある誤解

- NFAは「ランダムに一つを選ぶ機械」ではなく、受理可能な経路の存在を判定する数学モデルです。
- 正規表現は文字列検索の便利な記法ですが、実装によって使える拡張が違います。
- 状態を増やせば、どんな長期記憶も有限状態で表せるわけではありません。
- DFAの遷移を未定義にすると、完全なDFAの定義から外れるため、拒否用のsink状態を加えることがあります。
- UIの状態を一つの真偽値で表すと、同時にあり得ない状態が混ざることがあります。

## 演習問題

### ★ 基本

1. DFAの五つ組の各要素の意味を説明してください。
2. `0*1`に一致する文字列を二つ、しない文字列を二つ挙げてください。

### ★★ 標準

3. 末尾が0の二進文字列を受理するDFAの状態を考えてください。
4. 文字列`0101`を上のDFAで手計算してください。

### ★★★ 応用

5. NFAがDFAより簡潔に書ける例を、複数の受理経路という観点で説明してください。
6. UIの「未保存」「保存中」「保存済み」「エラー」を状態機械にしてください。

### ★★★★ 発展

7. 「0と1の個数がともに偶数」のDFAに必要な最小限の状態の意味を説明してください。

## 解答と思考プロセス

1. 状態、アルファベット、遷移関数、初期状態、受理状態です。
2. 一致は`1`,`001`、不一致は`0`,`010`です。
3. 「直前の文字が0か、それ以外か」の二状態を作り、入力の0で0状態、1で非0状態へ遷移します。
4. `q0→q1→q1→q2→q1` となり、末尾が01なら受理するDFAでは最後のq1により拒否します。
5. NFAは「この位置から始まる」「別の位置から始まる」候補を同時に持つように書けます。
   DFAへ変換すると候補集合を一つの状態にまとめるため、状態数が増えることがあります。
6. 保存ボタンは未保存→保存中→保存済み、通信失敗は保存中→エラー、再試行で保存中へ戻すなど、許されたイベントだけに遷移させます。
7. 0の個数の偶奇と1の個数の偶奇を記憶するので、`偶偶、偶奇、奇偶、奇奇`の4状態が必要です。

## 専門家の見方

### このセクションの読み方

ここでいう共通土台は、すべての専門家が一つの実装方式を支持するという意味ではなく、オートマトンを議論するときに多くの専門家が共有する概念上の足場です。

形式言語理論で確定した定義と、正規表現エンジンや状態管理フレームワークを選ぶ実務上の判断は分けて扱います。

### 5つの中核的なメンタルモデル

#### 1. オートマトンは入力を読む状態更新器である

定義：オートマトンは、有限個の状態、入力記号、初期状態、遷移規則、受理状態を使って、入力列を一文字ずつ処理するモデルです。

境界条件：有限オートマトンが保持できる記憶は有限個の状態に限られ、入力の長さをそのまま無制限に数えたり、任意のスタックを保持したりはできません。

他章との接続：遷移を選ぶ条件はブール代数で表せ、文字列の集合としての言語は集合と関数の章で扱った写像の考え方につながります。

コードや現実のモデル化への意味：入力イベントごとに現在状態と次の状態を明示すれば、UI、通信プロトコル、字句解析を追跡可能な状態更新として設計できます。

#### 2. 状態は未来の判定に必要な履歴の要約である

定義：同じ状態にまとめられた二つの履歴は、どのような将来の入力を続けても受理・拒否の結果が同じになるという意味で、将来に関して区別不要です。

境界条件：状態の最小数は図の書き方の好みではなく、対象言語が要求する区別の数で決まり、有限状態で要約できない言語もあります。

他章との接続：末尾の記号、個数の偶奇、接頭辞の種類などを状態へ圧縮する考え方は、アルゴリズムの不変条件と計算量評価に接続します。

コードや現実のモデル化への意味：状態に「これまでの全履歴」を詰め込むのではなく、今後の許可・拒否を変える情報だけを残すと、実装の網羅性とテスト可能性が上がります。

#### 3. 非決定性は複数の可能性の存在を表す

定義：NFA（非決定性有限オートマトン）では、同じ状態と入力から複数の遷移先を許し、少なくとも一つの経路が受理状態に到達すれば入力を受理します。

境界条件：非決定性はランダムに一つを選ぶ意味ではなく、数学的には受理経路の存在を表す量化です。

他章との接続：NFAからDFAへの部分集合構成は、複数の候補状態を一つの集合状態へまとめる変換であり、集合演算と正規表現の構成に接続します。

コードや現実のモデル化への意味：仕様を書くときは候補経路を簡潔に表せますが、実行時には並列追跡、メモ化（計算結果を保存して再利用する方法）、決定化、バックトラッキングのどれを採用するかを別に決めます。

#### 4. 正規表現は記法であり、エンジンは実行方式である

定義：形式言語としての正規表現は正規言語を記述する記法であり、エンジンはその記法をオートマトンや探索手続きへ変換して入力を処理する実装です。

境界条件：後方参照、再帰、実装固有の先読みなどを含む拡張は、古典的な正規言語の範囲を超えることがあり、同じ記法名でも計算量の保証が異なります。

他章との接続：DFAは入力長に比例するシミュレーションをしやすく、NFAは記述を簡潔にしやすい一方、変換や探索で状態数・時間が増える可能性があります。

コードや現実のモデル化への意味：正規表現を採用するときは、パターンの意味だけでなく、使用するエンジン、最悪計算量、入力上限、タイムアウトを仕様に含めます。

#### 5. 形式的な状態機械と実装フレームワークは異なる層である

定義：形式的な状態機械は状態・入力・遷移・受理や不変条件（常に守る条件）を数学的に定め、フレームワークはイベント配信、非同期処理、永続化、表示更新などの実行環境を提供します。

境界条件：フレームワークのオブジェクトやコールバックが存在しても、許される遷移、同時実行、失敗時の状態、再入を定義したことにはなりません。

他章との接続：形式モデルはモデル検査やテストケース生成に使え、実装フレームワークはそのモデルをイベント駆動システムへ接続します。

コードや現実のモデル化への意味：フレームワークのAPIを先に中心へ置くのではなく、状態遷移表と不変条件を決めてから、イベント処理や画面更新へ割り当てます。

### 3つの代表的な対立軸

#### 対立軸1: DFA中心の決定性とNFA中心の記述の簡潔さ

この対立は、実行時の一意性と予測可能なコストを目的にするか、仕様の合成しやすさと表現の短さを目的にするかという前提・コストモデル・設計哲学の違いです。

立場A：DFAを実行の中心にする。

立場Aの最も強い主張：現在状態と入力から次状態が一つに決まるため、入力長に比例する追跡をしやすく、実行時間、メモリ、デバッグ結果を予測しやすいです。

立場B：NFAを仕様や構築の中心にする。

立場Bの最も強い主張：選択肢を分岐として直接書けるため、正規表現の連結・選択・繰り返しを自然に合成でき、同じ言語をより小さな記述で表せる場合があります。

どの条件で選択が変わるか：入力を大量に長時間処理し、予測可能性や共有キャッシュを重視するならDFA寄りになりますが、パターンの構築、更新、説明の容易さを重視するならNFA寄りになります。

理論上はDFAとNFAが表す正規言語の範囲は同じですが、決定化で状態数が指数的に増える可能性があるため、実務上のコストは同じではありません。

#### 対立軸2: オートマトン型の正規表現エンジンとバックトラッキング型エンジン

この対立は、正規言語の範囲で最悪計算量を保証する目的と、拡張構文・優先順位・既存パターンとの互換性を重視する目的の違いです。

立場A：DFAやNFAを基礎にしたオートマトン型エンジンを使う。

立場Aの最も強い主張：古典的な正規言語の機能に限定すれば、入力長に対して安定した処理時間を設計しやすく、敵対的な入力による過剰な探索を抑えられます。

立場B：バックトラッキング型エンジンを使う。

立場Bの最も強い主張：部分一致の優先順位、後方参照、先読みなどの実用的な拡張を既存の記法で表しやすく、利用者が期待する検索結果を細かく制御できます。

どの条件で選択が変わるか：信頼できない長い入力を受けるサービスや字句解析では立場Aを優先しやすいですが、拡張構文が要件で入力上限とタイムアウトを管理できるなら立場Bも選択肢になります。

未解決の点：表現力、結果の優先順位、最悪計算量、互換性を一つの方式で同時に最大化する一般解は未解決であり、エンジンごとの仕様確認が必要です。

#### 対立軸3: 形式的な状態遷移表と実装フレームワーク中心の状態管理

この対立は、全状態と遷移を明示して検証可能にする目的と、イベント、非同期処理、依存性注入、画面更新をフレームワークへ委ねる目的の違いです。

立場A：形式的な状態機械を先に定義する。

立場Aの最も強い主張：許される遷移と不変条件を列挙すれば、到達不能状態、処理漏れ、異常時の戻り先をテストと証明の対象にできます。

立場B：実装フレームワークのイベントモデルを中心に設計する。

立場Bの最も強い主張：非同期イベント、購読解除、永続化、UI更新などの現実の複雑さを、実績のあるライフサイクルと部品へ委ねることで開発と運用のコストを下げられます。

どの条件で選択が変わるか：安全性やプロトコルの正しさが重要で状態数が管理可能なら立場Aを強めますが、画面や外部サービスとの連携が主な複雑さなら立場Bの仕組みを利用します。

形式モデルを作れば実装の正しさが自動的に保証されるわけではなく、フレームワークを採用すれば遷移の正しさが自動的に定まるわけでもありません。

### 理解の深さを見分ける10の質問

1. 「末尾が01の二進文字列」を受理するDFAの状態を、直前の二文字を保存する設計と、未来の判定に必要な情報だけを保存する設計の二通りで説明し、状態数を比較してください。

2. NFAの「少なくとも一つの経路が受理する」という定義を、存在量化（ある経路が存在するという主張）を使わず、探索アルゴリズムの言葉へ翻訳してください。

3. `0*(1|01)`をNFAとして構成するなら、どの分岐をどの状態で表しますか。

4. そのNFAをDFAへ決定化するとき、DFAの一つの状態がNFAの状態集合になる理由を説明し、状態数が急増し得る入力構造を考えてください。

5. 「DFAのシミュレーションは常に一定の追加空間で動く」という主張が成立する条件を、遷移表の保存方法、入力の読み方、決定化後の状態数に分けて説明してください。

6. 後方参照を含む正規表現が、古典的な正規言語の正規表現と同じ意味ではない理由を、有限状態だけでは保持しにくい情報の例で説明してください。

7. バックトラッキング型エンジンが同じ入力を何度も試す可能性を示すパターンを作り、入力長に対する時間の増え方と、サービスで設定すべき防御策を検討してください。

8. 「認証前」「認証中」「認証済み」「失効」「通信失敗」を持つプロトコルについて、各状態で許されないイベントを一つずつ挙げ、遷移表にないイベントの扱いを設計してください。

9. UIフレームワークのコールバックを状態遷移へ対応付けるとき、二重クリック、遅れて届く応答、画面破棄後の応答のどれを状態・イベント・ガード条件（遷移を許可する追加条件）のどこで扱うか説明してください。

10. 有限状態機械で「入力中の0の個数と1の個数が同じ」を認識できるかを判断し、可能なら状態の意味と数を、困難なら有限状態の記憶制約を根拠に説明してください。
